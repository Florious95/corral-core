# 任务书 · core 变成「被引用的发布产物」，app 壳搬进 corral-app

## 用户要的是什么（原话与解读）

> 「我希望以后关于性能这方面的东西能够稳定地在 core，如无必要不要改这个代码仓库。
> 另外其他的改动可以和它隔离开，APP 可以稳定地在 APP 那个仓库去改，并且禁止改 core 相关的代码。」
> 「如果说 APP 那边也影响性能，那就从 APP 去入手解决。那核心至少可以保留绝大部分的变量。」

**解读（leader 已与用户对齐）**：core 不是「性能的保险箱」，而是**把一大批变量钉死的地方**。
八个性能打点里**六个在壳、两个沾核**，所以边界不能按仓划、要按**代码位置**划；
而「禁止从 app 侧改核」必须靠**依赖形态**强制——app 仓里没有核源码，物理上就改不了。

## 底座与红线

- 当前稳定基线：tag `baseline-20260822-release`，真机金标准已过（蜂窝+中转节点「秒开、没有空白」）。
  **⛔ 本轮任何产物不许低于它**；判据 `tools/perfbase/judge-perf-nonregress.sh`。
- ⛔ 席位不许 `git push` / 动 `mirror-pr*.sh` / 碰远端仓库；推 maven 分支与推 corral-app 是 leader 的动作。
- ⛔ 不许拆掉 PerfTrace 仪表与 `addBinaryListener` 按 ref 分发的修复（量具没了就没法自证不回退）。
- ⛔ 不许改 `tools/perfbase/*.sh`（判据不许绕）。
- ⛔ 不开模拟器（t.perf 那格除外）、⛔ 不碰 9900、⛔ 不点真实舰队会话、⛔ 不写 /tmp、⛔ 不读 `.env`。
- ⛔ **不许给 leader 发消息**：唯一出口是 `report_result` + 落盘产物；只有**编排调整**才允许发一条。

## 🔴 本轮的 worktree 纪律（上一条链的教训，必须遵守）

**所有施工格共用同一棵 worktree `wt-ca`，串行推进。**
上一条链吃过两次亏：① 两棵树改同一批文件 ⇒ land 时 add/add 冲突；
② 某格的树建在上游 land 进 main 之前 ⇒ 切出来的包里没有仪表、取数 0 行。
共用一棵树 ⇒ 后一格直接看到前一格的成果，不存在基点错，也不与 land 竞速。

## 格 3 · t.capp —— corral-app 只引用产物（判据 `judge-capp.sh`）

## 格 4 · t.perf —— 用引用式构建的 APK 复测性能门（判据 `judge-perf-nonregress.sh`）

- 被测物 = 格 3 装出的那个 APK（记 md5 与来源）；
- 流程与 `.team/tasks/perfbase/任务书-02-基线.md` **完全相同**：模拟器 `agentmirror_test_b`、
  三夹具各 ≥10 次冷点开、**只从 `adb logcat -s PerfTrace` 取数**（⛔ 不识图/不取帧/不取帧间隔）、
  **极端值不剔除**（另列 outliers）、**每批记 load 读数**；
- 落 `.team/perf/recheck-<日期>-capp.json`（形状同基线文件）；
- 逐夹具逐段比 p50/p95，超基线 **+10%** 即红。⛔ 不许换夹具/换次数/换取数方式来让它变绿；
- 环境不具备或数据不齐 ⇒ **如实报不可判**，那是合法终态。
