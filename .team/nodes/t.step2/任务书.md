
# 任务书 · t.step2 · core-protocol：客户端能发裸字节（输入透传第 2 步）

## 一、目标与验收（⛔ 别自己发明标准）

**产品目标**：让所有键盘操作与鼠标点击对被投影的 Agent 界面**完全生效**；鼠标归**内层 Agent**。

**最终验收是用户真机「秒开无空白」**（092 §11 金标准），⛔ 不是任何量具的绿。
**性能是本产品最核心的体验，不许回退**。

**这一格的位置**：第 1 步已把服务端的闸打开（`Bytes` 字段已在协议里，见下），
但**客户端还表达不出任意字节**。这一格只做「能表达」，⛔ 不做鼠标编码（那是第 3 步）。

## 二、现状（已核实，⛔ 不必重查，但要自己确认行号）

**服务端侧（已完成，不用动）**：
- `server/internal/protocol/frames.go:167-171`：`Bytes` 是裸字节透传通路，
  **JSON 编码为标准 base64**；**老客户端省略该字段时与 pre-Bytes 路径逐字节相同**。
- `frames.go:173`：`Text` / `Keys` / `Bytes` / `AttachmentPath` **两两互斥**。
- 服务端注入切分在 `server/internal/bridge/inject_raw.go`（可打印段 `-l` / 控制段 `-H`，
  一次调用一段，⛔ 不是一字节一进程）。

**客户端侧（这一格要动）**：
- `app/core-protocol/src/main/java/dev/agentmirror/app/conn/Frames.kt:351` `data class InputFrame`
  —— 目前只有 `text` / `keys` 一类的表达，**没有裸字节**。你要自己核清它现有字段。
- 发送侧在 `app/core-conn/.../ConnectionManager.kt`（`sendKeystroke` 等），
  第 1 步实测过：它发 `InputFrame(text=char)` 且**不追加回车**。

## 三、要做什么

给客户端加**裸字节输入**的表达与发送路径。必须满足：

1. **线格式必须与服务端对得上**：`Bytes` 走**标准 base64**（`frames.go:167-171`）。
   ⛔ 不许自创编码、⛔ 不许 URL-safe 变体除非服务端也认。
   **要有一条测试用真实字节做往返断言**（编码 → 解码 → 与原字节逐字节相同）。
2. **互斥必须在客户端就守住**：同一个 `InputFrame` 里 `text` / `keys` / `bytes`
   **不许同时非空**（服务端会拒，但客户端不该发出注定被拒的帧）。
   要有测试断言这条。
3. **向后兼容是硬性的**：不发 `bytes` 时，序列化出来的 JSON 必须与改前**逐字段相同**
   （⛔ 不许多出一个 `"bytes":null` 之类的字段而改变线格式）。**要有测试断言这条。**
4. **`input_ack` 语义不变**，⛔ 这一格不碰 ack 节奏（那是第 5 步与预测回显的合并决定）。
5. **上限**：客户端侧要尊重服务端的 `max-input-bytes`（缺省 1 MiB）——
   至少不要在客户端无脑拼一个超大帧。怎么处理由你定，但要在说明里写清。
6. ⛔ **不许在这一格碰鼠标编码、不许碰终端仿真、不许碰 UI**。
   这一格只让「客户端能把任意字节表达并发出去」。
