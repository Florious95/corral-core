# 现场基 · study-herdr-agent-state

## 用户裁定（2026-08-12，直接否掉现行路线）

> 「你假如说认为这两种，一个是完成态，一个是工作中态，还在通过这样的**字符串形式**
>  去确定它的工作状态，那就**完全走偏了**。并且**这两个实际上都是完成的状态**。
>  你可以通过 **herdr** 这个仓库去确定如何正确的检测 Agent CLI 的状态。」

## 实证：字形/字符串层面无法分辨状态

Claude Code 的两种输出，leader 一度误判为「一个工作、一个完成」：

```
※ Brewed  for 42m 3s
✳ Churned for 3m 37s · 1 shell still running
```

**用户指出：两者都是完成态。** 且前导为同类星号字形。
即：**同一类字形既出现在完成态、也出现在其他态，字符串匹配从原理上就分辨不了。**

## leader 的错误必须记下来

D-26 中 leader 让席位把 `✳`、`◐◑◒◓◔◕` 补进 `spinnerFrames`「工作中」白名单。
**方向错误。** 上线后所有跑完的会话都会因 `✳ Brewed for` 被判「工作中」，
使「已停止工作却显示工作中」的误检**更严重**——而用户当前报告的正是这个方向的误检。

据此：
- 生产 daemon **暂不重编**（避免把该回归发出去）
- D-26 的 Layer ① 字形白名单**应当退场**，不是继续扩充
- D-26 的 Layer ② 活性判据（帧变化）方向正确但仍是**间接推测**；
  若 herdr 有结构性信号，应优先采用结构性信号

## 调研对象

- **herdrdev/herdr** —— "the runtime your coding agents live on"。
  它**托管** agent 进程，因此很可能以结构性信号判状态，而不是刮屏。
  重点查：它怎么知道一个 agent 是在跑、在等输入、还是已结束？
  数据来源是进程状态？PTY 读写活性？子进程树？CLI 自身的协议/钩子/退出码？还是别的？
- **dcolinmorgan/herdr-remote** —— 从手机/菜单栏/Telegram 驱动 agent，
  它必然也要向用户展示状态，看它拿的是什么信号
- 若 herdr 的机制依赖它自己托管进程（而我方是旁路镜像既有 tmux），
  **必须如实说明这个前提差异**，并回答：在「不托管、只旁观 tmux pane」的约束下，
  我方还能拿到哪些结构性信号

## 必须回答的问题

1. herdr 判定 agent 状态的**实际机制**：数据来源、信号、判据（附仓库/文件/函数）
2. 许可证，能否引用
3. **在不刮屏的前提下，我方 daemon 能获得哪些结构性信号？**
   - tmux 侧：pane 的前台进程、进程状态（R/S/D/Z）、子进程树、pane_current_command
   - PTY 侧：读写活性、输出速率
   - CLI 侧：Claude Code / Codex 是否提供状态钩子、退出码、或可查询的运行时接口
4. 替代方案与代价；D-26 现有 `rules.go` 字形白名单应如何退场

## 为什么标 contention: contract

状态检测是产品的核心能力之一（五态由服务端权威计算、客户端只渲染）。
换掉判定机制属于契约级改动，**定夺前相关模块不施工**。
本任务只产出方案，由 leader 与用户裁定后再开工。
