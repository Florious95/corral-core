# 任务书 · t.fanout · 一个 pane 的管道要能喂多个订阅者（修 Q5）

## 一、已坐实的缺陷（源码证据在 `.team/nodes/t.q8/答复.md` Q5，⛔ 不必重查，但要自己核一遍）

`server/internal/bridge/stream.go:14-16` 的包注释自己写着：

```
// One active pipe per pane (tmux's own limit): a new Subscribe replaces any
// previous pipe, whose relay then sees EOF and closes its channel.
```

三条实锤：

1. **单槽**：`stream.go:132-144` 新订阅者**先无参 `pipe-pane` 拆掉别人的**，再挂自己的 FIFO。
2. **零通知**：被顶掉的那个只看到 FIFO EOF；`ws_conn.go:534-555` 的 relay 退出只
   `teardownSubscription`，**不 `sendError`** ⇒ 客户端连接还在、自以为还订着，**画面冻在最后一帧**。
3. **拆除误伤**：第一个 relay 退出时又对**整个 pane** 发一次无参 `pipe-pane`，
   **可能把第二个订阅者刚挂上的管道也拆掉** —— 两败俱伤。

**影响面**：任何「多于一个订阅者盯同一 pane」的场景。这是本产品的**常规场景**，不是边角：
用户手机 + web 端（测试第一道）+ 桌面端消费方，会同时存在。
2026-08-23 用户手机在订、本机 Safari 与 Chrome 也在订同一 daemon，正好踩这条路径。

## 二、要做什么

### 第 1 步：复现先红（⛔ 复现不出不许动代码）

写一个**能红**的测试：同一 pane 上先后接入两个订阅者，断言

- **A**：第二个接入后，第一个**仍能收到 DELTA**（现在会失败）
- **B**：第一个断开后，第二个**仍能收到 DELTA**（现在可能被误拆）
- **C**：若某个订阅者确实被强制下线，它**收得到一个明确的控制帧/错误**，⛔ 不是静默 EOF

**三条断言现在应当至少红两条。** 把红的原文贴进说明。

### 第 2 步：修 —— 一条管道，扇出给 N 个订阅者

**目标**：pane 级只挂 **一条** `pipe-pane`，由 daemon 内部把字节流**扇出**给该 pane 的所有订阅者；
订阅者进出只改引用计数，**⛔ 不再互相拆管道**。

必须满足：

- **引用计数归零才真正拆管道**；⛔ 不许任何订阅者对整个 pane 无条件 `pipe-pane` 拆除。
- **拆除必须校验所有权**：只拆自己挂的那一条（比对 FIFO 路径 / 挂载标识），
  ⛔ 不许「反正拆一下没坏处」——这正是当前误伤的来源。
- **迟到的订阅者要拿到快照**：新订阅者接入一条已存在的管道时，仍要收到属于自己的首帧快照。
- **一个订阅者慢/卡住不许拖垮别人**：每个订阅者独立队列，慢的按既有 sendq 策略丢/断，
  ⛔ 不许阻塞扇出源。
- **若仍存在「必须踢掉某人」的路径**（比如 pane 消失），被踢者**必须收到明确帧**，⛔ 不许静默。

⛔ **不许把 `list-interval` / 超时之类的旋钮调一调就算修**。
⛔ **不许改客户端渲染来绕**——下游正是这么翻的车。

### 第 3 步：三条断言全绿 + 不退
