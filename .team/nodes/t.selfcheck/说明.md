## E1：`resize-window` 同不同步 reflow

命令与产品同款：`set-option -w window-size latest` + `resize-window -x/-y`，然后 `capture-pane -e -p`（`ws_handler.go:505-507` 注释所依赖的那次截取）。

每档 n=20。比较同一轮 resize 返回后 delay=D 的捕获 **与 delay=500ms 逐字节**。种子含框线 + 中文 + 200 个 `A`（让 wrap 可见）。tmux 3.6a。**load1=5.72**（开始时 `uptime`；结束后 5.59）。

表（`mismatch_rate` 为 0–1 的比例）——完整 JSON：`.team/perf/reflow-sync-20260823T051933Z.json`

| delay ms | 变窄 220→80 | 变宽 80→220 |
|---:|---:|---:|
| 0 | 0/20 = **0.0** | 0/20 = **0.0** |
| 20 | 0.0 | 0.0 |
| 50 | 0.0 | 0.0 |
| 100 | 0.0 | 0.0 |
| 200 | 0.0 | 0.0 |
| 500 | 0.0（同帧对照） | 0.0 |

**结论：注释里的断言成立。** delay=0 与 500ms 稳定态不一致率 ≈ 0。在 tmux 3.6a 上，`resize-window` **返回之后**再 `capture-pane`，再等最多 500ms **不会**再变字节。我方 subscribe/resize 路径「Resize 返回立刻 capture」对「截到的是已经稳定的格子」这一层有实测背书。

**不一致的样子**：没有。零 mismatch，无样本。

**不是这句注释、但测到的附带事实**（一枪，不进表）：resize **之前** 220 列顶行是 `┌─ E1E2MARK`，resize 到 80 列之后顶行变成 80 个 `A`（200 列 `A` wrap 把框线顶下去/滚进历史）。那是 **tmux 自己 reflow 改布局**，不是「返回后还在变」。原注释没声称「顶行不变」。
