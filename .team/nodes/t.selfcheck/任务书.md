## 二、实验 E1：`tmux resize-window` 到底同不同步 reflow

**被验的断言**（我方自己写的注释，`server/internal/api/ws_handler.go:500-509` 原文）：

```
// tmux reflows the pane synchronously on resize-window, so capturing right
// after Resize is content-correct
```

**我方 ② 全部建立在这句上**：「几何在首帧之前落定 ⇒ 首帧本身就是对的」。
若它不成立，我方 ② 就只是「窗口比对方小」而不是「窗口不存在」——
**只是手机窄屏不容易撞见**，不代表没有。

### 怎么测

隔离 tmux（⛔ 不碰用户真实 tmux、⛔ 不碰生产 `:9900`）：

1. 起一个宽 pane（≥200 列），灌入**含框线与宽字符的内容**（例如 box-drawing `┌─┐│└┘` +
   中文），让 reflow 的后果肉眼/机械都可判。
2. `resize-window` 到目标宽度（例如 114、80），然后在 **delay = 0 / 20 / 50 / 100 / 200 / 500 ms**
   各 `capture-pane -e -p` 一次。
3. 每档重复 **≥20 次**，比较**每一档的捕获内容与 delay=500ms（视作稳定态）是否逐字节相同**。
4. 报每档的 **不一致率**。

**判据要的就是这张表。**
- 若 delay=0 的不一致率 ≈ 0 ⇒ 断言成立，我方 ② 有实测背书。
- 若明显 > 0 ⇒ **断言不成立，这是我方缺陷**（我们在一个未 reflow 完的时刻截了快照）。
  ⛔ 这时不许粉饰，照实报，并写清不一致的**样子**（是整屏下移？框线断裂？还是只差尾部空白）。

⚠️ 换宽度的方向可能有别（变宽 / 变窄），**两个方向都要测**。

## 三、实验 E2：我方自己在宽主机（235 列）上会不会错乱

**为什么必须测**：我方给下游的④说「结构上不会错」，但**我方从来没在 235 列的宿主上跑过**——
用户是手机、pane 窄。**「架构上不该错」⛔ 不等于「实测过不错」。**

### 怎么测（⛔ 优先用 JVM 单测，不要为这个开模拟器）

我方 ④ 的主张落在 `app/core-terminal/.../TerminalEmulator.kt:139` 的
`replaySnapshot(bytes, cols, rows)`。所以直接测它：

1. 在隔离 tmux 里起一个 **235 列**的 pane，灌入框线 + 宽字符 + 长行内容，
   `capture-pane -e -p` 取**真实字节**存成 fixture（⛔ 不许手工编造字节，要真的从 tmux 取）。
2. 把这份 fixture 喂给 `replaySnapshot(bytes, cols, rows)`，
   **cols 取几个档**：235（同宽）、114、80（窄于源）。
3. 断言：
   - **A**：同宽（235）重放后，网格内容与源 pane 的 `capture-pane` 结果一致
   - **B**：窄于源时**不出现整屏位移**（顶行仍是顶行）
   - **C**：框线字符不落在错误的列（至少：每行的首个 `│`/`┌`/`└` 的列位与预期一致）
4. **若某条断言红了 —— 那就是我方缺陷，与下游同源。** 照实报，⛔ 不许改断言迁就实现。

⚠️ **fixture 必须留在仓里**（`app/core-terminal/src/test/resources/` 或同族既有位置），
否则这个测试以后不可复跑。
