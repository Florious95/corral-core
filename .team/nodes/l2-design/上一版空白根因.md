# 上一版空白根因（82865233c / 53ac62866）

现象：用户真机二级菜单**全空**。服务端有 tmux 数据（一级列表能出来），装上的 App 二级是空 LazyColumn。

材料：`scratch/archive-level2-v1/` 全文 + 当前仓里未随 level2 回退的接线层（`ServiceWire` / `WorkspaceViewModel`）。没有真机诊断日志，下面把「查到哪儿为止」和「从哪一步起是推测」分开写。

## 结论（查到为止，不靠猜）

不是「服务端没扫到 pane」，也不是「App 把 sessions 解成了 `[]`」。

是两条**各自就足够让二级永远空**的实现错误叠在一起：

1. **帧 type 对不上**（服务端推的帧 App 解不出来）
2. **即便解开，生产路径也不会送到二级 VM**（测试用 `setListener` 把这条路盖绿了）

订阅在**服务端**是建立得起来的。App 发的 `level2_subscribe` 与 Go 的 `TypeLevel2Subscribe = "level2_subscribe"` 一致。上一版死在「推回来的那一帧」和「谁来收」。

---

## RC1 — 帧判别符不一致（「帧字段对不上」）

| 端 | 文件（归档 after/） | wire `type` |
| --- | --- | --- |
| 服务端推送 | `server/internal/protocol/frametype.go` | `"level2_frame"` |
| App 解码 | `app/.../conn/Frame.kt` `FrameType.LEVEL2` | `"level2"` |
| 订阅（双向） | 两边 | `"level2_subscribe"` 一致 |

服务端 `c.send(protocol.Level2Frame{...})` → Marshal 打上 `type=level2_frame`。

App `FramePayload.decode` 的 `when (type)` 只认 `"level2"`。未知 type → `UNSUPPORTED_TYPE` → `onLocalDecodeError`。

`WorkspaceViewModel.onLocalDecodeError` **是空实现**（当前仓 `WorkspaceViewModel.kt:164`，回退没动过）。用户看不到错误，只看到空列表。

单测全绿的原因：`Level2StreamLifecycleTest.receivingLevel2FrameReplacesEntriesVerbatim` **不走 wire**，直接 `h.vm.onFrame(h.level2Frame(...))` 构造 Kotlin 对象。打包判据是「dex 里有 level2 符号」。符号在，帧过不去。

**判据**：打开归档 `after/server/internal/protocol/frametype.go:89` 与 `after/app/.../Frame.kt:55` 对读即可。不需要真机日志。

---

## RC2 — 生产接线没挂上二级 VM（「App 侧没解到 / 没送到」）

`ConnectionManager` 只有**一个** `listener`（`setListener`）。生产里这个槽被 `ServiceWire` 的包装监听占住，再扇出到 `ServiceWire.uiConnector`。

工作区屏把 `uiConnector` 设成 `workspaceViewModel`（`AgentMirrorApp.kt`）。`WorkspaceViewModel.onFrame` **只吃** `listing` / `list_delta`，其余 `else -> Unit`（当前仓 `:152-157`）。

上一版 `Level2ViewModel`：

- 实现了 `ConnectionManager.Listener`
- `init` 只调用 `manager.subscribeLevel2`
- **从不**把自己交给 `uiConnector`
- `WorkspaceScreen` 只 `remember { Level2ViewModel(...) }`，不接线

所以即使用户把 RC1 的 type 改对齐，`onFrame` 仍进 `WorkspaceViewModel`，被当无关帧丢掉，`Level2ViewModel.sessions` 一直是 `emptyList()`，`Level2LiveStreamScreen` 画空表。

单测 `Level2StreamLifecycleTest.Harness` 写了 `manager.setListener(vm)`——这是测试自建 manager 上的绿，**和生产 `ServiceWire` 单槽扇出不是同一条路**。`SessionViewModel` 的 KDoc 已经写明：生产禁止自行 `setListener`，会顶掉服务层包装。上一版二级抄了 Listener 接口，没抄接线纪律。

**判据**：归档 `WorkspaceScreen.kt:138-148` 无 `uiConnector` / 无把帧喂给 `l2Vm`；`Level2ViewModel.kt` 无 `setListener`；对照当前 `ServiceWire.kt` + `WorkspaceViewModel.onFrame`。不需要真机日志。

---

## 三条假设怎么落

| 假设 | 判定 |
| --- | --- |
| 订阅没建立 | **服务端侧否**。`level2_subscribe` 两边一致，`handleLevel2Subscribe` → `markLevel2` → `publishLevel2` 会扫 tmux。 |
| 帧字段对不上 | **是。RC1。** type 字符串就对不上，后面字段谈不上。 |
| App 侧解出来是空 | **不是「解出空数组」**。RC1 下根本解不成 `Level2Frame`；RC2 下解成了也到不了二级 VM。`sessions` 保持构造时的 `emptyList()`，不是服务端推了空 `sessions` 被如实画出来。 |

---

## 判断边界

**查到为止（归档 + 现接线，可复现）：**

- RC1、RC2 各自足以造成「全空 LazyColumn」。
- 上一版单测 / dex 符号判据故意走不通这两条。
- 服务端在已订阅时会 `Discover` 并按 `byCWD[workspace]` 组装 `Level2Frame`（`level2.go`）。

**没有真机导出日志，因此不声称：**

- 用户那一次打开时 RC1 和 RC2 谁先爆（RC1 在解码，更早）。
- 当时 `subscribeLevel2` 是否撞上 `!conn.isReady` 的静默 true（`ConnectionManager.kt:366` 未就绪直接 `return true` 且**不重放**）。这是第三条**可能**的空，但不是解释「服务端有数据」所必需的；标为推测，重做时仍要修（READY 后重放订阅）。
- `byCWD[ws]` 精确匹配失败导致服务端推了空 `sessions`。若 RC1/RC2 已挡死，这条到不了 UI。重做时仍要求：二级行的 workspace 键必须与一级 listing 的 `cwd` 逐字节相同；对不上就打日志（两边 cwd 原文），不要静默空表。

**不是根因的：**

- 回退后二级为空——那是拔干净的预期。
- `connected_idle_economy_test.go` 注释里的 `archive-level2` 字面量——与运行时无关。
