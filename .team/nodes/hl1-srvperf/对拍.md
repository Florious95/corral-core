# t.srvperf 服务端卡顿对拍

measurement-only，未改产品代码、未建分支。

## 方法

- base：`git archive dc9aab11b server` → `go build ./cmd/agentmirrord`（三条 server land 之前）。
- new：worktree `server/` 与 main `9f28b860b` 的 server 树 diff 为 0，`go build` 当前 server（最后一笔 `2a1a562c8` gofix-scrubbedenv）。
- 负载：隔离 tmux 会话里 `exec -a grok /usr/bin/yes` 加绿色前缀（`yes` 高频 + 彩色；`exec -a grok` 只为过 068 provider 白名单，否则 listing 为 0）。
- 客户端：tmp 内 WS 脚本 auth→list→subscribe，记录二进制帧到达时刻；并行 `ps -o pcpu= -p $DAEMON_PID` 每秒 60 次。
- 隔离：`env -i` 起 daemon；`AGENTMIRROR_E2E_DISCOVERY_SOCKET_DIRS` 收窄到自有 socket 目录；token 只走环境变量；未设 `TS_AUTHKEY`。
- tmux socket：worktree 路径实测 `File name too long`，socket 树只放 `/tmp/e2e-hl1srvperf`（chmod 700，`tmux -L hl1sp`，自检 `list-sessions=srvperf`）。跑完 `kill-server` + `rm -rf`。其余产物在 `.team/nodes/hl1-srvperf/tmp/`。
- 真 tmux 二进制：`/opt/homebrew/bin/tmux`（避开 PATH 上的 ta-tmux-shim）。

## 隔离核验

- 自有 daemon pid：38974 / 52716 / 67071 / 80511。只对这些 pid `kill`，未对 9900 发信号。
- 对拍期间 9900 监听 pid 从 99365 变成 68388（发生在 new-r1 与 base-r2 之间）。后一个 comm=`./agentmirrord-rollback-dc9aab11b`，是外部把生产 daemon 换成 base 构建，不是本席杀的。本席端口从未等于 9900。
- 默认 socket 上没有创建 `srvperf` 会话（对拍前 `has-session -t srvperf` 为否）。

## 为何不是「new 更差」

同一轮内 A/B 几乎贴着走（r1 双方都慢、r2 双方都快），跟踪的是本机 load（对拍时 1m load 9–16，用户指出的模拟器+构建混杂量）。new 没有稳定的 fps↓ / p95↑ / CPU↑。用户感到的卡顿要在 app/渲染/生产机其它变量上找，不在这三条 server land 的吞吐回归。
