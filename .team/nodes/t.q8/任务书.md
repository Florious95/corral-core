## 二、铁律：每一条答案都要有源码出处

- **每条结论必须带 `文件:行号`**，并附**代码原文片段**。⛔ 不许凭印象、⛔ 不许「应该是」。
- **答不出的照实写「查不出」**，并写清你查了哪些文件、为什么定不下来。

  - **`源码确定`**：代码原文直接支持，带行号

  - **`查不出`**：连该看哪都定不下来

## 三、8 个问题（原文照抄，⛔ 不许改写他们的问题）

**Q1** `capture-pane -e -p` 的一行是否等于网格的一行？捕获行超过订阅申报的 `cols` 是常态还是异常？
若是常态，超出部分的语义是什么（续行 / 未换行的逻辑行 / 转义序列是否计入显示宽度）？
客户端该如何把捕获文本还原成与主机网格逐行对齐的画面？

**Q2** 快照在哪个几何下截取？`subscribe {ref,rows,cols}` 是否先 `Resize` 再 `capture`？
`Resize` 与 `capture` 之间是否可能夹着**应用尚未重绘**的窗口？首帧快照是否可能反映 resize **之前**的内容？
（他们实测：订阅 39×114，tmux 报 `#{pane_width}=114`（550/550 零例外），
但同一帧快照里仍出现**显示宽度 115** 的行。）

**Q3** 宽字符卡在最后一列时序列化怎么处理？（他们实测：114 列、前 113 格占满、
行尾还有一个显示宽 2 的汉字（U+6B65 / U+7684 / U+5F80 / U+5047）；
重放进自建 114 列 pane 时 tmux 会把该汉字折到下一行，但现场 `capture-pane -p` 把整颗码点留在同一行。）
这是 tmux 既有行为还是 daemon 侧拼接？客户端该按哪个为准？

**Q4** 退订后 `paneGeometry` 会把 pane 恢复到基线吗？订阅计数归零时是否 restore？
多客户端交替订阅同一 pane 时几何会不会来回抖？
（他们实测：巡检结束后所有 pane 躺在 235×50，巡检期间订阅时是 114，所有 window 都是 `window-size manual`。）

**Q5**（🔴 **最要紧，可能是我方缺陷**）`pipe-pane` 是单管道吗？
第二个订阅者接入会不会**抢走**第一个的管道，且老订阅者**零通知**被拆（客户端仍以为订着、画面冻结）？
若确实如此，**有没有给老订阅者的通知机制**？
「手机端没问题」是否正是「最后订阅者永远正常」的表现？

**Q6** 协议里有没有「请求重绘 / 重发快照」的动词？
（他们读到 v1 只有 `subscribe` / `resize` / `listing` + 二进制 SNAPSHOT/DELTA/SCROLLBACK，
且 `resize` 在几何未变时是 no-op、不补快照。）
客户端发现画面不对时，除了退订再订还有别的办法要一帧干净快照吗？
空闲 pane（应用不再输出）错乱后会不会永远停在坏帧？

**Q7** `listing` 在订阅后会滞后多久？是设计如此（独立扫描节奏）还是缺陷？
客户端要拿「此刻主机几何」该用哪个字段？
（他们实测：订阅 114 后 tmux 的 `#{pane_width}` 已是 114，但 `listing` 在其后 **800ms 内**仍报订阅前的宽度。）

**Q8** 首帧延迟的物理下限。（他们实测本机 loopback 550 样本：`subscribe` 发出 → 首个 snapshot 到达，
中位 **180.7ms**、均值 191.6ms、**最小 84.7ms**。）
这个量级符合我方预期吗？捕获 / 编码 / WS 各占多少？有没有已知可调项？
