# 答复稿 · 桌面端 8 问（daemon 侧，按源码）

下游：`tmux桌面端::corral-desktop`。本答复只陈述我方 daemon **此刻源码做什么**；不改协议、不改代码。

---

## Q1 capture-pane 一行是否等于网格一行？超出 cols 是常态还是异常？

**结论**：daemon **原样转发** `capture-pane -e -p` 的字节，不按订阅 `cols` 折行、不测显示宽度、不剥 CSI。一行是否等于主机网格一行、显示宽能否超过 `cols`，是 **tmux 的序列化行为**，我方源码没有第二种处理。

**置信度**：需实测

**证据**：

`server/internal/bridge/bridge.go:61-62` —— 快照就是这一条 tmux 命令，无 `-J`（join wrapped lines）：

```
func (p *Pane) Snapshot(ctx context.Context) ([]byte, error) {
	return runTmux(ctx, p.socket, p.timeout, "capture-pane", "-e", "-p", "-t", p.target)
}
```

`server/internal/api/ws_handler.go:40-50` —— 收到后只做两件事：去尾部 `\n`，再拼一条 CUP 把光标锚回去。**没有**按 `cols` 切行：

```
func snapshotWithCursor(ctx context.Context, br *bridge.Pane) ([]byte, error) {
	snap, err := br.Snapshot(ctx)
	...
	snap = bytes.TrimRight(snap, "\n")
	return append(snap, []byte(fmt.Sprintf("\x1b[%d;%dH", y+1, x+1))...), nil
}
```

`-e` 把 ANSI 留在流里。若客户端用「字节长度」或「把 CSI 算进宽度」去量一行，会量出 **> cols**，那是量法问题，不是 daemon 另写了一套行。无 `-J` 时 tmux 文档语义是按屏上网格出货而不是拼逻辑行；**是否仍会出现显示宽 115 / 几何 114**，源码看不到，要在隔离 pane 上对 `capture-pane -e -p` 做 wcwidth 才能定。

**对客户端的建议**：按终端仿真器重放这段带 CSI 的字节流（wcwidth + SGR），不要按「一行纯文本 = cols 个格子」对齐。订阅申报的 `cols` **不会**出现在快照编码里。不要在未验证 tmux 网格语义前改渲染。

## Q2 快照在哪个几何下截取？是否先 Resize 再 capture？会不会拍到应用未重绘的窗口？

**结论**：顺序是 **Resize → 挂 pipe → capture**。Resize 与 capture 之间 **没有**等待应用 SIGWINCH 重绘。因此首帧 **可以**含「几何已是新的、内容仍是旧排版」的窗口。Resize 的读回宽高被丢掉，不告诉客户端。

**置信度**：源码确定

**证据**：

`server/internal/api/ws_handler.go:153-168`：

```
	if _, _, err := br.Resize(c.ctx, int(s.Cols), int(s.Rows)); err != nil {
		c.logErr("subscribe resize", err)
	}
	ch, detach, err := br.Subscribe(c.ctx)
	...
	snap, err := snapshotWithCursor(c.ctx, br)
```

`server/internal/bridge/bridge.go:377-391`：Resize 是 `set-option window-size latest` + `resize-window` + 立刻 `Size()` 读回。没有 sleep、没有等 pane 输出：

```
	if _, err := runTmux(..., "resize-window", "-t", winID, "-x", strconv.Itoa(cols), "-y", strconv.Itoa(rows)); err != nil {
		return 0, 0, err
	}
	return p.Size(ctx)
```

同文件 `handleSubscribe` 把 Resize 的 `(width,height)` **丢弃**（`_, _, err`）。`handleResize` 注释写「tmux reflows the pane synchronously… capturing right after Resize is content-correct」（`server/internal/api/ws_handler.go:505-506`）——那是 **注释主张**，主张的是 tmux 自己重排格子，不是应用已画完。应用未重绘这条路径源码没有挡住。

他们「`#{pane_width}=114` 但快照里有显示宽 115 的行」：daemon 截取时不读、不裁 `cols`（见 Q1）。几何以 tmux `#{pane_width}` 为准；行显示宽是 capture 文本的解析结果，两边可以不一致。

**对客户端的建议**：不要用 listing 的旧 `cols` 去解释首帧。首帧按仿真器重放。若必须等应用重绘，协议里没有「等一帧」；只能再 `subscribe`（见 Q6）或接受首帧可能旧。

## Q3 宽字符卡在最后一列时，是 tmux 行为还是 daemon 拼接？

**结论**：daemon **不拼接、不折行、不改码点**。现场 `capture-pane -p` 把整颗汉字留在同一行，就是 tmux 交出来的字节；daemon 原样放进 SNAPSHOT。客户端应以 **快照字节** 为准，不能以「自己再开一个 114 列 pane 重放会折行」为准。

**置信度**：需实测

**证据**：快照路径只有 Q1 引用的 `Snapshot` + `TrimRight` + CUP，没有任何按列切 UTF-8 / wcwidth 的代码。`Scrollback` 同样是 `capture-pane -e -p -S -E`（`server/internal/bridge/bridge.go:98-101`），也无折行。

他们把同一串重放进自建 114 列 pane 时 tmux 把汉字折到下一行——那是 **另一次 tmux 输入路径**（写入格子），与 **capture 输出路径** 不是同一个变换。我方源码不能证明 tmux 这两种路径是否该一致；要在隔离 pane 上对同一帧做 `capture-pane -e -p` vs `send-keys` 重放对照才能定。

**对客户端的建议**：重放 SNAPSHOT 时用终端状态机，不要假设「显示宽 2 的码点在最后一列一定折行」。不要为了迁就自建 pane 的折行去改所有会话的渲染。

## Q4 退订后 paneGeometry 会不会 restore？多客户端会不会把几何抖来抖去？

**结论**：会。基线是 **pane 级单例**：第一个订阅者记下当时的 `Size()`，最后一个 `release` 到 0 时 `Resize` 回基线。中间订阅者只加计数、不改基线，但 **每个 subscribe/resize 仍会把 pane 拉到该客户端的 rows/cols**（后操作者赢），所以多客户端交替时几何会抖。`window-size` 每次 Resize 都写成 `latest`，退订时 **不恢复成原来的 window-size 模式**。

**置信度**：源码确定

**证据**：

`server/internal/api/pane_geometry.go:51-71` 首个订阅者记基线：

```
	if g.active == 0 && !g.origKnown {
		c, r, err := br.Size(ctx)
		...
		g.origCols, g.origRows = c, r
		g.origKnown = true
	}
	g.active++
```

`server/internal/api/pane_geometry.go:74-101` 计数归零才 restore：

```
	g.active--
	if g.active == 0 {
		...
		if known {
			if _, _, err := br.Resize(context.Background(), cols, rows); err != nil {
```

`server/internal/api/ws_handler.go:144-156`：每个订阅者（含第二人）都 `Resize` 到自己的申报尺寸。

`server/internal/bridge/bridge.go:384`：每次 Resize（含恢复）都 `set-option ... window-size latest`。

他们「巡检后所有 pane 躺在 235×50」：若第一个订阅者记基线时主机已经是 235×50，恢复到 235×50 **符合这段代码**。不能从源码推出「本应恢复成别的数却没恢复」。`window-size manual` 不是这段恢复写回去的——我们只写 `latest`。

**对客户端的建议**：不要多客户端同时订同一 pane 还指望几何稳定。巡检用完要 `unsubscribe`（或关连接），让计数归零触发恢复。不要用 listing 的瞬时 cols 当「主机永恒几何」。

## Q5 pipe-pane 是单管道吗？第二人会不会抢走第一人的管道且零通知？

**结论**：是单管道。第二人 `Subscribe` **会拆掉**第一人的 pipe；第一人的 relay 只看到 FIFO EOF，**没有** error / unsubscribe / 任何控制帧。服务端还把该连接上的订阅拆掉（之后 input 会 `not_subscribed`），但客户端若只看「连接还在、以为还订着」，画面就冻在最后一帧。「最后订阅者正常」与「手机看起来没问题」相符。更糟：第一人 relay 退出时会再执行一次 **pane 级** `pipe-pane` 拆除，可能把第二人刚挂上的管道也拆掉。

**置信度**：源码确定

**证据**：

`server/internal/bridge/stream.go:14-16` 包注释写明上限与替换语义：

```
// One active pipe per pane (tmux's own limit): a new Subscribe replaces any
// previous pipe, whose relay then sees EOF and closes its channel. The API
// layer is expected to hold one subscription per pane at a time.
```

`server/internal/bridge/stream.go:132-144`：新订阅 **先无参 `pipe-pane` 拆除已有管道**，再 `-o` 挂自己的 FIFO：

```
	_, _ = runTmux(context.Background(), socket, timeout, "pipe-pane", "-t", target)
	cmd, stderr, derivedCtx, cancel := newTmuxCommand(ctx, socket, timeout, "pipe-pane", "-o", "-t", target, "cat >> "+shellQuote(fifo))
```

`server/internal/api/ws_conn.go:534-555`：管道 EOF 只 `teardownSubscription`，**不** `sendError`：

```
func (c *wsConn) relay(...) {
	defer func() {
		teardownSubscription(sub)
		...
	}()
	for {
		select {
		case chunk, ok := <-ch:
			if !ok {
				return
			}
```

`server/internal/api/ws_conn.go:501-516`：teardown 里的 `detach()` 又是一次无参 `pipe-pane`（`server/internal/bridge/stream.go:189-195`），目标是 **整个 pane**，不是「只拆自己的 FIFO」。

协议帧类型全集见 `server/internal/protocol/frametype.go:9-105`：没有「你的镜像被抢了」这类 S→C 通知。`pane_mode_changed` 只用于 copy-mode。

`handleSubscribe` 的 `subscribeCancel`（`server/internal/api/ws_handler.go:142`）只拆 **本连接** 上同一 ref 的旧订阅，不通知 **其他连接**。

**对客户端的建议**：在我方修之前，同一 pane **不要**让手机 + Safari + Chrome 同时 `subscribe`。发现画面冻结：退订再订（会变成「最后订阅者」）。不要把冻结当成渲染 bug 去改网格。

## Q6 有没有「请求重绘 / 重发快照」的动词？空闲错乱会不会永远停在坏帧？

**结论**：没有独立的「请再给我一帧快照」动词。能重新拿到 SNAPSHOT 的只有：① 再发 `subscribe`（同连接会拆旧订阅再拍）；② `resize` 且 **实际几何变了**。`resize` 几何未变是 no-op、不补快照。空闲 pane 不再出 pipe 字节的话，坏帧会一直留着。

**置信度**：源码确定

**证据**：

`server/internal/protocol/frametype.go:9-105` 控制帧闭集：`auth` / `list` / `subscribe` / `unsubscribe` / `input` / `scrollback` / `resize` / `scroll_wheel` / `attach_preview` / `level2_*` / `overlay_*`。没有 refresh / resnapshot / redraw。

`server/internal/api/ws_handler.go:448-498`：resize 比较 resize **前后真实** `Size()`，相同则 return，不推快照：

```
	if beforeW >= 0 && beforeW == afterW && beforeH == afterH {
		c.s.log.Debug("ws: resize no-op, skip snapshot", ...)
		return
	}
```

`server/internal/api/ws_handler.go:120-124`：再 `subscribe` 会拆旧订阅并「fresh snapshot is replayed」。

`server/internal/bridge/stream.go:167-170`：pipe 只在有新输出时推 DELTA；空闲无输出。

**对客户端的建议**：画面不对时发一次 **同 ref 的 subscribe**（不要指望同尺寸 resize）。这会打断该连接上的旧 pipe 并再拍一帧——也会踩 Q5，抢掉别人的管道。

## Q7 listing 在订阅后会滞后多久？此刻主机几何该看哪个字段？

**结论**：滞后是 **设计如此**：listing 循环默认 **2s** 扫一次；`subscribe` 只调用 `ensureInitialScan`（已有快照则 **no-op**），**不会**为这次 Resize 立刻刷新 listing。800ms 内仍报订阅前宽度，落在一个 2s 周期里，与源码一致。`listing` / `list_delta` 里的 `cols`/`rows` 来自上一次 discovery 的 `#{pane_width}x#{pane_height}`，不是订阅读回值。协议没有「查询当前 pane 几何」的专用帧。

**置信度**：源码确定

**证据**：

`server/internal/api/options.go:22-24`：

```
	defaultListInterval = 2 * time.Second
```

`server/internal/api/server.go:312-335`：有已认证客户端时 `time.After(s.listInterval)` 才 `publishListing`。

`server/internal/api/server.go:414-422`：`ensureInitialScan` 有快照就 return。

`server/internal/api/ws_handler.go:132-135`：subscribe 只 `ensureInitialScan`，不 `refreshListing`。对比 `handleList`（`server/internal/api/ws_handler.go:72-79`）会真正 `refreshListing`。

`server/internal/discovery/scan.go:28` 与 `server/internal/api/listing.go:28-34`：

```
const paneFormat = "...|#{pane_width}x#{pane_height}|..."
...
		Rows: uint16(e.pane.Height),
		Cols: uint16(e.pane.Width),
```

**对客户端的建议**：订阅后的几何以 **自己申报的 rows/cols**（以及后续成功的 resize）为准，不要用 800ms 内的 listing 去否定 tmux `#{pane_width}`。若要一张较新的列表，发 `list`（会立刻 rescan），仍可能和「刚 resize 完」有竞态。没有第三种字段。

## Q8 首帧延迟物理下限（loopback 中位 180.7ms、最小 84.7ms）是否符合预期？

**结论**：量级 **说得通**：subscribe 处理是一串同步 `tmux` fork（Resize 至少 3 次、pipe 拆+挂、FIFO open、`capture-pane`、`cursor`、编码、WS 写）。我方 **没有**把捕获 / 编码 / WS 拆开的计时，不能把 180ms 切成三段。`perf_subscribe` 的 `recv_ms/start_ms/done_ms/queue_ms` 量的是 **进程内** 读帧→dispatch→handle 返回，不是捕获各段。没有「跳过 Resize」之类可调项来压这条路径。

**置信度**：需实测

**证据**：

`server/internal/api/ws_conn.go:383-386` + `422-433`：三时间戳在 handle 返回时打一条 `perf_subscribe`，不含 capture 分段：

```
		c.handleSubscribe(t)
		c.logPerfSubscribe(t.Ref, recvMS, startMS, perfNowMS())
...
	log.Info("perf_subscribe",
		"recv_ms", recvMS, "start_ms", startMS, "done_ms", doneMS,
		"queue_ms", startMS-recvMS, "ref", ref)
```

`docs/基线-20260822-release.md:33` 只记录有这四个字段，没有预算表。

同步 tmux 次数下界（同一次 `handleSubscribe`）：Resize 的 set-option + resize-window + Size（`server/internal/bridge/bridge.go:384-391`）、Subscribe 的拆除 + 挂 pipe（`server/internal/bridge/stream.go:140-144`）、Snapshot + CursorPos（`server/internal/api/ws_handler.go:40-45`）。每条都是一次进程外 `tmux`。loopback 最小 84.7ms、中位 180ms 与「6+ 次 exec」不矛盾，但 **不是**我方事先写下的 SLA。

可调：`AGENTMIRROR_LIST_INTERVAL` 只影响 listing（Q7），**不影响** subscribe 首帧。`fifoOpenTimeout`（`server/internal/bridge/stream.go:39`）是 3s 上限，健康路径应是毫秒级会合，不是 180ms 的主因。

**对客户端的建议**：loopback ~180ms 不要当故障。要拆捕获/编码/WS，得在我方加分段埋点或他们在 subscribe 两侧打点对照 `perf_subscribe.done_ms-recv_ms`。没有客户端侧旋钮能跳过 Resize。

## 这 8 条里哪几条暴露了我方缺陷

按严重度：

### 1. Q5（必须单列）—— `pipe-pane` 单槽 + 零通知 + 拆除会误伤

**现象**：同一 pane 第二个 `subscribe` 会拆掉第一个的管道；老客户端收不到任何帧，画面冻结；服务端只在 EOF 后默默 `teardownSubscription`。老客户端的 `detach` 再对 **整个 pane** 发一次无参 `pipe-pane`，可能把新订阅者的管道也拆掉。

**影响面**：所有「多于一个订阅者盯同一 pane」的部署。2026-08-23 用户手机在订、本机 Safari 与 Chrome 也在订同一 daemon——**正好踩这条路径**。它 **可以**解释「某一端画面停住 / 白屏后不再更新」（管道被抢或被误拆之后再也没有 DELTA）。它 **不能单独证明** 当天「打开会话白屏很久」的全部机制（当天另有死 socket 烧 CPU 的已证实路径）。两条可以叠：扫描把 CPU 打满 + 多订阅者抢 pipe。要钉死白屏是不是 Q5，需要当时的订阅时序（谁后订）和手机是否还在收 DELTA，本格没有那些日志。

**不是客户端渲染问题。** 下游因未验证前提改渲染把所有会话搞乱，已经回退——Q5 更不能用改网格来修。

### 2. Q2 / Q6 —— 没有「应用已重绘」的会合，也没有轻量重拍

先 Resize 再立刻 capture；坏帧之后除了再 `subscribe` 或真的改几何，没有第三种要干净快照的办法。空闲 pane 会停在坏帧。这是协议/实现缺口，严重度低于 Q5（单客户端也能碰到，但是否就是「错乱」要他们用仿真器重放才能分清是坏帧还是解析错）。

### 3. Q7 —— listing 几何滞后不是缺陷

2s 独立扫描 + subscribe 不刷新 listing，是写明的节奏。800ms 仍报旧宽是预期，不是 bug。客户端不该用 listing 当「此刻主机几何」的权威。

### 4. Q4 —— 多客户端几何抖动是需求 005「最后操作者赢」，restore 在计数归零时会发生

巡检后回到 235×50，更像「基线就是 235×50」而不是没 restore。`window-size` 一直被写成 `latest`、从不写回 `manual`：若他们依赖 `manual`，这是行为差，源码确定我们没做模式恢复。

Q1 / Q3 主要是 tmux 序列化与客户端如何仿真，**不是** daemon 另写了一套行缓冲。Q8 180ms 没有源码级反例。
