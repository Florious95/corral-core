# 现场基 · fix-agentstate-detection-d26

## 用户截图实证（2026-08-12）

用户给出当前 tmux 窗口列表截图，Claude Code 最新版的窗口标题形如：

```
+ 1: w-base-v2-.    ✳ w-base-v2
+ 2: w-dev-cols*:   "◐w-dev-cols"
+ 3: w-dev-repaint: "◐w-dev-repaint"
```

用户原话：

> 「最新版本 Claude Code，它的工作状态已经改成这样。
>  然后此前这个工程它检测工作中状态还是**点的转圈或点的左右移动**。」

即：**上游把「工作中」指示符换成了 `◐` 这类半填充圆动画，我方检测仍在匹配旧字形。**
这是 D-26「状态检测准确率低」的直接原因，用户已就此报过三次失败。

## ⚠️ 只补新字形是治标，本任务要求两层都做

**按具体字形匹配，上游每改一次就失灵一次，而上游不会通知我们。**
这次是 Claude Code，下次可能是 Codex 或任何一个 Agent CLI。
本工程的定位是「手机远程操控主机 tmux 中**大量** Agent CLI」——
字形白名单注定追不上。

### ① 立即修（恢复准确度）
补齐当前已知 CLI 的工作指示字形，包括但不限于 `◐◑◒◓` 这类半填充圆序列、
`✳` 类符号、既有的转圈与左右移动点。**先让用户马上可用。**

### ② 治本（字形无关判据）
改成不依赖具体字形的活性信号，例如：
- 同一 pane 区域在短时间窗口内**高频变化** ⇒ working
- 连续多次采样内容完全一致 ⇒ idle
- 与既有的 blocked / done / unknown 判据如何共存，由你设计

**验收里有一条专门防退化**：用**一组从未见过的指示字形**测试，仍须判出 working。
只有过了这条，才算真的不再依赖白名单。

## 相关代码位置（起点，闭包见架构基）

- `server/internal/agentstate/adapters.go`、`sample.go`
- 状态五态（working / idle / blocked / done / unknown）由服务端权威计算，
  客户端只渲染不重算（需求 012）

## 不得破坏

- 状态层与镜像层解耦：状态只出现在控制帧，二进制通道只有原始终端字节
- 既有 agentstate 测试全绿
- 不动 `server/internal/api/`（D-36 席位正在改 ws_handler.go 与 bridge.go，避免冲突）
