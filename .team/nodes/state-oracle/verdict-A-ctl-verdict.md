## 三条裁定依据

### 1. 变异点是否精确命中判据声称要保护的语义？

**是，精确命中，且红得不廉价。**

变异点 = `track.go:44-47` 的导数分支（`if cur != old { return Working }`），变的是把 working→idle，
即删掉「内容在动 = working」的差分判定。这正是判据 P1/P2（标题/底部两帧在动 → working）的**实现载体**——
判据 P1/P2 断言的就是这条分支的语义。变异后 R1/R2 立即红。

红得廉价的反例是：删掉整个包、改函数签名、制造 panic——那种红是「破坏」不是「抓倒退」。
这里变异是**单 token 替换、能编译、能跑**，且只有依赖导数判据的 R1/R2 红。判据精确抓到了
「导数被删」这个倒退，打在判据声称要保护的核心语义上，不是打在无关路径上碰巧变红。

### 2. G1/G2 在变异下保持绿——是否排除了「一棍子打红」？

**是，充分排除，且绿有信息量。**

先承认一个细节：G1/G2 走的是**存在性判据**（esc to interrupt 工作条有无、完成态无工作信号），
与被变异的导数分支（`track.go:44` 的 `cur != old`）**不是同一条路径**——所以 G1/G2 绿的一部分
来自「本来就不碰那条路径」。

但排除「一棍子打红」的证据恰恰在这：如果判据是「对实现无条件不信任 / 任何变化都红」，
变异后应该是 **4/4 全红**。实际是 **2/4 红、2/4 绿**，且红的恰是依赖被删路径的 R1/R2、
绿的是不依赖的守卫 G1/G2。这证明判据是**对「特定倒退」响应**，不是对「任何变化」响应——它有分辨力。

换句话说：G1/G2 在变异后仍绿，证明了判据能把「该红的」（导数被删）与「不该红的」
（存在性信号 intact 的真实 working / 完成态）区分开。这不是一棍子打红。

补充说明（对完整性的已知留白，不构成 refutes）：报告做了**单点变异**（删导数），未做对称变异
（删存在性判据 → 验证 G1 红、R1/R2 绿）。方法论 §1 的判据自检要求是「把产物改坏一处，判据必须
转非 0」——单点变异是判据有效的最低可接受证明，报告选择了最核心的导数判据。对称变异是更充分的
证据但非必要；当前证据已证实判据能区分绿/红、能精确抓核心倒退、守卫不受牵连。

### 3. 三阶段哈希对照是否足以证明现场干净？

**是，足以证明。**

- live `track.go`：基线 = 恢复 = `2b768a64…`，变异 = `139110b75…`。哈希差异证明变异是真实注入、
  哈希一致证明变异被精确还原。我自己复现后还原，哈希精确回到基线。
- scratch 化石 `track.go`：全程 = `34b72e35…`。证明判据模块载体（归档旧实现）在三次运行间
  未被 live 重建代码污染——`run-probe.sh` 装 live 源码、跑完还原化石的机制工作正常，
  红测载体没有被悄悄替换成「能绿的代码」。
- 哈希只覆盖 track.go 一个文件，但变异只动这一个文件，覆盖足够；判据模块用 track.go 代表化石
  是合理抽样（它是被变异文件，它干净 = 现场干净）。

三阶段（基线绿 → 变异红 → 恢复绿）加上哈希对照，构成可审计的闭环，足以证明：
**判据对 live 代码的绿/红区分是真的，不是靠污染判据载体造出来的。**
