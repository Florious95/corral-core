# 终端绘制性能思路（S1 重排 / S2 掉帧 / S3 白闪）

本格未读取 Heeler 任何源码文件；信息来源见每条结论的链接。

本格只出思路，不改 `app/` 产品代码。借鉴的是公开行为与上游引擎文档里的**做法分类**（GPU 管线、独立渲染线程、字形缓存、格对齐几何），不是任何第三方的表达。Heeler 仓库许可是 AGPL-3.0（[仓库页](https://github.com/ZingerLittleBee/Heeler)），我们是 Apache-2.0；契约 085 §0 已裁定一行都不许抄。

## 1. 上游终端引擎的公开设计（不是「某 iOS 应用的代码」）

公开资料能钉死的事实只有两层：

- **Heeler 产品形态**：iOS 上 SSH + 真终端。官网与 README 写明交互终端走 **libghostty**，输出是 **Metal**；滚动是「原生 scrollback + 惯性触控滚动，全屏 TUI 跟手」。来源：[Heeler 官网](https://heeler.bybee.dev)、[Heeler README](https://github.com/ZingerLittleBee/Heeler)、[ADR 0004](https://github.com/ZingerLittleBee/Heeler/blob/main/docs/adr/0004-libghostty-terminal.md)。
- **libghostty / Ghostty 自己的渲染设计**（MIT，可放心读）：终端仿真 + 字体 + GPU 绘制是库的核心职责。来源：[About Ghostty](https://ghostty.org/docs/about)、[Ghostty 仓库说明](https://github.com/ghostty-org/ghostty)、[libghostty 路线](https://mitchellh.com/writing/libghostty-is-coming)、[libghostty-spm 说明](https://github.com/Lakr233/libghostty-spm)、[Ghostty 1.2.0 发行说明](https://ghostty.org/docs/install/release-notes/1-2-0)。

### 1.1 渲染管线是什么形态

| 问题 | 公开资料能确定的 | 查不清 |
|---|---|---|
| GPU 着色器？ | 是。Linux OpenGL / macOS Metal；1.2 起两套后端共用核心逻辑，并支持可热重载的 custom shader（片元着色器画在已绘终端上）。嵌入用的 libghostty-spm **保留 Metal 渲染器**，但裁掉 custom shader（`glslang`/`spirv-cross`）。 | Android GLES 嵌入形态：公开路线写「长期会提供 GPU rendering（交给一块 OpenGL/Metal surface）」，**没有**已发布的 Android 稳定 GPU 嵌入包。 |
| 纹理图集 glyph atlas？ | 是。1.2.0 changelog 明确写 font atlas 错误路径、cached glyph lookup、glyph hashing for caching。字体先栅格进图集，再按格取样。 | 图集是 SDF 还是位图、几张、如何换出：公开文档没写。 |
| 脏矩形？ | 未在 About / README / 1.2 发行说明里写成产品保证。有独立 **render thread**，以及「第一帧」被单独修过（undefined memory access on first frame render）。 | 滚动时是否只标脏行、是否用上一帧纹理位移：**查不清**。不得从「他们快」反推必有脏矩形。 |
| 框线/块元素 | 1.2 起大量符号改由引擎**按格画几何**，保证格边像素对齐、无缝。这与我们 083 已落地的 `BoxBlockGeometry` 是同一类做法（独立设计，不是抄）。 | — |

独立渲染线程 + GPU 后端 + 字形图集，是 Ghostty 自己写在仓库 README / 发行说明里的架构，不是猜测。

### 1.2 滚动怎么处理

Heeler 公开描述把滚动分成两条（ADR 0004）：

- **普通 buffer**：交给引擎的 scrollback action（「native scrollback」）。
- **备用屏 TUI**：手势转成发给 PTY 的滚轮序列，让远端程序自己重画。

官网补充：惯性触控滚动要能驱动全屏 TUI（[heeler.bybee.dev](https://heeler.bybee.dev)）。

引擎侧能确定的是：scrollback 存在引擎里，绘制在 GPU 上，有单独 render thread。  
**整屏 CPU 重绘 vs 位移已有纹理**：公开文档没有一句话钉死。本节标 **查不清**，不拿它当对照前提。

### 1.3 首帧 / resize

能确定的：

- 嵌入 API 有 `resize` 回调，宿主必须把远端 PTY 与格子同步（[libghostty-spm README](https://github.com/Lakr233/libghostty-spm)）。
- Heeler ADR 0004：字号变化走 `TerminalController` 配置，**Ghostty 的 cell-size callback 会 resize 远端 PTY**。
- Ghostty 有 reflow（1.2.0 修过「reflowing a grapheme」崩溃）；有「first frame render」独立修复。
- 1.2.0 起框线/Nerd 符号按格缩放，避免 fallback 字形撑破格子。

**查不清**：resize 期间是否复用旧帧、是否把 reflow 分期提交。公开资料没有「复用旧帧遮住 reflow」的陈述。本节不把它写成已证实能力。

## 2. 我们现在怎么做（本仓库代码）

主路径：`app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt` 的 `onDraw`，状态在 `TermViewPresenter.kt`，会话订阅在 `SessionViewModel.kt` / `SessionRoute.kt`。

### 2.1 `onDraw` 每帧做什么

帧循环（`TermSurfaceView` 类 KDoc + `frameCallback`）：

1. Choreographer 对齐；`takeDamage()` **取走即弃**，不按脏行裁剪。
2. `beginFrame()` 抓一次 `emulator.snapshot()`。
3. `invalidate()` → `onDraw`。
4. **整帧重绘可见窗口全部行**（注释原文：每帧工作量 = 窗口行数，非脏行数，006）。

`onDraw` 本体：

1. `presenter == null` 则 `return`（此时**还没**铺主题底；走 View 默认底）。
2. 整张画布 `drawRect` 一次铺默认背景。
3. 对 `win` 里每一逻辑行调用 `drawLine`。

`drawLine`：

- **背景**：逐格 `canvas.drawRect`（`width==0` 的 CJK 续格跳过；主格按 `cell.width` 铺满）。没有背景 run 合并。
- **前景**：`drawTextRuns` 按 **resolvedFg** 切同色段，再按字形槽切子段。
  - `MONO`（ASCII 0x20–0x7E）：一段一次 `drawText`。
  - `SYSTEM_FALLBACK` / `POWERLINE`：`drawCentered` **逐码点** `measureText` + `drawText`（或框线走 `BoxBlockGeometry` 的若干 `drawRect`）。

**没有 glyph atlas / 纹理图集。** `GlyphFontProvider` 只是三支 `Paint`（MONOSPACE / DEFAULT / 内置 Powerline），每帧直接把字形交给 Canvas/HWUI。`colorFor` 已走 `TermPalette` 预计算表（perf-v1：857.6ns→87.4ns），不是本帧大头。

### 2.2 量化：一屏多少格、几次 draw

字号默认 14sp（`SharedPreferencesFontSizeStore.DEFAULT_FONT_SIZE_SP`）。代码注释里的真机格宽实例是 **cellW=19px**（`⠋=22px vs 格 19px`）。构造期默认度量是 `DEFAULT_CELL_WIDTH=10` / `DEFAULT_CELL_HEIGHT=20`，仅在 seed 前存在，正常绘制用实测值。

以 1080px 宽、内容区约 1000px、cellW=19、cellH=32、可见约 40 行为例（公式，不是一次真机采样）：

| 量 | 公式 | 约数 |
|---|---|---|
| 列 | `usableWidth / cellW` | ~50 |
| 行 | `viewportHeight / cellH` | ~40 |
| 格 | 行 × 列 | **~2000** |
| 背景 `drawRect` | 每主格 1 次（CJK 主格 1 次盖 2 列） | **~1500–2000 / 帧** |
| ASCII `drawText` | 每行每条同色 MONO run 1 次 | 纯 ASCII 同色屏 ≈ 40；彩色 TUI 每行数段 → **数百** |
| fallback `drawText` | 每非 ASCII 码点 1 次 + 1 次 `measureText` | Claude/CJK/框线密集时 **数百到上千** |
| 合计 Canvas 调用 | 背景格 + 文本段 + 几何块 | **量级 2×10³ – 4×10³ / 帧** |

滚动时：`onScroll` 只改视口顶行（或把行增量发给远端），然后 `onFrameRequested` → **同一条全窗口 `onDraw`**。没有「位移上一帧纹理、只补新露出的一行」。

对比：GPU 终端公开设计是字形进图集后整屏几次 draw call（发行说明里的 atlas + Metal/OpenGL），不是每格一次 CPU `drawRect`。

### 2.3 滚动 / 首帧 / 尺寸协商

**滚动**：本地 `TermViewPresenter.onScrollBy` 或远端 `onRemoteScrollBy`。画面更新仍是全窗口重绘。脏区列表存在，渲染层不用。

**首帧 / 081**：

1. `SessionRoute.createSessionViewModel` 用常量 **`INITIAL_ROWS=40`、`INITIAL_COLS=120`** 构造 VM。
2. `SessionViewModel.init` **立刻** `manager.subscribe(ref, 40, 120)` —— 服务端按 120 列出第一张 SNAPSHOT。
3. `TermSurfaceView` 注入 presenter → `applyFontMetrics` → `seedCellMetrics`（不在这里 resize）。
4. 首次正尺寸 `onViewportSizeChanged` / `onRealViewportChanged` 才 `recomputeGeometry()` 并 `onResizeRequest`（081：进入 CLI **只允许一次** resize）。
5. `SNAPSHOT` 到达：`emulator.replaySnapshot`；列不一致时打 `reflow` 日志。

perf-v1 进入会话读数（基线包=当前包）：`viewport=4 resized_true=1 reflow=2 grid=1`。与「先按 120 列订、再按真机列数 resize 一次、CLI 重排」同构。

**S3 相关**：`onDraw` 在 `presenter == null` 时直接 return，不画格子。SNAPSHOT 是异步二进制帧。perf-v1 的 `screencap` 单次约 1.2s，亚秒白闪测不到。

## 3. 差在哪（可证伪对照）

每条格式：上游 X / 我们 Y / 差距导致 Z。

1. **字形**  
   上游引擎用 GPU 字形图集 + 缓存查找（来源：[Ghostty 1.2.0](https://ghostty.org/docs/install/release-notes/1-2-0) 「font atlas」「cached glyph lookup」）／我们现在是 `TermSurfaceView.drawGlyphRuns` / `drawCentered` 每帧 `Canvas.drawText`，`GlyphFontProvider` 无图集／差距导致每帧数千次文本光栅，对应可量指标：`onDraw` 墙钟、其中 `drawText` 次数与耗时（真机 DiagLog，见 §5）。

2. **背景铺格**  
   上游引擎用 GPU 格实例 / 着色器铺背景（来源：[About Ghostty](https://ghostty.org/docs/about) GPU；[libghostty 路线](https://mitchellh.com/writing/libghostty-is-coming) 「provide OpenGL or Metal surface」）／我们现在是 `drawLine` 逐格 `drawRect`（`TermSurfaceView.kt`）／差距导致仅背景就 ~2×10³ 次 draw 调用。指标：`bgRectCount` / `onDraw` CPU 微秒。

3. **脏区**  
   上游是否脏矩形：**查不清**（公开文档未保证）／我们现在明确是全窗口：`takeDamage()` 在 `frameCallback` 里排空即弃，`onDraw` 遍历整个 `win`（`TermSurfaceView.kt`）／差距导致 **1 行 TUI 更新也付 40 行的钱**。指标：`dirtyRowCount` vs `drawnRowCount`（今日后者恒等于可见行）。

4. **滚动**  
   上游公开保证是 GPU 上画 + 引擎内 scrollback（[Heeler 官网](https://heeler.bybee.dev)、[ADR 0004](https://github.com/ZingerLittleBee/Heeler/blob/main/docs/adr/0004-libghostty-terminal.md)）；是否位移纹理 **查不清**／我们现在滚动只改 `topLine` 然后整屏 `onDraw`／差距导致滑动每一帧都是满屏 2×10³+ 调用。指标：滑动窗口内 `onDraw_us` p95；perf-v1 模拟器 janky% ~93、p95 32–34ms（**绝对值不可信，见 §5**）。

5. **进入尺寸**  
   上游嵌入把 **cell-size → 立刻 resize 远端 PTY**，宿主负责格子与 PTY 一致（[libghostty-spm](https://github.com/Lakr233/libghostty-spm)、ADR 0004）／我们现在先 `subscribe(40, 120)`（`SessionRoute.kt` `INITIAL_COLS=120`）再在首帧视口上 `resized=true` 一次（`TermViewPresenter.onViewportSizeChanged`）／差距导致 **第一张 SNAPSHOT 按 120 列排、第二次按真机列数排**，用户看见进会话重排。指标：已有 `resized_true`、`reflow` 的 `frame cols` vs `render cols`（perf-v1：resized_true=1、reflow=2）。

6. **首帧有格**  
   上游有独立 first-frame 路径（1.2.0 修过 first frame 内存访问），但「进页 0ms 必有内容」**查不清**／我们现在 `presenter ?: return` 不铺格，内容等 `SNAPSHOT`（`SessionViewModel.onBinary`）／差距导致进入会话前几帧可能是 View 默认底。指标：`t_firstOnDraw` vs `t_firstSnapshot` vs `t_firstOnDrawWithCells`（今日无这三项，§5 要补）。

## 4. 我们该怎么做（自己的设计）

不嵌入 libghostty、不搬 Metal、不把 Android `Canvas` 换成「跟某 iOS 应用同一套 API」。目标是：**同一套格子语义（085 重着色、083 格对齐、CJK 宽字符）下，把每帧 CPU/HWUI 工作量从「可见格数」降到「变化格数」**。

### 4.0 共同前置格（所有症状的量具）

**改哪里**：`TermSurfaceView.onDraw` / `frameCallback`；只加 `DiagLog.record`，不改绘制结果。

记操作数（诊断纪律：两边都记）：

```
term-draw source=onDraw dt_us=… rows=… cols=… cellW=… cellH=…
bgRect=… textDraw=… measureText=… geomRect=…
dirtyRowsIn=… drawnRows=… presenterNull=0|1 cellsNonBlank=…
frameTimeNanos=…
```

`dt_us` = `onDraw` 入口到出口。`dirtyRowsIn` = 本帧 `takeDamage` 行数（即使暂时仍全绘也记）。`cellsNonBlank` = 本帧画到的非默认空白格数。

**预期**：不改变用户可见画面。收益是真机可定罪，而不是模拟器 janky%。  
**验证**：用户导出诊断日志，进会话 + 滑两下，应能看到上述行。  
**风险**：日志量。必须 `coalesceKey` 或滑动期每 N 帧一条，避免无界。  
**拆格**：单独一格 `t.meter`，写范围仅 `TermSurfaceView.kt` 仪表。串在所有绘制改动之前。

### S1 进入会话重排

**因果（已能从代码对上 perf-v1，不是猜）**：订阅列 120 ≠ 真机列 ~50，SNAPSHOT 先按 120 来，081 再 resize 一次，CLI 重排。`resized_true=1` 已是 081 下限，再砍「这次 resize」会让列错。要砍的是 **「错误的第一次格子」**。

**改哪里**：

- `SessionRoute.kt`：`INITIAL_ROWS` / `INITIAL_COLS` 不再写死 40×120。
- 新增（或复用已有 Settings 存储）「上次成功视口」：`rows, cols, cellW, cellH, fontSizeSp, viewW, viewH`。写入点：`TermViewPresenter.recomputeGeometry` 成功上抛之后。
- `createSessionViewModel`：用上次成功行列 subscribe；无缓存才回落 40×120。
- `SessionViewModel.init` 的 `subscribe` 入参跟这笔缓存走。

**预期收益**：真机第二次及以后进同一字号/同一方向会话，`reflow` 里 `frame cols` 应 **等于** `render cols`（或差 ≤1 列取整）。用户可见的「进页排版跳一下」应消失或只剩字号/旋转后第一次。`resized_true` 仍允许为 1（081），但若候选行列已等于内核，这次 resize 应是 no-op（协议层已有则保持）。量级：重排次数从「每次进入 1 次可见 TUI 重排」→「缓存命中时 0 次可见重排」。

**验证（真机日志，不要只看模拟器）**：

- `reflow frame cols=A render cols=B`，缓存命中时 A==B。
- `viewport … result resized=… candidateCols=… emulatorCols=…` 两边一起看。

**风险**：

- 085：不碰着色。
- 083：缓存必须带 `cellW/cellH/fontSizeSp`；字号变了弃缓存，否则列错。
- 旋转 / 分屏：视口变了必须当未命中。
- 081：仍然只允许一次真实 resize；缓存命中是「第一次订阅就已经对」，不是再发一次。

**拆格**：`t.enter-geom`。写范围：`SessionRoute.kt` + 一个小 Store + `TermViewPresenter.recomputeGeometry` 成功后的写缓存。**不要**同时改 `onDraw`。串在 `t.meter` 之后（用 reflow 日志验证，不依赖绘制改动）。

### S2 滑动掉帧

分两刀，文件交叉为零。

#### S2-a 让脏区真正裁剪绘制

**改哪里**：`TermSurfaceView.frameCallback` + `onDraw`。`takeDamage()` 的返回值改为本帧要画的行集；空脏且视口未滚则不要 `invalidate`。全窗口仍保留一条路径：snapshot 重放、字号变、主题变、`clipGuard` 需要时。

**预期**：稳态 TUI 每帧只更新状态行/光标行时，`drawnRows` 从 ~40 → 1–3。Canvas 调用从 10³ 降一个数量级。若 `onDraw_us` 是主因，真机 p95 应从「>16ms」掉到「个位数 ms」量级（**以真机 `dt_us` 为准，不以模拟器 janky% 为准**）。

**验证**：同一滑动手势导出日志，对比改前/改后 `drawnRows` 与 `dt_us` p50/p95。

**风险**：

- 滚动改 `topLine` 时，若只画 damage 行、不画因视口平移而新露出的行，会花屏。滚动帧必须把「新进入窗口的行」并进 drawn 集；S2-a 先做 **非滚动脏行**，滚动整窗仍可暂时全绘。
- 085：脏行仍走 `resolvedFg/Bg` → `TermPalette.colorFor`，语义不变。
- 083 / CJK：仍按整行画，不把宽字符从中间切开。
- BCE：未重绘的行必须仍是上一帧的像素；依赖 View 不在中途被系统清屏。若 HWUI 不保留，本格会失败——用 `dt_us` + 真机截图判定，失败则停，改走 S2-b，不叠补丁。

**拆格**：`t.dirty`。只动 `TermSurfaceView.kt` 的帧消费。在 `t.meter` 之后、`t.scroll-blit` 之前。

#### S2-b 滚动：整行像素平移 + 只补露出行

**改哪里**：`TermSurfaceView` 增加一块与 View 同尺寸的软件/硬件层缓冲（`Bitmap` 或 `RenderNode`）。当 `deltaLines != 0` 且 `|delta| < visibleRows` 时：把上一帧像素按 `deltaLines * cellH` **整数像素**平移，只 `drawLine` 新露出的那几行。

这是我们自己的设计：利用「终端滚动是整行」这一离散性质，不是位移 GPU 图集（那份做法公开资料也没写死）。

**预期**：滑动帧的 `drawnRows` ≈ `|deltaLines|`（通常 1–3），`bgRect`/`textDraw` 同比下降。真机 `dt_us` 应接近「画 1–3 行」而不是「画 40 行」。

**验证**：日志里 `source=onDraw` 带 `scrollDelta=` 与 `drawnRows=`；用户真机滑动不再以「整屏闪/拖影」为主诉（主观）+ `dt_us` p95 < 16ms（客观）。模拟器 janky% 只作附记。

**风险**：

- 083：平移必须是 `cellH` 的整数倍，禁止亚像素滚动（我们手势层已经是整行，`pendingScrollPx` 已对齐）。
- 085：缓冲里是已经投影过的 ARGB；主题切换必须丢缓冲全绘。
- CJK / 框线：只补整行，不切格。
- alt-screen 远端滚动：内容是远端重画而非本地 `topLine` 平移，S2-b **不适用**；那种帧走 S2-a 或全绘。日志必须带 `followBottom` / `alt` 若内核暴露；**内核若没有 alt 旗标可读，标查不清，先用「是否 onRemoteScrollBy」区分**。

**拆格**：`t.scroll-blit`。只动 `TermSurfaceView.kt` 缓冲，不动 presenter 几何。在 `t.dirty` 之后（需要「按行画」已经能工作）。

#### S2-c 字形图集（仅当 t.meter 证明 `drawText` 仍占 `dt_us` 大头）

**改哪里**：新建 `GlyphAtlas`（LRU 位图，键 = 槽位 + 码点 + textSize + 灰度），`drawCentered` / MONO 短 run 改为 `drawBitmap`。**不要**把颜色烤进图集（085 主题切换会爆缓存）；图集只存 alpha，绘制时用 `Paint.color`。

**预期**：fallback 密集屏（CJK、logo 块已改几何，主要剩 CJK/emoji）少反复 shaping。量级：`measureText` 次数应接近 0（命中时）；`dt_us` 再降一截，**幅度查不清**，必须先有 S2-a/b 后的基线。

**风险**：内存无界 → 必须有上限（按格数字节，超限逐出）。083 非整数密度：图集按当前 `cellW/cellH` 重建，禁止跨密度复用。框线/块继续走 `BoxBlockGeometry`，不进图集。

**拆格**：`t.glyph-atlas`。新文件 + `TermSurfaceView.drawGlyphRuns` 调用点。与 S1/S3 文件不相交。只在仪表证明文本是大头之后开工。

### S3 进入会话短暂白屏

先定罪，再改路径。白闪有两种完全不同的操作数，不能混成一条修法：

| 假设 | 日志判据 | 真解 |
|---|---|---|
| A. presenter 尚未注入 | `presenterNull=1` 的 `onDraw` 出现在 SNAPSHOT 之前 | 在 `AndroidView` 第一次 layout 前就注入已有 presenter（VM 构造时 presenter 已存在，缺的是 View 绑定时机） |
| B. presenter 在、格子还是空的 | `presenterNull=0 cellsNonBlank=0` 且 `t_firstSnapshot` 晚于首帧 | 让 SNAPSHOT 在首帧 `onDraw` 之前到达：L2 可见时预订阅，或 VM 构造推迟到已有缓存行列且连接已在推流 |
| C. 数据物理上不可能与第一 vsync 同帧 | `t_firstSnapshot - t_enter` 已低于一帧仍无格 | **这条我给不出真解** |

**改哪里（仅假设 A/B 成立时）**：

- A：`SessionScreen` 里 `AndroidView` 的 factory/update，保证第一帧 `presenter` 非空（文件：会话屏里创建 `TermSurfaceView` 的那一处，不动绘制算法）。
- B：把 `subscribe` 从「进入三级才订」前移到「二级列表该行可见」或「点击即时、在 composable 第一帧之前已有 SNAPSHOT」。写范围：`SessionViewModel` 的订阅时机 / L2 预取，**不要**改 `onDraw` 填色。

**预期**：`t_firstOnDrawWithCells - t_enter` 降到一帧量级（≤20ms 量级，真机日志）。用户感知的白闪消失。screencap 1.2s 粒度仍然抓不住，**不以 screencap 验收 S3**。

**风险**：L2 预订阅会多一条镜像流（流量/CPU）。必须有上限（只预取当前可见的一条，离开取消）。085/083 不涉及。若预取 SNAPSHOT 仍是 120 列，会把 S1 弄得更显眼 → **S3-B 必须排在 `t.enter-geom` 之后**。

**拆格**：

- `t.s3-bind`：只修 presenter 绑定时机（假设 A）。
- `t.s3-snap`：只修 SNAPSHOT 到达时机（假设 B）。与 `t.enter-geom` 都碰订阅参数 → **串行，且 enter-geom 在前**。

假设 C 成立时停笔，不发明画面。

## 5. 模拟器可信度与真机量法

083 §0：模拟器在渲染层没有分辨力；整数密度会掩盖取整误差。perf-v1 的 janky% ~93% 与 p95 32–34ms **基线包=当前包**，只能用来排除「085 把滑动弄得更差」，不能用来给「有多卡」定绝对值。那是模拟器伪影候选，不是真机判决。

**真机量法（用户导出诊断日志即可，不依赖 adb / 模拟器 / gfxinfo）**：

1. 打开会话，滑几下，再返回。设置里已有的诊断导出照旧。
2. 看 `term-draw`：
   - S2 定罪：滑动期间 `dt_us` 的 p50/p95，以及 `drawnRows`、`bgRect`、`textDraw`。p95 长期 >16000 且 `drawnRows`≈可见行 → 全绘过重成立。
   - S1 定罪：`reflow frame cols` vs `render cols`；不等则重排来自订阅列，不是「GPU 不够」。
   - S3 定罪：`t_firstOnDraw` / `t_firstSnapshot` / `t_firstOnDrawWithCells` / `presenterNull`。三者时间差能量到亚秒（日志是事件时间，不受 1.2s screencap 限制）。
3. 改动前后各导出一份，比的是 **这些操作数**，不是模拟器 `janky%`。

`gfxinfo` 可以作开发机旁证，**不能**当验收门。

## 6. 风险与查不清

- **滚动是否该上 GPU Surface**：公开的 libghostty GPU 嵌入目标是 OpenGL/Metal surface，**没有**现成的 Android 稳定包。自研 GLES 图集是另一条产品线，本格不把它写成 S2 的第一刀。查不清自研 GLES 是否值得，直到 `t.meter` 给出真机 `dt_us` 构成。
- **脏矩形在 Ghostty 里到底怎么做**：查不清。我们按自己的 `takeDamage` 语义做行级裁剪，不声称「与上游一致」。
- **S3 白闪的主因是 A 还是 B 还是 C**：查不清，现有采样粒度不够。先 `t.meter` + 时间戳，再开 `t.s3-*`。
- **S2 主因是 CPU `drawRect/drawText` 还是 HWUI/GPU 上传**：查不清。`dt_us` 只覆盖 `onDraw` CPU 墙钟；若 `dt_us` 已经 <8ms 而用户仍掉帧，瓶颈在提交/合成，S2-a/b 收益会很小，那时才考虑独立硬件层，而不是先上 GLES。
- **120 列首订是否每次都打到用户眼里**：perf-v1 的 reflow=2 支持「进页发生过列对齐」，但用户说的「明显重排」有多少来自 CLI alt-screen 自己的 redraw、多少来自 120→真机列，**查不清比例**。`t.enter-geom` 是对「列不一致」这一可证伪因子下手；若缓存命中后用户仍报重排，剩下的是 CLI 自身首帧，不是我们的二次 resize。
- **colorFor 10× 而屏幕不变**：已由 perf-v1 排除为主因。本思路不再动 `TermPalette`。

本格不把「查不清」补成故事。
