# 任务书 · t.sockfix · 死 socket → 空闲 CPU 的因果曲线，然后把它修平

## 一、已知与仍缺的（⛔ 先读，决定你做什么）

**已知（leader 在生产上实测，用户真机确认）**：

- `/private/tmp/tmux-501/` 里积了 161 个 tmux socket，其中 **140 个连不上（死的）**。
- 生产 daemon 空闲 CPU 采样 `0.0 17.0 33.6 21.6 34.3 33.7 27.4 18.2`（均值 ≈23%）。
- **只删掉那 140 个死 socket**（不改代码、不重启 daemon），CPU 立刻变成
  `0.0 0.2 2.6 0.1 7.1 2.0 0.0 2.4 0.0 2.9`（均值 ≈1.7%）。**用户复测：「变好了」。**
- 机理在 `server/internal/discovery/scan.go:152`：`DiscoverWithDirs` 对目录里
  **每一个 socket 文件串行 fork 一个 `tmux list-panes`**，死 socket 要等连接失败才跳过；
  `list-interval` 缺省 **2s**。

**仍缺的（这一格要补）**：上一格 `t.idlecpu` 在**隔离目录**里测，那里**没有死 socket**，
三态都是 0.0% —— 所以它**证不了也证伪不了**上面的机理。
**缺的是一个受控实验：把死 socket 数当自变量。**

## 二、第 1 步：因果曲线（⛔ 先做这个，不做完不许改代码）

起隔离 daemon（高端口，⛔ 不是 9900），发现目录用你自己的
（`AGENTMIRROR_E2E_DISCOVERY_SOCKET_DIRS`）。在目录里放 **N 个死 socket**
（死 socket 的造法：起一个 tmux server 再杀掉它、留下 socket 文件；
或任何能让 `tmux -S <f> list-sessions` 失败的 unix socket 文件——**造法写进说明**），
外加**恒定 1 个活着的** tmux server（跑 `cat`，保证有正常工作量做对照）。

对 **N = 0, 25, 50, 100, 140, 200** 各测 ≥60 秒（秒级采样），记录 daemon CPU。

**判据要的就是这条曲线。** 如果 CPU 随 N 单调上升、且 N=140 附近进入两位数，
机理坐实；如果不涨，说明 leader 的诊断错了——**照实报 `hypothesis_refuted`**，
附曲线原文。⛔ 不许因为任务书这么写就把曲线写成想要的样子。

## 三、第 2 步：修（只有曲线坐实才做）

**目标：让空闲 CPU 不再随死 socket 数增长。**

改 `server/internal/discovery/scan.go`（可连带 `server/internal/api/` 的调用侧）。
方向由你定，但必须满足：

- **功能不许退**：活着的 socket 一个都不能漏发现；新出现的活 socket 要能被发现
  （⛔ 不许用「只扫一次然后永远缓存」这种把功能做没了的办法）。
- **死 socket 恢复成活的要能被重新发现**（比如黑名单要有过期，或按 mtime/inode 变化失效）。
- ⛔ 不许简单地把 `list-interval` 调大了事——那是把症状推远，不是修根因。
- 建议方向（**供参考，⛔ 不是指定**）：先 `net.Dial("unix", sock)` 探活再决定要不要 fork；
  失败的 socket 进短期黑名单（带过期）；并行扫描 + 更短超时。

**这条红线要在你的实现里成立**（CLAUDE.md「工程常识红线」第 1 条）：
**静默经济——空闲 CPU 趋近 0、无固定频率子进程派生。**
