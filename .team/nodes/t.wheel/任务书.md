# 任务书 · t.wheel · 双指滑动 = 滚轮（修第 4 步引入的滚动回归）

## 一、用户实撞（2026-08-23，最高优先级）

用户装了含输入透传四步的包，真机反馈：

- ✅ **点工具调用能展开**——链路通了。
- ❌ **滚轮没了**：「之前向上向下滑的话，它是模拟鼠标滚轮的。现在就变成点击的操作了。
  变成点击操作之后，我滑的话，它实际上是鼠标点击左键，然后选择一块文本。」

**根因（leader 已定位，⛔ 但你要自己核一遍）**：第 4 步在
`app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt:377` 的 `onTouchEvent` 里
先跑 `dispatchTermMouse`，`ACTION_DOWN` 一旦被 sink 接受就置 `mouseHeld=true`，
于是后续 `ACTION_MOVE` 走「按住拖动」上报，**`gestureDetector` 拿不到事件**
（`if (!wasHeld && !mouseHeld)` 才转给它）⇒ 原来的 `onScroll → onRemoteScrollBy → ScrollWheelFrame`
路径被挤掉。

## 二、用户要的形状（⛔ 这是需求，不是建议）

1. **双指上下滑 = 滚轮**（模拟鼠标滚轮）
2. **单指拖 = 保持现在的行为**（按住左键拖动 → 内层可以拖选/拖折叠）。⛔ 不要把它去掉。
3. 🔴 **⛔ 不许阻断「真实滚轮」本身的通路**。用户原话：
   「不要阻断本身鼠标滚轮的行为，因为有可能你的核心和服务端代码会给桌面端去使用。」
   ⇒ **核层与服务端的滚轮/输入通路一个字都不许改**；桌面端（有物理滚轮）要照常能用。
   ⇒ 安卓上若接了物理鼠标（`ACTION_SCROLL` / `onGenericMotionEvent`），那条路也要照常。

## 三、要做什么

**只改壳的手势映射**（`app/app/`），把三条路分开：

| 输入 | 行为 |
|---|---|
| **单指** 按下/拖动/抬起 | 走第 4 步的 `dispatchTermMouse`（现状，保留） |
| **双指** 垂直滑动 | **滚轮** |
| **物理鼠标滚轮**（`ACTION_SCROLL`） | **滚轮**（⛔ 不许被新逻辑挡掉） |

**滚轮怎么发**——⚠️ 这一条你要**测出来**，⛔ 不许拍脑袋：

- 既有路径是 `onRemoteScrollBy → ScrollWheelFrame`（用户说那个**以前是好用的**）。
- 但内层若开了鼠标跟踪，**SGR 滚轮**（button 64=上 / 65=下，`CSI < 64 ; x ; y M`）
  才是终端惯例。
- **两条都试，报哪条真的能让内层滚动。** 说明里写清你测了什么、结论是什么。
  如果结论是「跟踪开着时要发 SGR、否则发 ScrollWheelFrame」，那就按这个实现。

## 四、复现先红

- **R1**：模拟**双指**垂直滑动，断言产生**滚轮**动作（⛔ 不是按住拖动上报）。改前必须红。
- **R2**：模拟**单指**拖动，断言**仍然**走 `dispatchTermMouse` 的拖动上报。改前应绿，改后必须仍绿。
- **R3**：模拟 `ACTION_SCROLL`（物理滚轮），断言**滚轮路径不被挡**。改前红或不适用，写清哪种。
- **R4**：内层**未开**鼠标跟踪时，双指滑动**仍能滚动**（回落既有路径）。
