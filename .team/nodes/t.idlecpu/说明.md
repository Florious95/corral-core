# t.idlecpu · 服务端空闲烧 CPU：复现实验

席位：`in-dev2`。worktree：`.worktrees/wt-idlecpu`。本格**只复现与定位，未改仓内产品码**。

`status=not_reproduced`

## 结论（先说）

用 commit `4120c0884817aa312d97d52eea55f49dc0beeb38`（`4120c0884`）在隔离端口 **19971** 起的 daemon，三态 CPU **都趋近 0**。leader 在生产上采到的 17–34% 空闲烧 CPU，**本格没有复现**。

按任务书：复现不出是合法终态。**不猜根因、不采 pprof、不改产品码。**

## 「趋近 0」的操作定义（写清以免和判据打架）

判据 `judge-idlecpu.sh` **不判 CPU 高不高**，只判实验扎实。下面这套是本格自己的复现判定，与 `.team/nodes/rf-ver/idle60.sh` 同口径：

- **趋近 0**：该态 `mean < 1.0` 且 `max < 5.0`（单位：一核的 %）
- **明显不趋近 0**（复现成立）：N0 或 N1-idle 的 `mean >= 5.0`（生产采样在 17–34，远高于此）

Darwin `ps -o time=` 粒度约 0.01s ⇒ 1s 差分的量化台阶约 **1%**。生产级 17% 烧 CPU = 每秒 ~0.17s CPU，会稳定出现在差分序列里，不会被台阶吃掉。

## 观察（不是根因）

1. N0 全 0 与 idle-gate 的 park 路径一致，说明「零客户端还在扫 tmux」这条旧病在 `4120c0884` 上**没有**复现。
2. N1-idle 只在订阅头两秒见到 ~1% 尖峰，之后 58 个样本为 0。日志 `listing: refresh on open` 出现在订阅时，之后 60s 没有持续刷屏。`ws: sendq health` **只在连接拆掉时打一行**（`ws_conn.go:228-234` 注释写「会话结束时打一行，空闲零开销」），不是空闲定时器。
3. N1-busy 作为「有活就该烧」的对照**没有烧起来**：20Hz 一行 `echo` + pipe-pane 增量，对这份二进制仍是 ~0%。这不是采样坏了（17% 会被看见），是隔离 1 pane、小流量撑不起生产那种幅度。
4. 采样期间 host `load1` 在 12.79–18.04，高于模拟器地板常用区间 6.87–10.49。负载高的时候隔离 daemon 仍然 ~0%，更不能用「机器忙」解释生产 17–34%。

## 判不出的部分（合法缺口）

- **生产 33+ 小时累积状态、真实舰队会话数、真实 CLI 复杂度**：本格是干净进程 + 1 个假 `claude` pane。没在生产进程上采样（红线）。
- **生产 1–3 个订阅者**：本格只测了 N=0 和 N=1，没测 N=3。
- **生产 top 17–34% 的瞬时口径**：本格主序列是 TIME 差分。若生产用 `top` 瞬时，数字不能逐点对拍；但 17% 持续烧在差分口径下也会是双位数，本格没有看到。
- **根因**：复现不成立，按任务书禁止猜。未抓 CPU profile，所以也没有 top 帧。
- **白屏与这次 CPU 的因果**：本格只回答「隔离 4120c0884 空闲是否烧 CPU」。用户「局域网打开会话白屏变长」是否另有网络/客户端路径，本格没测。
