# t.unk · 第三条 footer 语料补回

## 缺的是哪一行

`titles.tsv` 在 `git checkout` 后只剩两条 footer（leader 已从报错原文救回）：

| payload（子串针） | want | provider | 对应用例 |
|---|---|---|---|
| `command still running` | `1` | grok | `TestFooterGrokRunningIsCountNotFoldedIntoState` / `footer_grok_running_is_count_state_stays_idle` |
| `just a prompt · nothing in flight` | `0` | grok | `TestFooterGrokVacuumIsZeroNotConstantOne` / `footer_grok_vacuum_is_zero_not_constant_one` |

`n_footer >= 3` 卡的是第三态。Go/Rust 页脚维是三值：有规则命中=`N`、有规则未命中=`0`、**语料无该 provider 的 footer 规则=`unknown`**。第三条必须来自第三个实际用例，不能另编一条 grok 针把计数凑满。

第三个用例：

- Go `TestFooterProviderWithoutRuleIsUnknownNotZero`
- Rust `footer_provider_without_rule_is_unknown_not_zero`

两边用的是同一段 grok 页脚里的子串，对 **没有 footer 规则** 的 provider 断言 `unknown`（且不得报 `0`）：

```
◉ 1 command still running · send a message to interrupt
```

payload 按契约是子串针，不是整句。该用例相对前两条多出来的针是 `send a message to interrupt`；provider 取两边都点名的第一家 `claude_code`。

补回行：

```
send a message to interrupt	unknown	claude_code	footer
```

## 规则表不能登记 want=unknown

`load_footer_rules` / `loadFooterRules` 原先只要看到该 provider 的任意 footer 行就会建规则。若把上面这行登记进去，`claude_code` 会变成「有规则、零针」→ `Count(0)`，与第三个用例和「无规则绝不报 0」相反。

因此 want=`unknown` 只当语料断言，**不写入规则表**。Go/Rust 同一条处理，两边对同一语料判定一致。
