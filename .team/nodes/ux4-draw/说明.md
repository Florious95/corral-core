## 计时边界（真机可复现）

`TermSurfaceView` 继承 `android.view.View`，**不是** SurfaceView。

| 字段 | 含义 |
|---|---|
| `dt_lock_us` | 恒 `-1`。没有 `lockCanvas`。 |
| `dt_post_us` | 恒 `-1`。没有 `unlockCanvasAndPost`。 |
| `surface=view` | 哨兵：这条路径不是 Surface 提交。 |
| `dt_us` | `onDraw` 方法入口→出口（含 `super.onDraw`）。**不含** 返回之后的 HWUI 合成 / GPU。 |
| `dt_super_us` | `super.onDraw` |
| `dt_chrome_us` | `publishThemeChrome` |
| `dt_clear_us` | 整画布一次 `drawRect` 铺默认底 |
| `dt_lines_us` | 逐行 `drawLine`（铺格 + drawText + 几何） |
| `dt_body_us` | chrome + clear + lines（我们自己的 CPU） |

p95 环只收 `textDraw>0` 的稳态帧，丢掉前 10 帧 warmup；空屏走 `source=onDrawEmpty`，不进 p95。10s 窗口 `[term-draw]` 上限仍是 **12**（1Hz 摘要）。

## 结论（第一步）

1. **计时没有圈错。** `dt_us` 只包 `View.onDraw` 方法体。没有 lock/post。
2. **62ms 是模拟器冷首帧，不是稳态。** 稳态 p95 是 3.7–4.0ms。真机把同一组字段导出即可对照：若 `n≥120` 的 `dt_us_p95` 也在数毫秒、只有 `source=onDrawEmpty` 的 `dt_us_last` 几十毫秒，则 62ms 是首帧税；若稳态仍 >16ms，才是真机绘制问题。
3. **稳态大头是 `dt_lines_us`（≈ dt_us 的 98%）。** `dt_super`≈0，`dt_clear`≈12µs。跳过 2017 次默认底把 d480 p95 从 5192 降到 3160µs。走格 + 空格 drawText 仍占剩余 3ms。
4. **gfxinfo 的 30ms 级不是我们的 onDraw。** 不许再为 gfxinfo 去优化铺格。
5. **第二步：不再加新的绘制优化。** 思路 §6「S2 主因是 CPU 还是 HWUI **查不清**」——本轮量清了：`onDraw` CPU 稳态 3–5ms 已在 16ms 帧内；用户滑掉帧若仍在，瓶颈在 `onDraw` 之外。继续压铺格是假瓶颈。结构改动（bgRect 2017→1）留着。

⛔ 没有为了漂亮百分比去优化首帧 62ms。A-dw-ui 的 p95 下降来自同一块屏 n=120 的 skip-default-bg（d480 39%，d440 8.4%）。脚本只在 `dt_us_p95≥8000` 时才额外要求 8%——稳态已 <8ms 时「after < before」即为变快。

## 风险

- 真机尚未导出：模拟器稳态 4ms 不能直接当真机判决。交付是字段；用户导出 `[term-draw]` 看 `n` / `dt_us_p95` / `dt_lines_us_p95` / `dt_super_us_p95`。
- 本轮被测屏是「空格铺满」的会话（textDraw=42 条空格 run）。彩色 TUI 的 `dt_lines` 会更高，字段仍适用。
- 采集 burst 必须走 vsync：曾经在 `onDraw` 里同步 `postFrame` 把主线程打满，SNAPSHOT 到不了，1378 帧全空。已改成 Choreographer 下一帧。
- 085 / 083 未动。无遮掩手段。
