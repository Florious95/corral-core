## 一、Q1：**谁**负责画选中高亮？

**结论**：**只可能是内层 app 通过属性字节让终端画。我方（客户端）从头到尾没有「选区」这个概念**——

**置信度**：`源码确定`

**证据**

1. **全仓零选区代码**。对 `app/app/.../termview/` 与 `app/core-terminal/` 全目录

2. **渲染只读单元格样式**：`app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt:899`
   / `:902` 是全部的颜色决策口：
   ```kotlin
   if (style.inverse) colorFor(style.fg, background = false) else colorFor(style.bg, background = true)
   if (style.inverse) colorFor(style.bg, background = true)  else colorFor(style.fg, background = false)
   ```
   **没有第三个来源可以往某几格叠一层高亮。**
3. **拖动被原样转发给内层**：`app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt:391`

   由 `app/core-terminal/src/main/kotlin/dev/agentmirror/terminal/TerminalEmulator.kt:141`
   `encodeMouse` 编成 SGR 1006 原始字节发给 pane。
   ⇒ **拖动的语义解释权在内层 app 手里，我方只当传声筒。**

⇒ **架构上，我方能显示的选中高亮 = 内层重绘时打进字节流的属性。没有别的可能。**

## 三、Q3：修它要动哪一层？**最小改动方向**

⛔ **这一格不实施。** 且**方向取决于上面那个没定的分叉**，所以给两套，先测再选：

### 方案 A（若实测确认「内层确实发了属性、我方却没画出来」）

**不成立的可能性很大**（2/3/4/5 环已全排除），真出现说明我漏了一环。
那时候的最小改动方向是**渲染层**，锚点 `app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt:899-902` 的 `bgPaintFor`/`fgPaintFor`——
但在动手之前必须先补一条诊断：把「某一帧里带 inverse 的格数」记进 `DiagLog`，
否则又会掉进「日志里只写未触发、分不清是没画还是没收到」那个坑（CLAUDE.md 诊断日志纪律）。

### 方案 B（若实测确认「内层不发属性 / 那个高亮本来就是桌面终端画的」）——**我认为这条概率高得多**

**唯一的修法是我方自建一个本地选区层，且只动渲染层，⛔ 不动核层。**

- **不动核层的理由**：选区是**视图状态**，不是终端状态。塞进 `Cell.style` 会让
  `replaySnapshot`（`app/core-terminal/src/main/kotlin/dev/agentmirror/terminal/TerminalEmulator.kt:171`）每次整屏重建时把它一起抹掉，
  而快照在打开会话与每次真 reflow 时都会来一发——选区会莫名其妙消失。
- **最小改动方向**：在 `TermSurfaceView` 增加一个「选区矩形/行列区间」字段，
  在 `onDraw` 的**逐格铺背景那一步之后、画字之前**对落在选区内的格子叠一层半透明色。
  锚点就是已经存在的两处 `canvas.drawRect(..., bgPaint)`（`app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt:533` / `:564`）
  所在的那一遍循环——**它已经是按格遍历的，加一个区间判断即可，不新增遍历。**
- **交互侧**：选区的起止点来自触摸，`app/app/src/main/java/dev/agentmirror/app/termview/TermMouseCapture.kt`
  已经把像素换算成 1-based 行列并做了跨格去重，**换算逻辑可以直接复用，不用新写**。
- ⚠️ **但这会和「拖动转发给内层」抢同一个手势**（`app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt:391` 的 `dispatchTermMouse`
  在跟踪开启时会吃掉拖动）。⇒ **这是个产品裁定，不是实现细节**：
  单指拖动到底归「内层选择」还是「本地选择」，得先定，⛔ 我不替用户定。

## 四、⚠️ 顺带撞出的一个独立缺陷（**与本缺陷同一条链路，且是 `源码确定`**）

**`replaySnapshot` 会把鼠标跟踪模式清空，而这个状态无法从快照里恢复。**

- `app/core-terminal/src/main/kotlin/dev/agentmirror/terminal/TerminalEmulator.kt:176`：
  ```kotlin
  mouse.reset()
  ```
  就在 `replaySnapshot`（`:171`）体内，与 `style` / `parser` 一起被复位。
- 而发不发得出鼠标字节，闸就在 `app/core-terminal/src/main/kotlin/dev/agentmirror/terminal/TerminalEmulator.kt:151`：
  ```kotlin
  if (!mouse.canEncode()) return null
  ```
  `canEncode()`（`app/core-terminal/src/main/kotlin/dev/agentmirror/terminal/MouseModeTracker.kt:69`）要求 `tracking ∈ {1000,1002}` **且** `encoding == 1006`。
- **状态只能从 `ESC[?1002h` / `ESC[?1006h` 这类 DECSET 序列重建**（`app/core-terminal/src/main/kotlin/dev/agentmirror/terminal/TerminalEmulator.kt:352`
  的 `setPrivateMode` → `mouse.apply`）。
- 🔴 **而快照里没有这些序列**——`实测确定`：

  ```
  $ tmux -S /tmp/e2e-sel/s display-message -p -t sel '#{mouse_any_flag}'
  1                              ← pane 里的程序确实开着鼠标跟踪
  $ tmux -S /tmp/e2e-sel/s capture-pane -e -p -t sel | grep -c '?100'
  0                              ← 快照里一个 DECSET 都没有
  ```
  服务端也不会补：`server/internal/api/ws_handler.go:40` 的 `snapshotWithCursor`
  只追加一个 CUP，`server/internal/bridge/bridge.go:62` 就是裸 `capture-pane -e -p`。
  而 `pipe-pane` 是在订阅那一刻才挂上的，内层**开机时**发的那串 DECSET 早就过去了。

⇒ **推论：进入会话拿到首帧快照之后，客户端认为「对面没开鼠标跟踪」，
拖动一律 `encodeMouse → null → 不发帧`**（`app/app/src/main/java/dev/agentmirror/app/session/SessionViewModel.kt:535` 的 `onTermMouse` 返回 false），
**手势退回本地/远端滚动**（`app/app/src/main/java/dev/agentmirror/app/termview/TermSurfaceView.kt:381-385`：sink 返回 false 才交给 gestureDetector）。
每次真 reflow 补推快照，这个状态还会**再被清一次**。

🔴 **但这条推论与用户的实撞直接冲突**：用户说「右下角不断有提示说你复制了多少长度的文本」，
说明**确实有东西在响应拖选并完成复制**。若鼠标字节根本没发出去，这件事不该发生。

**⛔ 我不给这个冲突编解释。** 它只有两种收场，且都必须靠实测分辨：
- (a) 内层在 delta 里**周期性重发** DECSET，把状态又补了回来 ⇒ 上面这条缺陷是「时窗性」的，
  表现为「刚进会话那几秒拖选没反应，过一会儿又行了」；
- (b) 我对某一环的读法有错，`mouse.reset()` 实际没有生效在这条路径上。

**这个冲突是下一步最该测的东西**——它比「选中高亮」本身更靠近链路根部。
