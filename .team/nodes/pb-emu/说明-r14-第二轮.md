### 本轮的新证据（这是这一轮的价值）

`grep -l "ref_mismatch\|reason=no_open" .team/perf/raw/*.log | wc -l` → **0**。

`t.instr2` 把两条原本静默的 return 补成了 `emitted=0` 记录：
- `SessionViewModel.onBinary` 首行 `frame.ref != ref` ⇒ `first_frame_recv emitted=0 reason=ref_mismatch frame_ref= want_ref=`
- `PerfTrace.emitFirstFrameIfFirst` / `emitSnapshotIfFirst` 的 `opens[ref]` 落空 ⇒ `emitted=0 reason=no_open want_ref=`

**两种都一条没打** ⇒ `onBinary` 这个方法本身没有被调用过。所以：
**不是 ref 不匹配，也不是 opens 簿记落空，是帧根本没走到收帧口。**

同时服务端仍然坚称推了：daemon 日志每条连接 `conn.snapshots_pushed=1 conn.snapshots_from_subscribe=1`，
每次订阅 `msg=perf_subscribe … done_ms-recv_ms≈60–80ms`
（原文 `.team/perf/raw/diag/daemon-sendq-perfsubscribe-tail.log`）。

> 附一条对第一轮的更正：`conn.frames_sent=0` **不是**证据。读 `sendq_metrics.go:86` +
> `ws_conn.go:331` 可知 `FramesSent` 只在 `sendMirror`（delta 路径）自增，空闲夹具没有 delta，
> 恒为 0 属正常。第一轮我把它列为旁证，收回。

### 下一个该补仪表的位置（读码给出，⛔ 我没改）

`app/app/src/main/java/dev/agentmirror/app/conn/ConnectionManager.kt:617`
```kotlin
override fun onBinary(frame: BinaryFrame) {
    listener?.onBinary(frame)      // ← 单一全局 listener；为 null 或被别人覆盖时静默丢帧，零日志
}
```
`listener` 是**一个全局槽位**（`:96 private var listener: Listener?`，`:137 setListener`）。
帧到达时若该槽为 null 或已被别的页面覆盖，`?.` 会静默吞掉，**上下游都不会留任何一行**。
这正是现在唯一还分不开的两种可能：
① WS 层压根没收到这一帧（网络/读循环侧）；② 收到了但 `listener` 没接上/被覆盖 ⇒ 丢在 `:617`。
建议在 `:617` 补一行 `emitted=0 reason=no_listener`（带 `frame.ref` 与 `listener==null` 两边操作数），
并在 WS 二进制读入口补一行「收到帧」计数，两处一补即可一锤定音。这属仪表面第三轮返修，不是本格能定的。

  `sh tools/perfbase/judge-baseline.sh` 实跑 FAIL（输出 `.team/nodes/pb-emu/tmp/judge-baseline.out`）。
- **本轮连「≥10 次冷点开」都没凑齐**：三夹具有数据的次数分别是 6 / 8 / 9（尝试各 10 次）。
  失败原因是导航超时与 logcat 空输出，**不是我少跑**；跑的是各 10 次，原始记录都在。

  第一轮 ≈ 0.54 s。差别来自宿主机负载（load 9.16→11.89、free 一度只剩 70 MB），不是被测物变化。
  这条本身就说明：**要立地板，得先有一个负载受控的量测环境**，否则同一构建两轮能差 3 倍。
- 极端值**一个都没剔除**：所有有数据的次数全在 `partial_runs`，缺键原因逐条写在 `outliers`，各附 `raw_log_path`。
- 服务端 `perf_subscribe` 三时间戳只用作旁证（判服务端推没推），⛔ 没拿它去补客户端缺的键。
