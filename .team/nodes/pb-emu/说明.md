## 二、量测流程（照任务书，⛔ 只从 logcat 取数）

每次冷点开（脚本 `.team/nodes/pb-emu/tmp/coldopen.sh`）：
1. `adb shell am force-stop dev.agentmirror.app` → `adb logcat -c`

6. `adb logcat -d -s PerfTrace` 落 `.team/perf/raw/<夹具>-NN.log`

  ⛔ 没有坐标硬敲（坐标一律来自 uiautomator dump 的 `bounds` 中心点）。

## 三、实测到的事实（这就是判不出的原因）

30 份 raw 日志的事件链**完全一致**：

```
ev=tap → ev=route_enter → ev=subscribe_sent(emitted=1) → ev=geom_seed
→ ev=first_draw  emitted=0 reason=glyphs_zero glyphs=0
→ ev=layout_settled quiet_ms=500 last_reflow_src=subscribe
```

`first_frame_recv` 与 `snapshot_applied` **一次都没有出现**；`first_draw` 从来没有真发过。
`layout_settled` 三夹具都稳定在 ≈537 ms —— 正好是 `geom_seed(≈22ms) + 500ms 静默窗口`，
即它结算于 subscribe 那一次重排，**从来不是快照带来的重排**。原文样例（`raw/real_claude_idle-03.log`）：

```
08-22 03:57:04.607 D PerfTrace: open_id=1 ev=tap t=43107181
08-22 03:57:04.619 D PerfTrace: open_id=1 ev=route_enter t=43107193
08-22 03:57:04.627 D PerfTrace: open_id=1 ev=subscribe_sent t=43107201 emitted=1 reason=sent ready=1 conn=1 ok=1 take_before=0 replay=0 rows=41 cols=46
08-22 03:57:04.627 D PerfTrace: open_id=1 ev=geom_seed t=43107201 rows=41 cols=46
08-22 03:57:04.901 D PerfTrace: open_id=1 ev=first_draw t=43107475 emitted=0 reason=glyphs_zero glyphs=0
08-22 03:57:05.142 D PerfTrace: open_id=1 ev=layout_settled t=43107715 quiet_ms=500 last_reflow_src=subscribe rows=41 cols=46
```

**服务端那边说帧发了。** daemon 日志每条连接都有
`conn.snapshots_pushed=1 conn.snapshots_from_subscribe=1`，累计 `total.snapshots_from_subscribe=32`，
且每次订阅都有 `msg=perf_subscribe … done_ms-recv_ms ≈ 60–80ms ref="/tmp/e2e-pb-emu/tmux-501/default\x1f%N"`
（原文 `.team/perf/raw/diag/daemon-sendq-perfsubscribe-tail.log`）。
⇒ **服务端认为它按订阅推了快照，客户端侧没有任何一行说收到过。**

### 唯一一次八键齐的例外（很关键）

我在正式跑之前做过一次试跑（同一脚本、同一流程），那一次链是**完整**的：
```
tap 0 → route_enter 14 → subscribe_sent 22 (rows=40 cols=120) → geom_seed 23
→ first_frame_recv 268 (kind=snapshot bytes=1137) → snapshot_applied 282
→ first_draw 325 (glyphs=313) → layout_settled 784 (last_reflow_src=snapshot)
```
该次是**配对后的第一次打开**，订阅几何是 `40x120`（会话原生尺寸，app 还没量到自己的视口），
daemon 侧对应连接是全场唯一一条 `conn.snapshots_from_resize=1` 的连接
（全程 `total.snapshots_from_resize=1`）。此后每次订阅几何都是 `41x46`，只剩
`snapshots_from_subscribe`，**再没有一次收到帧**。
我另做了一次对照：先 `tmux resize-window -x 100 -y 30` 改夹具 pane 尺寸再冷点开
（`raw/diag/real_claude_idle-94.log`），链条**依旧缺帧**，说明不是简单的「几何相同就不下发」。

### 判不出什么（这两条我分不开，需要 leader 裁定归属）

1. **产品缺陷**：冷点开后终端 10 s 内一片空白（`glyphs=0`），服务端推的订阅快照客户端没消费；
2. **仪表盲区**：两个打点都在静默 return 的后面 ——
   `SessionViewModel.onBinary` 首行 `if (frame.ref != ref) return`（ref 不匹配则**一行都不打**），
   `PerfTrace.emitFirstFrameIfFirst` / `emitSnapshotIfFirst` 内 `opens[ref] ?: return`（同样不打）。
   ⇒ **光看导出的日志，分不出「帧没到」还是「帧到了但被 ref 守卫吞了」**——
   这正是 CLAUDE.md「诊断日志纪律」点名要防的那种沉默（该处缺 `emitted=0 reason=ref_mismatch` 一类的记录）。

我**没有**去改产品码验证哪一条成立（席位铁律：不改产品文件）。
建议下一步：给这两个 return 各补一行 `emitted=0 reason=`（带 `frame.ref` 与 `ref` 两边操作数），
重跑本流程即可一锤定音；这属于任务一仪表面的返修，不是我这格能自己决定的。
