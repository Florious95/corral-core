# 判据基底摘要：直通输入（每键直达 / 删除键直达 / 发送只提交）

> 本文档是**零知识对照席（r.control）唯一允许阅读的判据文档**。
> 你什么都不带地来，你读它，然后做定点变异，验判据会不会真的红。
> 本文档自洽、自足、无内部引用——所有判据都是可重跑命令 + 期望退出码，不靠任何外部文档。
> 起草：r.advisor（t.pt-oracle，2026-08-15）。

## 0. 你要验收的东西（一句话）

判据 = **一条命令**：`bash .team/nodes/passthrough-oracle/run-probe.sh`。

- 被测对象（直通输入实现）**对** → 命令退出码 **0**。
- 被测对象**坏**（退回任一旧行为）→ 命令退出码 **非 0**。
- 你能用「定点变异」验证它：把实现改坏一处，命令必须从 0 转非 0。转不动，判据无效。

## 1. 被测对象在哪个文件，判据怎么知道它「对」还是「坏」

直通输入横跨服务端与 App 两端：

| 端 | 文件 | 承担 |
|---|---|---|
| 服务端 | `server/internal/bridge/bridge.go` | tmux 注入原语（逐键直通 / 提交） |
| 服务端 | `server/internal/protocol/keys.go` | wire 键名（含删除键 backspace 映射） |
| App | `app/.../session/SessionViewModel.kt` | 发送动作（提交 / 整条注入） |
| App | `app/.../session/SessionScreen.kt` | 键盘输入绑定（直通 / 本地累积） |

判据命令对这 4 个文件做**结构检查**（grep 判据，见 §2 四条），全 PASS 退出 0，任一 FAIL
退出 1。纯静态、可重跑、秒级出结果：不启动模拟器、不碰生产 daemon、不连网络、不跑 gradle。

## 2. 判据规范：判什么、每个输入要产生什么输出

用户要的三条语义（2026-08-15 裁定，契约条目 059）：

> 1. **每个按键单独直通到 Agent CLI 输入框**（不再 App 本地累积整条草稿）
> 2. **虚拟键盘删除键同样直通**（删除键经服务端进 CLI，不经 App 本地消费）
> 3. **发送键只提交、不再整条注入**（草稿态归 CLI 输入框，发送键是唯一提交动作）

| ID | 判据 | 机械检查 | 必须输出 |
|---|---|---|---|
| S1 | **每键直通（服务端）**：存在「逐键注入且不回车」的原语 | bridge.go 里有一个函数内含 `send-keys -l`（逐键字面量注入）**且本函数不追加 Enter** | **PASS** |
| S2 | **删除键直通（服务端）**：存在 backspace wire 键映射 | keys.go 或 bridge.go 出现 `backspace` / `"bspace"` / `"bksp"`（键名 → tmux BSpace/Backspace） | **PASS** |
| S3 | **发送只提交（App）**：发送动作不再把整条草稿文本注入 | SessionViewModel 里**没有** `sendInput(ref, text)` 与 `textFieldValue.text` 整条注入 | **PASS** |
| S4 | **每键直通（App）**：键盘输入不再累积本地草稿 | SessionScreen 里**没有** `onValueChange` 写回 `textFieldValue`（本地累积） | **PASS** |

## 3. 判据自检（每一条）——如果被测对象是坏的，命令会不会仍返回 0？

- **把删除键退回本地消费**（删掉 backspace 映射）→ S2 FAIL → 命令转非 0 → 判据响。
- **把发送键改回整条注入**（sendDraft 重新 `sendInput(ref, text)`）→ S3 FAIL → 命令转非 0 → 判据响。
- **把键盘退回本地累积**（onValueChange 重新写 `textFieldValue`）→ S4 FAIL → 命令转非 0 → 判据响。
- **把逐键打字与提交绑回一个动作**（唯一 `send-keys -l` 路径又在同一函数里加 Enter）→ S1 FAIL → 命令转非 0 → 判据响。
- **grep 模式本身写错**（漏了该抓的结构）→ 对应判据对坏代码仍 PASS → 命令仍 0 → **判据无效，报告 refuses**。
  这就是你要用定点变异抓的东西。

## 4. 为什么判据这么写（不是随便抓四个字符串）

判据落在**行为结构三态**上，每条正好卡住一条用户语义：

1. **S1 抓「逐键与提交解耦」**：旧范式 `Inject()` 是「send-keys -l 注入 + 同函数 Enter 提交」
   一体——整条一次性注入被取代的正是这个「注入与提交绑一个动作」。实现后必须把逐键打字
   （`send-keys -l`，不回车）与提交（Enter）拆成两个原语，S1 才能 PASS。
2. **S2 抓「删除键可达远端」**：直通后删除键要经服务端送进 CLI，必须有 wire 键名 → tmux
   Backspace 的映射。当前 keys.go 闭集只有 esc/ctrl_c/tab/up/down/left/right，**没有 backspace**。
3. **S3 抓「发送只提交」**：草稿态归 CLI 输入框后，App 发送键不应再取 `textFieldValue.text`
   整条注入——那正是被取代的一次性注入在 App 侧的残余。
4. **S4 抓「键盘不本地累积」**：每个键直通后，键盘输入不应再写回 App 本地 `textFieldValue`
   当草稿累积——那会把直通降级回「本地输入 + 发送注入」。

判据只看结构在不在，不指定逐键直通用什么协议帧、删除键走 keys 还是 text 通道——实现自由
度留给开发席，判据只管「那条语义对应的结构有没有」。

## 5. 边界（判据命令不碰的东西）

- 只读 4 个被测文件做结构检查；不写任何文件（红测日志由 r.advisor 单独落盘）。
- 不启动模拟器、不跑 gradle/go build、不连服务端、不碰生产 daemon 与用户 tmux。
- 判据只验证「直通输入的三条语义对应的结构在不在」，不验证手感/输入法组合期（那两类
  属于用户手测与 leader 判断，不在本判据验收面）。

## 6. 你的任务：定点变异（验判据真的会红）

拿到本文档后，只读它 + 执行判据命令。步骤：

1. **基线**：跑 `bash .team/nodes/passthrough-oracle/run-probe.sh`，记录退出码。
   - 实现完成后 → 基线应 **0**（S1/S2/S3/S4 全 PASS）。
2. **变异**：在四个被测文件里**改坏一处**，制造本文档声称该被抓到的倒退。任一即可：
   - **删除键退回本地**：把 backspace 映射从 keys.go / bridge.go 删掉 → S2 必须 FAIL。
   - **发送退回整条注入**：把 `sendDraft()` 改成 `sendInput(ref, textFieldValue.text, …)`
     → S3 必须 FAIL。
   - **键盘退回本地累积**：把 `onValueChange` 改成 `{ viewModel.textFieldValue = it }`
     → S4 必须 FAIL。
   - **逐键与提交绑回**：在唯一的 `send-keys -l` 函数里同函数追加 Enter → S1 必须 FAIL。
   改一个字符/加一行即可。
3. **重跑**：`bash .team/nodes/passthrough-oracle/run-probe.sh`，记录变异后退出码。
   - 基线 0 → 变异必须转**非 0**；基线已非 0 → 变异必须**仍非 0 且理由成立**（FAIL 项变化）。
   - 判不出差异 ⇒ 判据无效，报告 **refuses**。
4. 把基线退出码 vs 变异后退出码、变异点写进 `.team/nodes/passthrough-control/mutation-report.md`。

**判据有效（supports）** ⇔ 基线绿且变异红，且你亲手能复现。判据无效（refuses）⇔ 判不出差异。
