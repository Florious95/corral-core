- 引擎：装机 `ledger-run`（`--drive` / `--drive --once` 两种入口都复现）

## 现象（一句话）

**返修回环的第一轮 rework 点了火，但第二轮压根派不出去**：判者判 `rework` → 引擎记下 route_hop →
把判者格转成 `blocked['await_reentry:t.app']` → 然后前沿为空、收工 `AwaitingHuman`，
`idle_reason=no_dispatch`。fix 格 `t.app` 始终停在 `succeeded`，**没有任何人把它复位**，
于是「等再入」永远等不到。

`.team/ledgers/perfbase-drive.log` 末段：

```
[ledger-run 2026-08-21T19:29:11Z] 状态路由回环 route-loop | task=t.rv.instr status=rework → t.app，源格 blocked 等再入
```

**不是一次性抖动**：随后单独跑 `--drive --once`，rc=3、写回为空、同样 AwaitingHuman：

```
{"ok":false,"revision_before":5,"revision_after":5,"wrote_back":[],
```

```
audit.route_hops = [
  {"from":"t.app","to":"t.rv.instr","status":"done","at_revision":3, ...},
  {"from":"t.rv.instr","to":"t.app","status":"rework","at_revision":4, ...}   ← 第二跳记下了
```

`--dry-run` 同一份账本：`frontier` 为空，`t.app` 不在 excluded 的任何一条里以「可动」出现。
把 `t.app.state` 手工改回 `planned` 之后，`--dry-run` 立刻给出 `frontier=["t.app"]` 并正常派单
——**唯一的差别就是这一个字段**。

## 复现

1. 造一条 `返修回环(review, fix, accept, exhausted, max_rounds=N)`（DSL 组件原样，不改）。
2. 让 fix 格正常 `report_result status=done` → 判据绿 → `state=succeeded`。
3. 让 review 格 `report_result status=rework`。
4. 观察：route_hop 记下，review 转 blocked，**fix 格仍是 succeeded**，驱动器收工 AwaitingHuman。

## 原因分析及其边界

- **能确定的**：路由层把 hop 记全了、也把源格标成了「等再入」，但**没有任何一方负责把
  目标 fix 格从终态复位成可派状态**。前沿计算只看 `state`，`succeeded` 一律不进前沿 ⇒ 死锁。
- **查不清的**：这到底是「引擎该在 route-loop 时复位目标格」的缺陷，还是「账本作者/leader
  被要求手工复位」的未文档化契约。我在 `ledger-run --help`、DSL v0.1.0 的 README 与
  `返修回环` 组件文档里**都没找到**关于「回环第二轮谁复位 fix 格」的任何说明；
  也没有 `--reset` / `--reenter` 之类的子命令。若是后者，请把它写进 README 的组件小节，
  因为 `返修回环` 的语义暗示它自己会转起来。
- ⛔ 我没有去读你们的引擎源码，也没有替你们做取证阶梯——这份报告只用我自己的运行日志与账本快照。
