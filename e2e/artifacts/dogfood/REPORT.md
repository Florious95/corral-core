### D-01 相机权限二次拒绝后，「授予相机权限」按钮点了毫无反应（静默死按钮）

- **现象**：首次拒绝相机权限后回到配对页，按钮外观仍是高亮可点的实心蓝；再点它，Android 已进入
  "永久拒绝"态不再弹系统弹窗，而 App 侧**没有任何可见反馈**——不跳系统设置、不提示"请到设置里开启"、
  无 toast、无文案变化。用户点了三次和点了一次的屏幕一模一样。
- **截图**：`03-camera-permission-denied.png`（拒绝后回到配对页）、`04-camera-permission-dead-button.png`
  （再次点击后，与 03 逐像素同构，仅状态栏时间差 1 分钟）
- **复现**：`pm clear dev.agentmirror.app` → 冷启 → 点「授予相机权限」→ 系统弹窗选 Don't allow →
  再点「授予相机权限」→ 观察屏幕无任何变化。
- **严重度**：**P1**（有手填兜底所以不阻断，但用户会卡在"这按钮坏了"的困惑里自救不能）
- **对照**：根 CLAUDE.md **工程常识红线第 5 条「失败可见」**——"用户任何动作在有限时间内必得可见结果
  （成功或带原因的失败），静默等待即缺陷"；兼 018-6 反馈。
- **建议方向**（只提不修）：二次拒绝后按钮改为"去系统设置开启相机权限"并跳 `ACTION_APPLICATION_DETAILS_SETTINGS`，
  或按钮置灰 + 说明文案。
- **状态**：待复验（本席复验后更新）

### D-03 上传文件名传的是 MediaStore 数字 ID，**扩展名全丢**，注入 CLI 的路径下游不可用

- **现象**：传图成功后注入输入框的主机路径是 `/tmp/dg1/up/upload-20260809T153141-1000000123`——
  **没有 `.png`/`.jpg` 后缀，也没有原文件名**，只有一串数字。主机侧落盘文件名同样如此
  （本席在 daemon 的 `-upload-dir` 核对：`find /tmp/dg1/up -type f` →
  `upload-20260809T153141-1000000123`，确凿）。
- **截图**：`15z-upload-zoom.png`（注入的路径全文）、`15a-after-pick-image.png`、`15b-path-sent.png`
- **复现**：会话页「+」→ 选一张 png → 观察输入框注入的路径 → 主机 `ls <upload-dir>` 对账。
- **严重度**：**P1**（不是观感问题：需求 003 这条链路的目的就是"把图交给 CLI 里的 Agent"，
  而 Agent 侧读图工具普遍按扩展名判类型，无后缀的文件会被当作未知二进制拒读——链路名义打通、
  实际用不了）
- **对照**：**003「附加输入能力：手机上传→主机落盘→文件路径注入 CLI」**；**011「multipart 上传→
  落盘→路径注入」同源一致**。
- **根因（本席只读代码定位，未改一字，供修复席直取）**：
  - **App 侧是根因** — `app/app/src/main/java/dev/agentmirror/app/session/SessionScreen.kt:421`
    `val name = (uri.lastPathSegment ?: "image")`。Photo Picker 返回的 content URI 形如
    `content://media/picker/0/…/media/1000000123`，其 `lastPathSegment` 就是 MediaStore 的数字 ID，
    天然不含文件名与扩展名。该名经 `HttpUrlConnectionUploader.kt:84` 原样填进 multipart 的
    `filename=`。
  - **服务端无份** — `server/internal/api/upload.go:163 sanitizeBaseName` 的字符白名单**保留 `.`**，
    落盘 `upload-<UTC时间戳>-<base>` 只是照单全收客户端给的名字。
  - 修复方向（只提不修）：App 侧改查 `MediaStore` 的 `DISPLAY_NAME`，或用
    `contentResolver.getType(uri)` 的 MIME 反查扩展名补齐。

### D-04（**已复验并改判**）终端滚动方向与全平台惯例**相反**：下拖看不了历史，纹丝不动且零提示

- **改判说明**：原判"scrollback 失效（P0 候选）"经本席真机复验**证伪**——滚动功能完全正常
  （历史能看、视口能锁、「↓ 回到底部」按钮能出能点能复位）。真问题是**手势方向反了**，
  它伪装成"滚动坏了"，把前席和本席**两个独立的"用户"先后骗过一次**——这恰恰是它作为
  可用性缺陷的最强证据。
- **现象**：终端里看更早历史的通用手势是**手指下拖**（内容跟手下移、露出上方历史），
  所有主流终端与列表都如此。本 App **反过来**：
  - 手指**下拖**（`swipe 540 700 → 540 1500`，800ms，×3）：画面 **MD5 完全相同**
    （`20a` vs `20b` 均为 `d6e18f3b…`），**一行没动，且无任何提示告诉用户"已在底部"**；
  - 手指**上滑**（`swipe 540 1800 → 540 400`，1200ms）：**才**滚到历史（视口从行 400 跳到
    行 135–221，再滑到行 1–77），「↓ 回到底部」按钮同时出现。
- **截图**：`20a-scroll-before.png`（底部，无按钮）｜`20b-scroll-drag-down.png`（下拖后，与 20a
  逐字节同图）｜`20c-scroll-drag-up.png`（上滑后 → 行 135–221 + 「↓ 回到底部」现身）｜
  `20d-scroll-bigdrag.png`（继续上滑 → 行 1–77，触达 scrollback 顶）｜`20e-back-to-bottom.png`
  （点按钮 → 恢复跟随，按钮消失）
- **复现**：会话内 `for i in $(seq 1 400); do echo "行 $i …"; done` → 在终端区**下拖** → 画面不动；
  改为**上滑** → 才看到历史。
- **严重度**：**P1**（功能在、方向反。用户按直觉下拖 → 零反馈 → 合理推断"滚动坏了"而放弃；
  长输出的历史事实上被藏了起来）
- **对照**：**006「scrollback 本地化、锁定视口 + 回到底部按钮」**（机制达成，交互方向不符）；
  **红线 5「失败可见」**（下拖到底不动时无任何边界反馈——连 overscroll 回弹都没有）。
- **根因（只读定位）**：`TermSurfaceView.kt:96-103`
  `deltaLines = (dy / lineHeightPx).roundToInt()` 后直接 `onScrollBy(deltaLines)`。
  Android `GestureDetector.onScroll` 的 `distanceY = 上次事件Y − 当前事件Y`，故**手指上滑时
  `dy > 0`**；而 `TermViewPresenter.kt:104` 约定"正 `deltaLines` = 向上滚看更早历史"
  （`next = current − deltaLines`）。两者一串，就成了"上滑看历史"。
  代码注释 `// 向上滚 = dy<0` **写反了符号**，正是这个反向的源头。
  修复方向（只提不修）：`onScrollBy(-deltaLines)`，或把注释与约定统一后调正一处符号。
- **附带 PASS 项（本次复验一并确认）**：
  - 「↓ 回到底部」按钮**存在、正确按需显隐、点击恢复跟随**（`20c/20d` 现身 → `20e` 点后节点数归 0）
    → **前席"疑似无回到底部按钮"的记录本席正式撤销**，该按钮功能完好，此前不出现只是因为
    视口从未离开底部。
  - 视口锁定、触达 scrollback 顶（行 1）、历史内容完整无损 → **E2 的机制面 PASS**。
- **复验前的三个假设，事后核销**（留痕：我当初列了"①手法假阳性 ②`deltaLines` 恒为 0
  ③Compose 截获触摸"三种可能，**真相是三个都不是**——是符号方向反了。
  记这一笔是想说明：**根因假设清单开得再齐，也可能整份落空，最终仍要靠真机双向对照定案**）。

### ~~D-05 触控目标远低于 48dp~~ —— **本席误判，已撤销（不计入缺陷）**

> **撤销结论**：真机 `uiautomator dump` 权威量测证明**触控目标达标**。实测密度 420dpi ⇒ 48dp = 126px；
> 键条每一键的**可点击节点**（`clickable="true"` 的 Surface 容器）实测：
> `Esc [11,2022][137,2148]` = **126×126px = 48.0×48.0dp**，`Ctrl-C` 161×126，`Tab`/`↑`/`↓`/`←`/`→`
> 均为 126×126；「+」`[22,2186][148,2312]` = 126×126；「发送」152×126。**全部恰好达到 48dp。**
>
> **我错在哪（两处，都记下来当教训）**：
> 1. **量错了对象**。我按截图目测量的是**视觉色块**（102×69px ≈ 39×26dp），而 Android 的触控目标
>    指的是**可点击热区**。二者在 M3 里本就不同：Compose Material3 的
>    `LocalMinimumInteractiveComponentSize`（默认 48dp）会把任何带 `onClick` 的组件的**热区**
>    撑到 48dp，同时**允许视觉尺寸更紧凑**。视觉块小 ≠ 点不准。
> 2. **读码读反了**。我先前断言"M3 的 `Surface(onClick)` 不像 `Button`/`IconButton` 那样自带 48dp
>    最小触控目标"——**这句是错的**，Compose M3 对所有带 `onClick` 的组件一律强制最小交互尺寸。
>    `SessionScreen.kt:310-327` 没写 `sizeIn` 是**正确的**，不是遗漏。
>
> **量触控目标的正确姿势（供后续席位）**：`uiautomator dump` 后取 `clickable="true"` 的节点 bounds，
> **不要**量截图上的视觉色块，也**不要**量挂着 `content-desc` 的内层 Text 节点
> （本例中内层 Text 是 102×69，父级可点容器才是 126×126——差一层就得出相反结论）。

### D-06（**降级为观察项**）「空闲」与「未知」两态色相完全同构（灰点+灰底）

- **现象**：工作区列表徽章里，`空闲` 与 `未知` 用**同一个灰圆点 + 同一个灰底胶囊**，只有中文字不同。
  `工作中`（蓝）与 `需人`（红）区分良好。
- **截图**：`07b-workspace-list.png`（同屏可见 `空闲`/`工作中`/`未知`/`需人` 四态并列对照）
- **本席自我修正**：读码后发现这是**有意设计而非疏漏**——`StateBadge.kt:61` 注释原文
  "色弱可辨不依赖色相：五态文案各异 + contentDescription（017 R-7），深浅双套各自配色"。
  即该组件刻意选择"**靠文案而非色相**"承载可辨性，`空闲`/`未知` 文案确实各异且都带

### D-16 手机一连上，主机 daemon 就持续吃 **14.8% CPU**（27 pane 实测，用户零操作）

- **现象**：同一个 daemon、同一批 tmux 会话，**唯一变量是"有没有一个客户端连着"**：

  | # | 状态 | CPU | 采样（最终样本，非中间快照） |
  |---|---|---|---|
  | ① | **零客户端**（空闲） | **0.0%** | **30 点 / 360 秒**，CPU time 恒为 `2:12.97`，**一秒未增**（`/tmp/dg1/d1-samples.txt`） |
  | ② | **一个客户端在线，用户零操作** | **14.8%** | **20 点 / 171 秒**（00:20:45 `5:09.57` → 00:23:36 `5:34.89`），CPU 消耗 25.32s，逐点线性极稳（`/tmp/dg1/d16-samples.txt`） |
  | ③ | **客户端断开后**（同一 daemon 进程，未重启） | **0.0%** | 20 秒采样，CPU 消耗 `0.00s`。客户端一走**立刻**回落 |

  **③ 是事后补到的第三个数据点，它把因果关系钉死了**：同一个 daemon 进程、同一批 tmux 会话，
  开销随客户端**接入而起、断开而灭**，且回落是即时的。这排除了"daemon 自身随运行时间劣化"
  或"宿主其他因素"的解释——**开销完全由"有客户端在线"驱动**。
  （③ 的取得纯属顺手：并行席 w-ts-verify2 为跑自己的 e2e 对 App 做了 `pm clear`，
  我从宿主侧 `lsof` 看到 19983 的连接消失，立即补测了一轮，**全程未碰设备**。）

  手机放在一边、用户一根手指都没动，主机上这个 sidecar 就一直烧掉约 1/7 个核。

- **⚠ 测量精度的诚实交代（请按此口径判读，勿放大）**：14.8% 那一端，客户端的确切状态是
  **「已连接 **且** 停在一个会话页（即有 1 个活跃订阅）」**——这是我最后一次操作后 App 停留的位置。
  **我没有单独测到「已连接但只在列表页、零订阅」这个中间态**（需要操作设备退回列表页，
  而设备当时已让给 TS 席）。因此严格口径是：
  - 已证实：**零连接 = 0.0%** ↔ **连接 + 1 个订阅 + 用户零操作 = 14.8%**；
  - 未证实：这 14.8% 里，全量 listing 轮询与单会话订阅推流**各占多少**。
  - 但根因分析可给出方向：**每 2 秒对全部 27 个 pane 重采状态的那部分开销与订阅数无关**
    （listing 是全局的），所以即便退到列表页，这部分也跑不掉；订阅推流只额外涉及 1 个 pane。
    **故"主要成本在全量轮询"是合理推断，但未经独立测量，不作为结论。**
  - **补测方法（留给后续席位，很便宜）**：App 退回列表页 → 采样 60 秒 → 再进会话页 → 采样 60 秒，
    两个数一减即得拆分。
- **复现**：起 daemon → 不连任何客户端，`ps -o time= -p <pid>` 采样若干分钟 → CPU time 不动；
  用 App 配对连上 → 什么都不做 → 再采样 → 每 9 秒稳定消耗约 1.34 秒 CPU。
- **根因（只读定位，两个常量一撞就是它）**：
  - `server/internal/api/options.go:22` `defaultListInterval = 2 * time.Second`——**每 2 秒**一次全量 listing；
  - `server/internal/api/state_wiring.go:64` `defaultStateRefreshTTL = 1 * time.Second`——单 pane 状态缓存
    **只活 1 秒**，比轮询间隔还短，**每一轮必然全部过期、全部重采**；
  - 每次重采走 `server/internal/api/state_wiring.go:190 refresh()` → **`state_wiring.go:264
    capturePaneOutput()`**，其中 `exec.CommandContext(ctx, "tmux", "-S", …, "capture-pane", …)`
    **派生一个进程**；且据 `state_wiring.go:76-78` 注释，一次 refresh 还包含
    **Identify 自身 500ms 的 `ps` 预算**——**即单次采样是 `ps` + `capture-pane` 两次进程派生**，
    比单看 capture-pane 更贵。
  - 本环境 daemon 枚举到 **27 个 pane**（见下方"数字的代表性"），⇒ 约 13.5 次 refresh／秒
    × 每次 2 个子进程。与实测 14.8% 量级相符。
  - **（本席原稿两处错误，已按裁定席核正并保留痕迹）**：
    ① 原引 `bridge.go:51` 作为采样入口——**引错了**，那是**会话订阅**的快照/滚动路径，
    与 listing 的状态采样是两条路；正确入口是上面的 `state_wiring.go:264`。
    ② 原写 `defaultStateSamplingBudget = 3s` 是"频率限流、预算(3s)>间隔(2s)所以没限住"——
    **论证是错的，已删除**。它实为 `state_wiring.go:194 context.WithTimeout` 的
    **单次刷新超时上界**（超时即降级 unknown，008），与频率无关。
    实现里真正的限流是 `p.maxConc` 的**并发上限**（`state_wiring.go:191-192`），这一点应予公允记述。
- **严重度**：**P1**。三条理由：
  1. **这是主用场景不是边缘场景**。本产品的命题就是"手机常连主机"（001/003/004），
     "连着但没在操作"是它一天里 99% 的时间形态。持续 14.8% CPU 在 MacBook 上意味着风扇转、
     续航掉——用户会因为"一开这个东西电脑就烫"而卸载。
  2. **开销随舰队规模增长**。这一点**依据的是代码形状而非实测**：`refresh` 对**每个** pane 各跑一次
     `ps` + `capture-pane`，故成本随 pane 数增长（受 `maxConc` 并发上限调节，非严格线性）。
     001 的产品命题明写舰队规模、scenario D2 设想"几十目录几百会话"，**该量级下的开销未被测量**
     ——本席只实测了 27 pane 这一个点，**"200 pane 吃满一核"是代码形状推算，不是实测结论，
     不得作为定量依据**（规模压测归 test-fleet-scale）。
  3. **红线 1 的精神正指向它**。红线 1 原文点名"无固定频率的子进程派生"——这里正是
     **每 2 秒一次、数量等于会话数的固定频率派生**。
- **对照**：根 CLAUDE.md **红线 1「静默经济」**（字面只约束"空闲态"，故**本条不判红线 1 违规**——
  空闲态本 daemon 表现优异、是 PASS 的；本条判的是红线 1 未覆盖但同源的**在线态能耗**）；
  兼 004「电量策略」。
- **数字的代表性（重要限定，如实交代）**：这 14.8% 对应的 27 个 pane，**不是我造的测试数据，
  就是用户这台机器上真实存在的 tmux 舰队**（`07b` 可见：多agent协作 7 会话、冒险岛怀旧服自动化
  5 会话、远程Agent安卓 4 会话、ta-e2e-* 4 会话…… 加本席隔离的 3 个）。
  换言之**这个数字直接就是用户真机的实际开销**，不需要打折看。
  反过来说，若某用户只开 2–3 个会话，开销会显著低于此值——严重度请按各自舰队规模判读。
