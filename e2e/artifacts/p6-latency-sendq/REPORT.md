## 假说（w-dev-repaint）

`sendMirror` 非阻塞发送，队列（容量256）满时丢弃 delta（004 契约：丢数据靠下一次快照对账）。
推论：TS 慢链路 → 队列满 → 丢 delta → 补发快照 → 客户端 `replaySnapshot` 整屏重建 = 用户说的
「从上往下刷」。局域网队列从不满 → 不丢 → 流畅。

## 关键方法论过程（诚实记录：代理经过三次迭代才排除工具误差）

**第一版**（`reader.read(65536)` 无限制读 + 写前 sleep）：`deltas_dropped=0`——但这个结果不可信，
因为这版代理会把上游（daemon）socket 瞬间读空，daemon 的写永远针对代理的 OS 级 TCP 接收缓冲
瞬间成功，无论代理在转发前 sleep 多久，daemon 侧都感受不到背压。**这不是"没丢"的证据，是工具
没有制造背压能力的证据。**

**第二版修复尝试**（sleep 挪到读之前）：破坏了 RTT 语义——sleep 从"数据到达后才开始计时"变成
"每次循环迭代开始就计时"，导致两跳延迟发生重叠而非顺序叠加，自证从预期 ~400ms 掉到 ~202ms
（已用 echo server 实测复现）。回退。

**第三版**（保留写前 sleep 保证 RTT 正确，改成每次读最多 4096 字节）：制造了真实带宽节流
（~20KB/s），自证：64KB 突发的往返从瞬时变成 ~3.4s，量级吻合节流预期。RTT 自证仍为 ~404ms
（200ms×2，正确）。但用这版测出的还是 `deltas_dropped=0, queue_peak=1`。

**第四版**（在第三版基础上再加：daemon 侧 socket 的 `SO_RCVBUF` 收缩到 2048 字节）：
`setsockopt`/`getsockopt` 验证 2048 确实生效（未被 OS 下限吃掉）。RTT 自证仍 ~404ms。
**这版测出的还是 `deltas_dropped=0, queue_peak=1`。**

## 结论：假说未被证伪，但被排除的是"简单场景能触发"

四版代理（从"只加延迟"到"真实带宽节流+收缩接收缓冲"）ADD 递增的背压压力，**单条 80 行、
约 7-8 秒生成完的 AI 回复，从未让服务端发送队列堆积超过 1**（`frames_sent` 294 次写入，跨度
~8秒，平均节奏远低于任何一版代理的节流上限）。

**物理解释**：LLM 流式输出本身就是被生成速度限速的——80 行内容摊在 7-8 秒里逐 token/逐块吐出，
折算下来的数据密度（很粗略：几百字节/秒量级）远低于我模拟的"慢网络"节流上限（~20KB/s）。
**单条消息回复的数据节奏，天然追不上任何合理的网络慢速上限，队列自然不会堆。**

这不代表 sendq 丢弃假说是错的——它可能仍是根因，只是需要**更大的突发**（比如全量 scrollback
快照重放、短时间内多次 resize/reconnect 叠加、或真的很差的网络条件如持续高丢包触发大量重传）
才会触发，不是"发一条长回复"这种单点场景就能复现的。

**建议下一步**：不要再用"发一条消息"做触发场景。改用会产生更大瞬时突发的动作——比如断线重连
后的**全量快照重放**（scrollback 几千行一次性推送），或者在注延迟环境里做几次快速的
resize/切前后台，观察这些**批量/瞬时**场景下 `queue_peak`/`deltas_dropped` 是否真的能顶到非零。
