## 一、现象拆解成可判定部分

用户原话：「我发消息**有概率从上部往下刷新**，**导致底部的最新消息看不到**」

### 前半句「从上部往下刷新」= 可观测量
- 帧差分形态：SCROLL_DOWN / FULL_REFLOW / 逐行重画？
- 重绘次数：一次响应内整屏重绘多少次（vs 脏行级几次）？
- 视觉节奏：是「连续滚动」还是「分块闪烁」？（TS 下分片间隔数百 ms → 看得见每块）

### 后半句「看不到最新消息」= 可观测量
- 内容底边位置 vs 视口底边：最新行是否在视口内？
- 视口跟随态：跟底是否保持？（稳态 + 瞬时真实尺寸**都已排除**）

### 这两半是不是同一个原因？
- **跟底稳态/瞬时都已排除**（探针逐帧跟底正确）→ 后半句**不是**「视口没跟底」。
- 剩余解释候选：
  - **渲染层滚动错位**：滚动整段标脏 → 重画，但画的是「滚动后的新行布局」，若脏区/窗口换算
    有 off-by-one，用户看到的窗口顶部/底部错位 → 最新行可能在视口下方（画到窗口外）。
  - **「有概率」= 内容长度**：回复短、屏幕没写满 → 不滚动 → 正常；回复长、写满 → 每行都滚 →
    出问题。**不是随机，是长度依赖。**（这是滚动假说 vs 其它假说的关键判别）

### 判别树：4 数回来时怎么用

- **4 数①（整屏位移次数 ≈ 回复行数）**：证实 7（滚动是机制）。
- **4 数②（每次重画行数 ≈ 满屏）**：证实 7 的代价形态（每滚一行整段重画）。
- **4 数③（每次重绘耗时）**：小 → 「慢」不是主因（帧多才是），滚动仍成立但感知是「频繁小重绘」；大（数百 ms）→ 「慢」是主因，blit 才值得。
- **4 数④（teammate 对照组）**：teammate 不滚/少滚 → 滚动是用户不对称的原因 → **主线索坐实**；teammate 同样滚几十次 → **滚动不是原因，假说要重想**（那 8 或 10 上升）。
