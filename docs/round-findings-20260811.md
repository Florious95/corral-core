## P-1 前台服务从未被启动 —— **判定：缺陷，未兑现已裁需求**

**事实**：`MirrorForegroundService` 在 `AndroidManifest.xml` 里声明了，但全仓库
**没有任何 `startService` / `startForegroundService` / `stopService` 调用点**。
它自己的 KDoc（commit `105a2fe`）写着"死件家族第六例，接线留待后案"。
真实接线是：`ConnectionManager` 由 `startPersistentConnection`（`MainActivity.onCreate`）
或 `SessionRoute.createSessionViewModel` 创建，时钟泵由**在屏组合的 `LaunchedEffect`** 驱动，
fg-service 的 `pumpRunnable` 从未运行。

**需求依据（已裁，非待定）**：
- `011 技术路线裁定` — 「推送/后台：Android **前台服务 + 常驻连接**，不依赖 FCM/Google 服务」，
  依据 010（验收只含安卓）+ 004（前台服务路线已裁）+ 008（开源自托管友好）。
- `004 后台策略` — 「Android 额外提供前台服务选项（通知栏常驻），成本低收益实」。

**结论**：这不是"要不要做"的选择题，需求已裁定要做。当前状态是**未兑现**，按缺陷处置，
已立任务 `feat-fg-service-wiring`。

**注意 004 的边界不要读错**：004 的主张是「不保活、客户端无状态、被杀即无所谓」，
那是针对 **iOS 玄学保活** 的架构原则，不等于「安卓也不要前台服务」——
同一条 004 明确把前台服务列为安卓侧应提供的选项，011 更把它收口为既定技术路线。
接线时须守住 004 的架构底线：**前台服务是体验增强，不得成为正确性依赖**——
即便服务被杀，冷启动 → 重连 → 首屏快照仍须在 1 秒内恢复原状。

**关联**：`BACKLOG-20260810.md` §4 真机验收 8 项里的「进程被杀与锁屏重连」，
在接线完成前不具备通过条件。

## P-2 配对 token 明文存储 —— **判定：当期不做，需求基未要求**

**事实**：`.pairing` 的 `manualToken` 注释原挂着"存储加密 TODO"，而全仓库无任何加密实现，
token 明文落盘。（本轮新增形态 ⑩「幽灵 TODO」的实例，注释已按实现改写，不再谎称有在途计划。）

**撞库结果**：
- 需求基通篇**无落盘加密要求**（grep `token|密钥|加密|存储` 全量条目）。
- `017 R-4 token 轮换` 当期裁定为「**文档化**『删 token 文件重启即全量吊销』；版本化多 token **后置**」——
  即需求基把 token 当作**可删除的文件**对待，未涉 at-rest 加密。
- 协议 §9 的 token 契约边界是**不上屏明文、不落日志、不入截图、QR 是唯一合法出口**，不含落盘加密。
- `INDEX.md` 未决议题表：「暂无挡道议题」。

**结论**：现状**不违反任何已裁契约**。当期不做。
若要做（Android Keystore / `EncryptedSharedPreferences`），须先作为新条目进需求基、
在 `REVISIONS.md` 登记，不得由施工席在实现里夹带——那会让需求基与代码脱节，
正是本轮在治的病。

## P-3 终端渲染丢弃脏区，每帧整窗重绘 —— **判定：需求只管结果，先量测再定**

**事实**：终端内核 `TerminalEmulator` 确实在算脏区并通过 `DamageListener` 回调，
`TermViewPresenter` 也确实接管并换算缓存了——但渲染层**把它扔了**：
`doFrame` 里 `while (p.takeDamage().isNotEmpty()) Unit` 排空即弃，然后 `invalidate()` 整帧全窗口重绘。
同一句假话在两个包散了 **5 处副本**（`TermSurfaceView` 类 KDoc、`TermViewPresenter` init、
`pendingDamage`、`takeDamage`、`DamageListener`），互相印证成"已做增量刷新"的假象，本轮已全部改实。

**需求依据**：`006 秒开与本地滚动` 要求的是「本地化后滚动即原生列表滚动——**60fps**、惯性、离线可滚」。
**需求约束的是结果（60fps），未规定实现手段（脏区增量 vs 整帧重绘）。**

**结论**：不需要裁定，判据需求已给。
执行顺序：先跑 `docs/perf-scenarios.md` 的 **F1 终端滚动帧率**量测 →
达标则整帧重绘可接受，不动；不达标则接脏区做局部重绘（数据现成，是明确的性能余量）。
量测前不预先施工，避免为未证实的瓶颈做优化。

## 流程教训（记档防重犯）
