## 背景与目标

fix-input-send-fullrepaint 需要「整屏被重写时，用户不看到写了一半的中间态，落定后一次性呈现」。
当前实现用**结构性判据**（自清屏起每一行都被重写 → 落定）+ 硬上界兜底（2000ms）。

**`clear` 场景缺陷（实测 2050ms）**：用户敲 `clear` → 清屏 + 提示符只写第 1 行 + 其余行本就该空、
永不重写 → 结构性判据永不满足 → 直到硬上界（2000ms）才呈现 → 用户看到旧内容残留 2 秒。
`clear && echo hi`、TUI 退出回干净 shell、`tmux clear-history` 同形。

**核心张力**（leader 明确不可拍脑袋）：
- 静默窗口太短 → 高 RTT 下分片间隔超它 → 抑制提前结束 → 中间态露出；
- 静默窗口太长 → `clear` 场景等太久。

## 分级判据设计（三层，每级可观测 + 测试锚定）

### 第 1 层 · 结构性落定（整屏 recap 优先）
自整屏清屏（ED2/3 脏区覆盖全窗）起，累积重写覆盖的行（bitmask），**每一行都被重写** → 落定。
- 覆盖：整屏 recap（CLI 自上而下逐行重写**填满屏幕**）。
- 已实现：`rewriteDirtyRows` bitmask + 覆盖满判定。
- **第 1 层的结构性判据本身是不完备的**：它假设「重写会填满屏幕」——`clear`（只写顶部）永不满足
  正是这不完备的体现，不是「分工」。**第 2 层不是第 1 层的补充分工，是它的兜底。**
  区别很重要：写成「分工」，后来人不会改进第 1 层；写成「不完备 + 兜底」，后来人知道这里有债
  （真正的完备解可能是 2026 标准，见「两条路的关系」）。

### 第 2 层 · 落定判据（clear 等短写入场景）★ 本设计必须实现
**主判据：光标下探判别（时间无关，leader msg_23a141553408 方向二，已探针实测）**。

`ScreenSnapshot` 已带 cursorX/cursorY/cursorVisible（内核游标位置可用，客户端暂未消费）。探针实测
（20×12 屏）光标结束位置：

| 场景 | 结束光标 | 判读 |
|---|---|---|
| clear（ED2 + 提示符行 0） | (2, **0**) | 停在顶部 |
| recap 完整（清屏+重写 0..11） | (6, **11**) | 落到底部 |
| recap 部分（清屏+只写 0..5，clear 类） | (5, **5**) | 停在写到的行 |

**判据变体（依赖「重写过程中光标是否下探」，不依赖最终位置）**：
- 重写期间**光标 Y 持续下探**（随脏行覆盖增长而下移）→ 整屏 recap 进行中 → 继续抑制；
- 重写期间**光标 Y 停在顶部/回顶部**（不清除下探）→ short-write（clear 类）→ 落定呈现。

**为何时间无关**：clear 后光标停提示符（顶部）不动；recap 光标随重写逐行下移。这个判别是
结构性的（看光标动没动），不依赖「静默了多久」——天然规避「调一个数字两头不能同时满足」的张力。

**时间兜底仍保留（第 3 层硬上界）**：即使光标判据有盲区（如 mid-screen 部分 recap），
2000ms 硬上界保证不冻屏。

**阈值校准（第 3 层的数字，仍待实测）**：硬上界 2000ms 的合理性、以及光标判据失效时的时间兜底
阈值，仍需 w-base-v2 注延迟的分片间隔分布（0ms/400ms RTT recap 相邻到达间隔 p50/p90/p99/max）。
**没有这组数字前，硬上界只是个猜的数**——但它是「最后一次兜底」的猜，不是主判据的猜。

### 第 3 层 · 硬上界兜底（畸形输入保险）
重写期间数据静默超过 **2000ms** → 无条件呈现当前状态。
- 覆盖：重写中断/卡住/判据漏洞。
- 已实现：`rewriteFallbackCount` 可观测 + 2000ms。
- 量级依据（已有）：2× 局域网 recap 时长（1s）留余量；按「距上次收到数据」计，非从重写开始。

## `clear` 场景的判据归属

`clear` 落在**第 2 层（静默落定）**：清屏 + 提示符 1 行 + 流静默（短阈值）→ 呈现清屏结果（<500ms 目标）。
`TermRewriteClearScenarioTest` 锚定第 2 层，是永久门（现有实现红：2050ms 靠第 3 层）。

## 产品边界约束（tmux 层修法的红线）

**若 2026 路线走通**，落地需让 tmux 向内声明 Sync 能力（`terminal-overrides` 是 tmux server 级选项）。
这会影响该 tmux server 上**用户自己的其他 pane**，不只是我们管的会话。

**约束：修法不能是「偷偷改用户的 tmux 配置」。** 这是产品边界，需用户裁定。可选更干净的落点：
- 只对 daemon **自己创建**的会话设置，不碰用户既有会话；
- 由 daemon 在 spawn CLI 时通过环境变量/TERM 影响（如 pane 的 TERM 声明 Sync），而不改 tmux server 选项。

## 范围收缩（leader msg_e576b9396c78，重要结论）

**当前实现对 recap 是正确的，坏的只有 clear。** 探针实测：recap 开头（清屏 + 写第一行 + 停顿 700ms）
期间取帧 → 抑制保持（画面停旧内容），**不露空白**。即：现有抑制机制对整屏重写完全正确，
唯一缺陷是 `clear` 卡在 2000ms 硬上界。**这缩小了问题范围**——不必重做抑制机制，只要给 clear
加一条出路（次级静默判据）。

## 光标判据：为什么不成立（leader msg_e576b9396c78 要求保留，供后来人省一轮）

曾经的方向（leader msg_23a141553408 方向二 + msg_5043d31800e8 两状态）：
- 探针实测光标位置可区分 clear（停顶 (2,0)）与完整 recap（落底 (6,11)）。
- **但不成立**：recap **开头**光标就在行 0（写第一行），与 clear 提示符**同形**。任何
  「光标在不在顶部」的瞬时判据都会把 recap 开头误判为 clear；「有没有下探过」需要观察窗，
  观察窗又是时间 → 回到需要校准的时延。**光标不是免费的确定性信号。**

## 唯一未决：recap 内部最大分片间隔（决定简单方案是否够用）

次级静默判据 X 必须 > **整屏 recap 内部，相邻分片到达的最大间隔**（注意：**不是**两波之间 765ms
那个数——那是回显波与响应波的间隔，中间隔着 CLI 处理消息的时间，不是 recap 内部分片间隔）。
- 若间隔 A 很小（几十 ms，CLI 连续写、网络成批送）→ X 取三四百 ms 同时安全又够快，**张力不存在，
  简单方案最优，光标判据确实不需要**；
- 若间隔 A 很大（几百 ms+）→ X 要取大、clear 变慢，那时才需要更聪明判据。

**等 w-base-v2 测间隔 A（0ms/400ms RTT 各一组，区分 recap 内部分片 vs 波与波之间）之前，
不定方案、不实现**（leader msg_e576b9396c78 裁定）。

## 结论：抑制机制已回退（2026-08-13 leader msg_2ca924e58b58）

**回退**：整屏重写抑制（recap 中间态）从 `takeFrameRepaint` 移除，退化回 `takeDamage` 直通。
脏行渲染（半一）保留；`clear` 测试改造成回归门（断言 clear 立即呈现，防将来再被抑制弄慢）。

**为什么回退——三次实测均为零收益**：
1. 对「发消息整屏刷」：ED2/ED3 次数 = 0（w-base-v2 逐块验证 59 块响应零命中）→ 机制从不触发。
2. 对「捏合闪烁」：`replaySnapshot` 本身原子（reset + feed + 一次 flushDamage），一个完整快照
   只渲染一帧 → 没有中间态可抑制。
3. 协议边界：快照是恰好一个 WS 二进制帧，不拆分 → 落定精确，但也说明客户端无中间态问题。
代价：用户敲 `clear` 等 2050ms（我们主动引入的净负面）。

**写进文档的形状（不是失败，是一次被拦住的浪费）**：
> 我们先认定了一个机制（整屏重写抑制），再反复为它寻找适用的缺陷。三次都是先有机制、
> 后找病人。正确顺序是先有病人（可复现的失败态数字）、再找机制。它没有上线，是因为
> 每一次「它对哪条缺陷有用」都被要求拿实测回答，而三次实测都是零收益。

**遗留真实方向**（见 docs/ 其他记录）：捏合闪烁疑为「客户端本地 resize 后，在途旧几何 delta
喂进新几何网格」的协议时序错位（非渲染中间态）；发消息滚动为「scrollUp 整段标脏 + 无 blit」。
这两个是「先有病人（可复现数字）、再找机制」的正确路径。
