## 背景与目标

fix-input-send-fullrepaint 需要「整屏被重写时，用户不看到写了一半的中间态，落定后一次性呈现」。
当前实现用**结构性判据**（自清屏起每一行都被重写 → 落定）+ 硬上界兜底（2000ms）。

**`clear` 场景缺陷（实测 2050ms）**：用户敲 `clear` → 清屏 + 提示符只写第 1 行 + 其余行本就该空、
永不重写 → 结构性判据永不满足 → 直到硬上界（2000ms）才呈现 → 用户看到旧内容残留 2 秒。
`clear && echo hi`、TUI 退出回干净 shell、`tmux clear-history` 同形。

**核心张力**（leader 明确不可拍脑袋）：
- 静默窗口太短 → 高 RTT 下分片间隔超它 → 抑制提前结束 → 中间态露出；
- 静默窗口太长 → `clear` 场景等太久。

## 两条路的关系（互补，不是二选一）

| 路线 | 管什么 | 落点 | 状态 |
|---|---|---|---|
| **2026 同步输出**（Synchronized Output） | **CLI 主动声明**的整屏重写（发 `ESC[?2026h...l` 包裹） | 内核接 2026h/l 抑制；前提是 tmux 向内声明 Sync 能力（见下「产品边界」） | 待 w-base-v2 真终端验证 override 后 Claude Code 发不发 |
| **分级判据**（本设计） | **没有声明但确实在整屏重写**（大部分 CLI 不发 2026）+ **`clear` 这种清屏后不填满** | 客户端内核（presenter 落定判据） | **无论 2026 是否走通，本设计都必须实现——至少解决 `clear`** |

**关键**：2026 解决不了 `clear`（Claude Code 为 `clear` 也不会发同步标记）。所以分级判据不是备胎，
它至少要解决 `clear` 那条；2026 走通了也只覆盖「声明了同步」的子集。

## 分级判据设计（三层，每级可观测 + 测试锚定）

### 第 1 层 · 结构性落定（整屏 recap 优先）
自整屏清屏（ED2/3 脏区覆盖全窗）起，累积重写覆盖的行（bitmask），**每一行都被重写** → 落定。
- 覆盖：整屏 recap（CLI 自上而下逐行重写**填满屏幕**）。
- 已实现：`rewriteDirtyRows` bitmask + 覆盖满判定。
- **第 1 层的结构性判据本身是不完备的**：它假设「重写会填满屏幕」——`clear`（只写顶部）永不满足
  正是这不完备的体现，不是「分工」。**第 2 层不是第 1 层的补充分工，是它的兜底。**
  区别很重要：写成「分工」，后来人不会改进第 1 层；写成「不完备 + 兜底」，后来人知道这里有债
  （真正的完备解可能是 2026 标准，见「两条路的关系」）。

### 第 2 层 · 静默落定（clear 等短写入场景）★ 本设计必须实现
重写进行中，数据静默超过**短阈值** → 判定「已写完」，呈现当前状态。

**阈值必须从注延迟实测的分片间隔分布取，不能从吞吐推理取（leader msg_50cba47b01e8）**：
- 「WS 帧流式背靠背、分片间隔远小于 RTT」的推理在**局域网**成立，在**用户主场景 Tailscale 不成立**。
- w-base-v2 实测：注 400ms RTT 时两波更新之间静默 **765ms** ——真实链路静默间隔可到 700ms 以上。
- **若阈值取 200ms，TS 下会在整屏 recap 中途就判定「写完了」、把中间态放出来**——抑制在用户主场景
  失效，而在测试局域网下看起来正常。这正是本工程明令禁止的「局域网下看不出来」。
- **待取数字**：整屏 recap 期间相邻数据到达的间隔分布，在 **0ms 和 400ms RTT 两种条件**各一组
  （w-base-v2 的 `delay_proxy.py`，自证 5.3ms→403.6ms）。**没有这组数字前，阈值只是个猜的数。**

**结构性消歧（可选增强，降低对精确阈值依赖）**：
- `clear` 类：重写只覆盖**顶部少数行**（提示符在行 0），重写范围上限很小；
- `recap` 类：重写覆盖**逐步下探到屏幕底部**。
- 判据：静默时若重写覆盖的**最大行号 < 屏幕高度某阈值**（如 <50%）→ 视为「清屏后短写入」落定；
  否则视为 recap 进行中，继续等结构性落定或硬上界。
- 此阈值是结构性分数（有语义：recap 写满屏、clear 写顶部），比纯时间更稳，但仍需实测校准。

### 第 3 层 · 硬上界兜底（畸形输入保险）
重写期间数据静默超过 **2000ms** → 无条件呈现当前状态。
- 覆盖：重写中断/卡住/判据漏洞。
- 已实现：`rewriteFallbackCount` 可观测 + 2000ms。
- 量级依据（已有）：2× 局域网 recap 时长（1s）留余量；按「距上次收到数据」计，非从重写开始。

## `clear` 场景的判据归属

`clear` 落在**第 2 层（静默落定）**：清屏 + 提示符 1 行 + 流静默（短阈值）→ 呈现清屏结果（<500ms 目标）。
`TermRewriteClearScenarioTest` 锚定第 2 层，是永久门（现有实现红：2050ms 靠第 3 层）。

## 产品边界约束（tmux 层修法的红线）

**若 2026 路线走通**，落地需让 tmux 向内声明 Sync 能力（`terminal-overrides` 是 tmux server 级选项）。
这会影响该 tmux server 上**用户自己的其他 pane**，不只是我们管的会话。

**约束：修法不能是「偷偷改用户的 tmux 配置」。** 这是产品边界，需用户裁定。可选更干净的落点：
- 只对 daemon **自己创建**的会话设置，不碰用户既有会话；
- 由 daemon 在 spawn CLI 时通过环境变量/TERM 影响（如 pane 的 TERM 声明 Sync），而不改 tmux server 选项。
