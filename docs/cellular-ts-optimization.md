## §0 一句话结论

**这条链路是双重中继：手机(蜂窝) → DERP 中继 → 用户自建新加坡代理(sg-proxy2.team-agent.net)
→ Mac 家宽；WG 直连 UDP 实测零载流。** 应用层真实单价不是 ICMP 的 1.22s，而是
**1.5–1.8s/往返（尾部 ≥2.4s，重传率 10%）**。最大的一笔收益（十倍级）在网络侧——让两台
都在国内的设备别绕新加坡：家里路由器映射 UDP 41641 + Shadowrocket 给 tailnet 网段直连豁免，
两步、可回退、用户自己动手。代码侧按新单价重排：**delta 背压合并（原 D2）风险调整后第一个做，
捏合 10–20 往返（原 D3）账面最大升入第一梯队，重连快路径因新观测到的连接 churn 而升权**。

## §1 现状判读（增量实测）

### 1.1 DIRECT 还是 DERP？——无直连 UDP【实测】，DERP+自建代理双重中继【推断·强】

**实测**（23:36:02–23:36:10，nettop 对 MacPacketTunnel pid 39476 三采样，期间向手机发
60 个 ICMP 且全部有真实往返）：

- Tailscale 的 WG 数据端口 `udp *:41641`：bytes_out **534124 → 534124 全程不变**，
  bytes_in 仅 +124B（心跳级）。**穿透手机的流量没有走这个端口 → 当前无活跃直连 UDP 路径。**
- 同进程对外的全部活跃数据流 = 30+ 条 TCP，目的地 82.21.81.136 与 172.237.72.43。
  两个 IP 的 TLS 证书同为 **CN=sg-proxy2.team-agent.net**（Let's Encrypt，23:35:41 实测；
  172.237.72.43 rDNS 为 linodeusercontent.com）。**即前几轮所称"海外出口"实为用户自建的
  新加坡代理节点，不是 Tailscale DERP 本体。**

**推断（强，标注为推断）**：Tailscale 失去 UDP 通路时唯一的数据面回退是 DERP（HTTPS/TCP）。
Mac 侧 Tailscale（跑在 Shadowrocket 里）的对外 TCP 全部指向 sg-proxy2 → 它的 DERP 连接被
包裹在到自建代理的隧道里，**具体 DERP region 从主机侧不可见**。因此判定为：
**RELAY（DERP），且 Mac 侧在 DERP 之外还多套了一层新加坡自建代理 = 双重中继。**

- 确证动作（1 分钟，零风险）：手机 Tailscale App 状态页看该 peer 显示 direct 还是
  "Relay: <region>"。这同时补上 region 这个缺口。

### 1.2 394ms 下限拆得开吗？——拆开了一段，剩下的拆不开（并说清要什么）

| 成分 | 数值 | 性质 |
|---|---|---|
| Mac → sg-proxy2（82.21.81.136）| **121–190ms，ICMP 丢 20%**（23:35:44，`ping -b en0` 绕开 TUN；同窗该组 TCP 流内核 srtt 122–284ms 交叉印证） | 实测 |
| Mac → 172.237.72.43（同集群另一节点） | 272–326ms，丢 50% | 实测 |
| 蜂窝相对 WiFi 的接入增量 | ~+67ms（394.3−327.4，两次实测之差，不同时刻可比性有限） | 实测差值 |
| 本机用户态转发（Shadowrocket netstack + Clash TUN） | **≤10ms 量级**（到同一 IP，经 Shadowrocket 的 TCP srtt ≈ en0 裸 ICMP，无显著加价） | 推断（有对照） |
| 手机(蜂窝) → DERP → sg-proxy 复合段 | ~200–260ms（394 − 130 的算术余量） | **拆不开** |
| 均值(1.2–1.6s)与下限(0.39–0.46s)之间的 ~1s | 排队/缓冲膨胀：0% 丢包下 RTT 5 倍振幅锯齿（snapshot-02 波形）= 深缓冲特征 | 推断（有波形佐证） |

**要把"复合段"拆开需要**（按成本升序）：① 手机 Tailscale 状态页（region + direct/relay，
1 分钟）；② 用户在 sg-proxy2 上有 root——在服务器上分别 ping Mac 家宽出口与 DERP，
两条命令把中段钉死；③ Mac 侧 `sudo tcpdump -i en0` 对 DERP 流量测时（本席无 sudo，未做）。
在拿到 ①② 之前，任何"DERP 在哪、占多少"的说法都是猜——halt，不猜。

**方法论警告（本轮新发现，后续所有测量都要避开）**：经默认路由（Clash TUN）的 ICMP 被
本地代答——ping 82.21.81.136 与 8.8.8.8 都返回 0.3–0.9ms、TTL=64（23:33:13/23:35:44 实测）。
**经 TUN 的 ICMP 一律不可信**；要测真实 RTT 必须 `ping -b en0` 绕开 TUN。
（ping 100.69.43.120 的数百~数千 ms 属真实穿透值，量级排除代答。）

### 1.3 ICMP 和应用层往返是不是一回事？——不是，差 35% 起步

同一观测窗口的两个数：

- ICMP：avg **1318ms**（23:33:02，20 包）
- 真实 WS TCP 连接的内核 srtt：**1762.66ms**，重传 1374/13261 字节 ≈ **10.4%**，
  rx_dupe 332（23:36:32，nettop 对 daemon pid 70317——这是手机连着的那条真连接，
  不是探针）

**结论**：应用层单价 ≥ TCP srtt > ICMP。差额来自重传（RTO 停顿可达数秒）、TCP 队头阻塞、
排队。**往返账的"次数"结构不变（那是代码推导，可信），单价要从 1.22s 上调到
1.5–1.8s/往返、尾部 ≥2.4s。** 所有"省 N 个往返"的收益按账面再放大 30–50%。

另一层（【推断】，锯齿波形佐证）：这是条深缓冲链路——126KB 级大载荷（翻页、连续全屏快照）
在飞行期间会抬高**其间所有流量**的 RTT。字节减负在这条链路上不只是省带宽，是给别的往返降价。

### 1.4 连接稳定性（新观测，修正"漫游不断连"的印象）

- 23:29 与 23:33 手机连接源端口 50914 → 23:36 变为 49834 → **23:41 无 established 连接**，
  同刻 ICMP 丢包 16.7%、max 3971ms。
- 即 8 分钟内至少一次重连 + 一次断开（原因未判定：可能 App 切后台、蜂窝波动或中继掐线）。
  leader 交接里"WiFi→蜂窝切换 TCP 没断"是真的，但它是快照——**蜂窝+双重中继下连接 churn
  是常态假设更稳妥**。每次重连都要付冷启动的往返账（见 §3 C3）。
- 把 churn 从推断变实测：部署 `server/internal/api/sendq_metrics.go`（已写好未部署）拿
  `close_reason`——需重启 daemon 断线几秒，**等用户点头，本席不动**。

## §2 网络侧建议（用户自己动手；按 收益/操作成本/风险 排序）

> 共同前提：改的全是用户自己的网络设备/软件，我们只出步骤；每步给验证与回退。
> 收益标注：凡未实测的量级一律【假说】（机制成立、数字待验）。

### N1 让 Tailscale 打洞直连：路由器映射 UDP 41641 + Shadowrocket 直连豁免

两台设备都在国内，却绕新加坡双重中继。打洞只需**一侧**可达：蜂窝侧是 CGNAT 改不了，
所以家宽侧可达性是唯一杠杆。

- **改什么**：
  1. 路由器管理页 → 端口转发：**UDP 41641 → 192.168.31.116**（或开 UPnP 让其自动映射）。
  2. Shadowrocket 配置加两条直连规则：`IP-CIDR 100.64.0.0/10 → DIRECT`；
     目的端口 41641/UDP → DIRECT。**注意**：Tailscale 控制面（controlplane.tailscale.com、
     DERP 域名）在无代理条件下的可达性未验证——**先只放行数据面（上面两条），控制面保持
     现状走代理**，避免把登录/密钥轮换弄断。
  3. 前置核查（决定这条路通不通）：路由器 WAN 口 IP 若是 100.64/10、10.x、172.16/12
     → 家宽是 CGNAT，本条打洞成功率大降，转 N2。
- **预期收益**：RTT 下限 394ms → 蜂窝到家宽的国内路径（几十 ms 量级），**约十倍级**，
  且甩掉 sg-proxy 那条 20% 丢包的腿【假说——机制是实测钉死的（无直连 UDP、双重中继），
  改善数字待改后实测】。
- **怎么验证**：Mac 上 `ping -c 20 100.69.43.120`（此目标不经 TUN 代答，可信）——
  min 从 ~400ms 掉到 <100ms 即生效；手机 Tailscale App 里该 peer 显示 direct。
- **做错了会怎样**：端口映射错了 → 只是打洞继续失败，回落 DERP，**现状不变差**；
  Shadowrocket 规则错了 → 最坏是某些流量分流错，删规则即恢复。
- **回退**：删端口映射、删两条规则，全部即时恢复原状。

### N2 若 N1 卡在 CGNAT：IPv6，或自建国内中继

- **IPv6 支**：国内蜂窝普遍有 IPv6；若家宽光猫/路由器开 IPv6 且防火墙放行 UDP 41641，
  Tailscale 会走 v6 打洞。操作：路由器开 IPv6 + 防火墙例外。验证/回退同 N1。
- **自建 DERP 支**：用户已运维 sg-proxy2（Linode，有 root），但新加坡位置本身就是那
  ~300ms。要把中继单价打下来需要**国内 VPS 自建 DERP**（Tailscale 支持 ACL derpMap
  自定义），中继路径变 手机→国内DERP→Mac，RTT 预期 <150ms【假说】。
  成本：一台国内 VPS + 备案/合规考量 + DERP 部署，属小项目；风险中；回退 = ACL 删
  derpMap。**排在 N1 之后**：直连是零成本上限更高的路，先试完再花钱。

### N3 卫生项：修 Clash 的 route-exclude（leader 已查明未生效）

`route-exclude-address: 100.64.0.0/10` 没生效，tailnet 流量在本机多穿一层 Clash TUN，
且 TUN 代答 ICMP 污染一切测量（§1.2 警告）。修复语法/版本后：本机到 tailnet 的路由不再
克隆自默认路由。**直接延迟收益小（≤10ms 量级，§1.2 实测对照），但它是 N1 第 2 步的配套**
（41641 出包路径理顺），并让今后的测量不再被代答骗。风险低；回退 = 配置改回。

### N4 纯观测（零改动，随时可做）

手机 Tailscale 状态页截图（region + direct/relay）；在 sg-proxy2 上向 Mac 家宽出口与
DERP 各 ping 一轮。这两样把 §1.2 的"拆不开"补齐。

## §3 代码侧建议（假设链路修不好，按实测 1.5–1.8s/往返 重排）

### 先回答 leader 的两个问题

**① "省往返排 D3"还对吗？——不对了，理由是单价变了 4–6 倍。**
前一席排序时的单价语境是"TS 单往返数百 ms"（roundtrip-audit 的估算），D1（链路）十倍级
排第一在当时和现在都对——但它已被本文移入 §2（本来就是用户动手项）。省往返当时按
"数百 ms 级改良"压在 D3；实测应用层单价 1.5–1.8s 后，**捏合 = 15–36 秒、冷启动+每次重连
= 6–8 秒**，这不是改良是可用性问题。省往返必须升入代码侧第一梯队。

**② delta 背压合并（原 D2）在慢链上值多少？——风险调整后是代码侧最值的一条。**
定性账：srtt 1.7s、重传 10% 的链路上，服务端 sendCh 积压是常态而非边角——合并触发频率高；
它不降单往返延迟，但把"N 个中间状态各到达渲染一次"变成"一帧到位"，直击用户主诉
"看得见每个中间状态"；合并的是本就在排队的东西，零延迟代价、零协议改动、纯服务端、
不碰任何被回退过的 UI 路径，红测标准明确（客户端收到字节流逐字节等价）。
【机制与语义安全已由 docs/ts-link-baseline.md 查证；收益量级需 C1 档机器眼实测，属假说】

### 重排结果（C1 最先；原 D1 已移入 §2 网络侧）

| 新序 | 原序 | 改什么 | 为什么在这条链路上体感变好 | 怎么证明 | 风险 |
|---|---|---|---|---|---|
| **C1** | D2 | delta 背压合并（sendCh 满不丢、并帧 flush） | 见上：积压常态化 → 高频生效，闪烁/分批直接消失 | 红测字节等价 + C1 档机器眼数中间状态 | 低（空闲路径行为不变；`deltas_dropped` 计数语义要同步改） |
| **C2** | D3 | 捏合 10–20 resize → 松手 1 次 | 账面最大单项：15–36s → 1.5–1.8s；且省掉 10–20 个全屏快照对深缓冲链路的 RTT 污染（§1.3） | C1 档数一次捏合的 resize 帧数与快照字节 | **中高**：有被用户判"比 v6 差"的回退史（先读 `docs/reverted-to-v6/` 失败原因），捏合注入器在新 AVD 上是坏的 → 验证要走用户真机 |
| **C3** | D5 前半 | 冷启动/重连 4→2 往返（深链 subscribe∥list∥scrollback 并行，audit §一-A 已查证零协议改动） | 新观测把权重抬起来：8 分钟内一次重连+一次断开（§1.4），每次 churn 都付这笔账——4 往返 ≈ 6–7s 旧屏/黑屏 → 3s | 重连场景计时 + sendq `close_reason` 统计 churn 频率（部署需用户点头） | 中低（深链订阅失败回退路径要处理） |

| C5 | D4 | 进会话双快照消除 | 收益 1 往返（~1.5–1.8s，账面比原估大） | conn.snapshots_from_resize 2→0 | 高：上次回退根因未明，前置"名义 vs 实测字格宽"仍未修，位次不动 |
| C6 | D6 | 客户端渲染合帧 | 与 C1 同目标 | — | 维持原判：C1 量化前不动（有三次零收益一次全黑的历史） |

**与网络侧的关系**：C1–C3 与 N1 正交——N1 成功后单价掉到几十 ms，C2/C3 的绝对收益缩水
但仍为正（LAN 也少 10–20 次快照重绘）；C1 在任何慢时刻（含未来弱网）都生效。**不存在
"等网络修好就不用改代码"或反之的互斥。**

### ⚠️ 订正（2026-08-14，w-c1-probe 隔离实测推翻 C1 前提）

- **C1 的触发前提被证伪，C1 不该上线。** 本文原判"sendCh 积压是常态"（已标【假说】）：
  w-c1-probe 隔离 daemon 实测（`e2e/harness/c1_sendq_probe_test.go`），LLM 流式 400–500B/s
  下 queue_peak=1、84 帧零缓冲；最恶劣本地背压（对端完全不读 + 2KB 窗口 + 2000 行突发）
  queue_peak 也只到 2，距 256 槽两个数量级。
- **机制订正**：队列不住在应用层 sendCh，住在内核 socket 缓冲与网络里——本席自己的观测
  佐证同一机制（23:36:32 nettop：daemon 真连接 tx_win ≈3.1MB，KB 级 delta 永远被内核整包
  吸收，writeFrame 不阻塞 → 合并永不触发）。残余触发场景只剩"MB 级输出突发 + 对端长时间
  不读"的罕见叠加；dev 实现 + 红测按 w-c1-probe 判定留档，作未来真背压时的现成方案。
- **"看得见中间状态"的真因**（w-c1-probe 判定，与本席机制订正一致）：delta 分散到达、
  到达即各渲染一次，与队列压力无关。杠杆移到**到达侧**：客户端合帧（原 C6——它此前
  压在"C1 量化之后"的理由随 C1 一起失效，需重新评估，但其历史风险不变：三次零收益、
  一次全黑）或服务端按时间窗/未 ack 字节的应用层节流（新方案，需裁定）。位次裁定权在 leader。
- **单价同步订正**：打洞后实测 RTT 147ms、重传 0（w-c1-probe 报）→ §3 按 1.5–1.8s/往返
  折算的账全部除以约 10：捏合 ≈1.5–3s、冷启动/重连 ≈0.6s。省往返（C2/C3）仍为正、
  位次维持，但从"可用性问题"回落为"改良"，预期收益按新单价读。

   （先看路由器 WAN 口 IP：是 100.64/10、10.x、172.16/12 就直接转 N2 的 IPv6 支。）

   min <100ms = 直连成功；仍 ~400ms = 打洞失败，回落中继，现状不变差，按 §2 N2 走。
   同时手机端看 peer 是否变 direct。
