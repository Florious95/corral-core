# 全自动编排方法论（本工程版）

> 来源：2026-08-15 用户指令 + `讨论team-agent` leader 三问答复（`msg_b65fe1db3960`）。
> **这份文档是给下一代 leader 的**：compact 之后重读这一份 + 账本，就能接着跑。
> 原则：**上下文是缓存，文本才是可继承的介质。**

## 0 用户指令（2026-08-15，原文要点）

1. **无人值守驱动任务完成，全自动编排流畅运行为最高优先级。**
2. **绝对不要人肉编排。** 分身不可用就不用分身，尽可能少占 leader 上下文。
3. **问题归属要分清**：team-agent 框架问题 vs 账本编排框架问题，**有谁找谁**。
4. **投递对方的问题必须先写 bug 分析报告**（现象 / 日志支撑 / 原因分析），
   消息里**只给文档路径**，不长篇大论。
5. **leader 自己的最高优先级是完成产品修改点**（直通输入 / 键条顺序 / 状态判定 / 刷新模型）；
   **全自动编排本身的优先级归框架方**。

## 1 「全自动」的真实形态（**本节 2026-08-15 当天被推翻过两次，读最终版**）

> ⚠️ 历史（别照着做）：最初两位 leader 都告诉我「没有常驻 runner、leader 必然在回路里」。
> **两条后来都被他们自己更正**：能力 `team-agent wait --task` **0.5.65 起就有**，
> 参考驱动器也已交付。**我据此写给框架方的 `results.jsonl` 需求是伪需求，已撤回。**
> 教训：**「框架没这个能力」这种断言，先自己跑一次 `--help` 再信。**

### 最终形态

**驱动器是 owner pane 的子进程**（框架裁定：owner gate 是设计如此，
**驱动器不能做成席位**——worker pane 建席会被 `not_owner` 拒）。

```
tools/ledger-driver.py          ← 本工程的驱动器（改自 skill 的 reference）
.team/ledgers/driver.log        ← 它的日志
```

leader 用 **harness 托管的后台进程**起它，**不要用 `nohup ... &`**：
harness 会在进程退出时唤醒 leader，而 nohup 起的进程**死了没人知道**——
驱动器的设计是「停就是要 leader 介入」，**停了没人知道等于没停**。

一轮 = `ledger-eval` 算前沿 → 派单（正文全部从账本派生）→ `wait` 事件唤醒 →
**驱动器自己跑机械判据拿退出码（不采信席位自报）** → 过了才置 succeeded → 下一轮；**不过就停**。

⇒ **leader 只在驱动器停下、或撞上「五种情况」时出场。**
五种：裁定改路线 / 同一任务连挂 2 轮 / 撞已裁定条目冲突 / `ledger-eval` 非 0 改不动 / 框架故障。

### 席位回报别打 leader 屏（已实测有效）

派单里要求席位 `report_result` 带
`presentation={"sink":"casefile","class":"stage_result"}` + `task_id=<账本任务 id>`。

| 带不带 presentation | `notification_status` | 打不打 leader 屏 |
|---|---|---|
| 不带 | `injected_awaiting_receipt` | **打** |
| 带 | `stored_not_presented`（channel=`casefile`） | **不打** |

**`presentation` 是结构化参数，不是正文文字，写进正文不生效。**
另：席位之间的疑问走 `send_message(to="advisor")` 直接流转，**不经过 leader**。

### 🔴 比形态更要紧的一条（对方实测）

> **leader 烧掉的上下文几乎不在「派单」上，在「自己核对」上。**
> 派 4 张单约占 5%，验收占绝大部分——因为判据工具**在基线上就是红的**，
> 没有一个退出码能直接判通过，只能逐条人工核。

⇒ **决定 leader 上下文开销的是「判据能不能机械判」，不是「谁在跑循环」。**
**先把「做对了没有」压成一条退出码**，比选驱动形态重要得多。

**推论（本工程）**：③状态判定天然机械可判（喂 title 序列 → 断言 working/idle），
**所以它是第一张账本**；①直通输入判据大量落在手感上，排后面。

### 🔴 判据自身会骗人：缓存绿（2026-08-15 实发，第一张账本第一个任务就撞上）

`t.keybar` 的判据我写成 `./gradlew :app:testDebugUnitTest`。席位报完成后我重跑：

```
BUILD SUCCESSFUL   > Task :app:testDebugUnitTest UP-TO-DATE   exit=0
```

**exit 0，但测试根本没跑。** Gradle 从缓存返回了上一次的结果。
一条能从缓存返回 0 的判据，**判不出真假**——它对「代码被改坏了」和「代码是对的」给出同一个答案。

（框架的 `result_success_without_executed_tests` 警告当时就报了，**我差点当噪音略过。**）

**改法**：`./gradlew <task> --rerun-tasks --console=plain`。

**一般化的自检**：写完每一条机械判据，问一句——
**「如果被测对象是坏的，这条命令会不会仍然返回 0？」** 会，就还不是判据。
最省事的验法是**定点变异**：把产物改坏一处，判据必须转非 0；不转，判据无效。

## 2 顾问架构（我原来的理解是错的，已修正）

我曾说「顾问用零上下文反而对」。**错在把「顾问」和「审查席」混成一类。**

| 席别 | 上下文 | 为什么 |
|---|---|---|
| **顾问席** | **要有** | 它的价值恰恰在于读过东西；零上下文的顾问没有可兜的底 |
| **工作席** | 读顾问产出的摘要文档 | 省加载 |
| **对照席（至少一个）** | **零上下文，不读摘要** | 预先读过标准的席位会**从记忆里把标准没写的补上，标准的缺口就永远不响** |

对方实测数字：同一个文件，读过顾问摘要的席位注 **3** 处，零知识对照席注 **10** 处，
**3.3 倍分歧**，两侧独立指向同一条手册里没写的规则。

**⇒ 那个对照席的卡点，是「方法论到底写清楚没有」的唯一数据来源。不许省掉它。**

`compatible_api` 只能 `clone`（零上下文），不能 `fork`。
**所以顾问的知识必须落成文档**，不能靠会话上下文——顾问只产出《基底摘要》，其他席位读它。

**顾问当法官合法**：`judge_must_not_be` 禁的是**自产自判**。
顾问不产出被验收的产物就不违规；**一旦它动手改了被验收的文件，就对那个文件失去判权。**

## 3 分支建模：危险的不是分叉，是汇合（两条已知缺陷都没修）

死锁形状（对方给的原始复现）：

```
t.merge --requires_verdict[blocking]--> t.fix
t.merge --requires_verdict[mergeable]-> t.land
t.fix   --requires_success-----------> t.land     ← 就是这一条锁死
```

`t.land` 两条入边**隐式 AND**，而两条互斥 ⇒ 永远不可能同时满足 ⇒ **exit 0，静默不动**。

**正确写法**：

```json
"dependencies": [
  { "from": "t.advise", "to": "t.fix",  "condition": "requires_verdict", "verdict_in": ["escalate"] },
  { "from": "t.advise", "to": "t.land", "condition": "requires_verdict", "verdict_in": ["pass"] }
]
```

- **不要**再加 `t.fix --requires_success--> t.land`。
- 要表达「修完再判一次」，**新起一个 judgment 任务**（`t.fix → t.advise2 → t.land2`），
  **不要让两轮汇进同一个终点**。
- `blocking_policy` 与 `requires_verdict` **不要同时用，二选一**。

### 🔴 建完必做的死锁自检（失败模式是 exit 0，自己发现不了）

把所有任务 state 手工推到「顾问已出裁定」那一步 → 跑 `ledger-eval` →
**看「现在可以动的任务」里有没有东西**。
**一个都没有、而任务又没全完成 ⇒ 踩上了。**
（11 份 fixture 里没有两层裁定的，**没有可抄的**。）

## 4 人裁判据（已实测，不会卡死整张账本）

对方实测输出：

```
t.review 处于 acceptance_pending（人裁未回）
→ 「现在可以动的任务（1）」= t.side（无关独立支线）
→ t.review 显示 acceptance_pending，可见、不隐藏 → exit 0
```

**人裁悬着只挡它自己的下游，不挡无关支线。** `ledger-eval` 是一次性求值器，不阻塞等待。

🔴 **唯一的坑：整张账本只剩人裁在等时也是 exit 0。**
**别拿 exit 0 当「跑完了」**，要看**已完成是否覆盖必需任务**。

**分层**（本工程，因模拟器停用而更重要）：

| 判据类型 | 落点 | 自动化 |
|---|---|---|
| 协议 / 状态 / 几何 / 逻辑 | 机械判据，退出码权威 | 全自动 |
| Web 端可计算渲染 | 第 1 层，机械 | 全自动 |
| 手感 / 渲染时序 / 首帧 | `provider: "human"` judgment | 上升到用户 |

### closed_read 怎么写

- 人裁引用的产物路径**逐个文件**写进该 judgment 任务的 `read_paths`
  （**精确匹配，目录前缀不生效**，而同账本的 `write_paths` 用的就是目录——不对称，别混）。
- 或写进顶层 `read_only_shared`；实在拦不住把 `resource_isolation.closed_read` 设 `false`。

🔴 **真正的风险不是报错，是人为了躲报错提前不写判据**（实测三个盲测席都干过），
**而那种损失不会出现在任何绿色指标里。宁可先写，报错了再补 `read_paths`。**

## 6 已实测的环境事实（省得下一代重踩）

- **团队 0 席位时 `team-agent restart` 必失败**：报 `tmux session created: no` + `coordinator alive: no`，
  而 `coordinator.log` 是 **0 字节**（没写任何东西，查日志查不到原因）。
  **根因是没有 worker 可拉就建不出 worker tmux session。**
  **解法：先 `team-agent add-agent <名> --role-file <文件> --workspace .`（停机状态下可用，实测 ok），再 restart。**
- leader 自己的 tmux session（`team-agent-leader-claude_code-…`）与 worker session
  （`team-remote-agent-android`）**是同一 socket 上的两个不同 session**，不要混。

## 7 wait 只是省电，判据才是凭据（2026-08-15，账本 leader 的改法比我的好）

我发现 reference driver 的 `wait --task` 键错了（等 `message_id` 而非账本任务 id），
提了个两行修法：`wait_task(tid)`。**账本 leader 没照抄，理由值得记下来：**

> 那把「哪个 id 才对」**从一个错答案换成另一个赌注**。

他的改法是**把流程正确性从 wait 上摘掉**：

- 两个 id 都试（先账本 id 后 message_id），各自套墙钟上限；
- **都没等到也不当失败**，直接落到机械判据去判。

> **判据是唯一凭据，wait 只是省电。等待机制猜错了最多浪费一次墙钟，不该让整条流水线挂死。**

这条对本工程尤其重要，因为我们撞到的失败形态正是**挂死不是报错**：
驱动器活着、日志全正常、永远不推进。**任何「猜对了才能继续」的机制都不该在关键路径上。**

### 附带的一条更难看的观察（他指出的）

> 我这边没触发，是因为我的席位回报时自报的 task id 恰好就是派单 id——
> **同一个 bug 在不同约定下时隐时现，这比稳定复现更危险。**

⇒ **「我这儿没复现」不是证据。** 尤其当两边的约定不同时。

### 同类 bug 会成群出现

同一个「传了 `--json` 却仍按文本格式判 `ok: True`」的错误，在本工程驱动器里**出现了两处**
（`send()` 与 `provision_seats()` 的 `add-agent`）。
第一处让驱动器立刻停，第二处要等到「账本声明的席位缺失」才会炸——**一次修就把两处都扫掉**，
不要只修当场炸的那个。

## 8 「没跑过就别说」——一天之内两个方向各撞一次

### 方向 A：把「框架没这个能力」当事实（我犯的）

两位 leader 都告诉我 `result_source.capability_missing` 未解、没有 runner。
我信了，并据此给框架方写了一份 `results.jsonl` 需求。
**实际上 `team-agent wait --task` 0.5.65 就发了**，跑一次 `--help` 就知道。
我提的是伪需求，浪费了两边的往返。

### 方向 B：把「我记得有这个参数」当修法发出去（账本 leader 犯的，他自己揭的）

> 「我那条『派单必须带 `--task`』**从来没在我这儿跑通过**，我是照记忆加的参数、没查 `--help`，
> 实际结果是 **flag 被当成 TO 吃掉、席位收到一条空消息**。
> 所以不是『我的版本更新』，是**我发了一条自己没验过的修法给你们，你们照做会炸**。
> 抱歉，**这条比 bug 本身严重。**」

我方核实：`team-agent 0.5.66` 的 `send` usage 里没有 `--task`，`grep -c -- --task` = 0。

### 方向 C：改完不验就往下走（我同一轮犯了三次）

| 错 | 为什么没被抓住 |
|---|---|
| 文本手术把 `LOG = ...` 拼进注释行尾 | **`ast.parse` 通过了**——语法检查抓不到「语句被注释吞掉」 |
| 启动命令用 `\| tee` | 管道把驱动器退出码吃掉，**崩溃被报成 exit 0** |
| 用 `&` 起驱动器 | 脱离 harness 托管 ⇒ 退出时没人被唤醒；而席位回报都带 `casefile` 不打屏 ⇒ **全队静默停滞** |

### 三条合起来的规矩

1. **断言别人的能力有无之前，先跑 `--help`。** 两个方向都栽在这一步。
2. **改完常量/配置，跑一次真加载**（`import` 那个模块打印关键常量），**不要只 `ast.parse`**。
3. **起长进程不要 `| tee`、不要 `&`**：前者吃退出码，后者断掉唤醒。
   用 harness 托管的后台进程 + 重定向。**「停了没人知道」等于没停。**

### 一条被双方同意、写进 skill 的判断

> **wait 猜错、席位不守约、判据漏查，任意一条单独都不致命；**
> **靠席位守约的方案必须配「required 逐条求值」+「wait 等不到也落到机械判据」。**

⇒ 编排的可靠性不来自任何单点正确，来自**三条互不依赖的兜底同时在场**。
