## 1 「全自动」的真实形态（已确认，不要再讨论）

`result_source.capability_missing` **至今未解**，没有常驻 runner、没有 watch/hook、
skill 的 11 份 fixture **全是校验类，没有可抄的驱动脚本**。

⇒ 形态就是：**席位回报唤醒 leader → leader 跑一次 `ledger-eval` → 照「现在谁该动」派单 → 睡。**

**leader 必然在回路里。「全自动」= leader 不做判断只做转发，不是「没有 leader」。**

### 🔴 比形态更要紧的一条（对方实测）

> **leader 烧掉的上下文几乎不在「派单」上，在「自己核对」上。**
> 派 4 张单约占 5%，验收占绝大部分——因为判据工具**在基线上就是红的**，
> 没有一个退出码能直接判通过，只能逐条人工核。

⇒ **决定 leader 上下文开销的是「判据能不能机械判」，不是「谁在跑循环」。**
**先把「做对了没有」压成一条退出码**，比选驱动形态重要得多。

**推论（本工程）**：③状态判定天然机械可判（喂 title 序列 → 断言 working/idle），
**所以它是第一张账本**；①直通输入判据大量落在手感上，排后面。

## 2 顾问架构（我原来的理解是错的，已修正）

我曾说「顾问用零上下文反而对」。**错在把「顾问」和「审查席」混成一类。**

| 席别 | 上下文 | 为什么 |
|---|---|---|
| **顾问席** | **要有** | 它的价值恰恰在于读过东西；零上下文的顾问没有可兜的底 |
| **工作席** | 读顾问产出的摘要文档 | 省加载 |
| **对照席（至少一个）** | **零上下文，不读摘要** | 预先读过标准的席位会**从记忆里把标准没写的补上，标准的缺口就永远不响** |

对方实测数字：同一个文件，读过顾问摘要的席位注 **3** 处，零知识对照席注 **10** 处，
**3.3 倍分歧**，两侧独立指向同一条手册里没写的规则。

**⇒ 那个对照席的卡点，是「方法论到底写清楚没有」的唯一数据来源。不许省掉它。**

`compatible_api` 只能 `clone`（零上下文），不能 `fork`。
**所以顾问的知识必须落成文档**，不能靠会话上下文——顾问只产出《基底摘要》，其他席位读它。

**顾问当法官合法**：`judge_must_not_be` 禁的是**自产自判**。
顾问不产出被验收的产物就不违规；**一旦它动手改了被验收的文件，就对那个文件失去判权。**

## 3 分支建模：危险的不是分叉，是汇合（两条已知缺陷都没修）

死锁形状（对方给的原始复现）：

```
t.merge --requires_verdict[blocking]--> t.fix
t.merge --requires_verdict[mergeable]-> t.land
t.fix   --requires_success-----------> t.land     ← 就是这一条锁死
```

`t.land` 两条入边**隐式 AND**，而两条互斥 ⇒ 永远不可能同时满足 ⇒ **exit 0，静默不动**。

**正确写法**：

```json
"dependencies": [
  { "from": "t.advise", "to": "t.fix",  "condition": "requires_verdict", "verdict_in": ["escalate"] },
  { "from": "t.advise", "to": "t.land", "condition": "requires_verdict", "verdict_in": ["pass"] }
]
```

- **不要**再加 `t.fix --requires_success--> t.land`。
- 要表达「修完再判一次」，**新起一个 judgment 任务**（`t.fix → t.advise2 → t.land2`），
  **不要让两轮汇进同一个终点**。
- `blocking_policy` 与 `requires_verdict` **不要同时用，二选一**。

### 🔴 建完必做的死锁自检（失败模式是 exit 0，自己发现不了）

把所有任务 state 手工推到「顾问已出裁定」那一步 → 跑 `ledger-eval` →
**看「现在可以动的任务」里有没有东西**。
**一个都没有、而任务又没全完成 ⇒ 踩上了。**
（11 份 fixture 里没有两层裁定的，**没有可抄的**。）

## 4 人裁判据（已实测，不会卡死整张账本）

对方实测输出：

```
t.review 处于 acceptance_pending（人裁未回）
→ 「现在可以动的任务（1）」= t.side（无关独立支线）
→ t.review 显示 acceptance_pending，可见、不隐藏 → exit 0
```

**人裁悬着只挡它自己的下游，不挡无关支线。** `ledger-eval` 是一次性求值器，不阻塞等待。

🔴 **唯一的坑：整张账本只剩人裁在等时也是 exit 0。**
**别拿 exit 0 当「跑完了」**，要看**已完成是否覆盖必需任务**。

**分层**（本工程，因模拟器停用而更重要）：

| 判据类型 | 落点 | 自动化 |
|---|---|---|
| 协议 / 状态 / 几何 / 逻辑 | 机械判据，退出码权威 | 全自动 |
| Web 端可计算渲染 | 第 1 层，机械 | 全自动 |
| 手感 / 渲染时序 / 首帧 | `provider: "human"` judgment | 上升到用户 |

### closed_read 怎么写

- 人裁引用的产物路径**逐个文件**写进该 judgment 任务的 `read_paths`
  （**精确匹配，目录前缀不生效**，而同账本的 `write_paths` 用的就是目录——不对称，别混）。
- 或写进顶层 `read_only_shared`；实在拦不住把 `resource_isolation.closed_read` 设 `false`。

🔴 **真正的风险不是报错，是人为了躲报错提前不写判据**（实测三个盲测席都干过），
**而那种损失不会出现在任何绿色指标里。宁可先写，报错了再补 `read_paths`。**

## 6 已实测的环境事实（省得下一代重踩）

- **团队 0 席位时 `team-agent restart` 必失败**：报 `tmux session created: no` + `coordinator alive: no`，
  而 `coordinator.log` 是 **0 字节**（没写任何东西，查日志查不到原因）。
  **根因是没有 worker 可拉就建不出 worker tmux session。**
  **解法：先 `team-agent add-agent <名> --role-file <文件> --workspace .`（停机状态下可用，实测 ok），再 restart。**
- leader 自己的 tmux session（`team-agent-leader-claude_code-…`）与 worker session
  （`team-remote-agent-android`）**是同一 socket 上的两个不同 session**，不要混。
