## 任务一：打开会话全链路日志仪表（性能测量的地基）

**目标**：从「点开一个会话」到「完全加载完毕」之间存在结构化日志打印，级别 Debug、级别可改。
**硬约束（用户原话）**：后续测试**不能识图、不能取帧/取间隔**——性能只能从日志读出。
所以仪表必须自足：光看日志就能算出每段耗时（诊断日志纪律：记操作数，不只记判决）。

### 打点位（app 侧，按事件顺序；命名建议 tag=`PerfTrace`，一行一事件 key=value）
| # | 事件 | 建议锚点（基线代码） |
|---|---|---|
| 1 | `tap` 用户点击会话行 | 列表 onSessionClick 入口 |
| 2 | `route_enter` 会话页路由进入 | SessionRoute 组合首帧 |
| 3 | `subscribe_sent` 订阅帧发出 | ConnectionManager.subscribe |
| 4 | `geom_seed` 首次几何/resize 发出（带 rows/cols 操作数） | TermSurfaceView/SessionRoute 几何链 |
| 5 | `first_frame_recv` 首个二进制帧到达（带 kind、payload 字节数） | ws 收帧口 |
| 6 | `snapshot_applied` 快照进终端模型（带 序号、是否 alt） | TerminalEmulator.replaySnapshot |
| 7 | `first_draw` 画布首次非空绘制（带 glyph 数>0 的判定操作数） | TermSurfaceView onDraw 首次有字 |
| 8 | `layout_settled` 排布完成 = 之后 N ms（建议 500ms）内无再次 resize/reflow/全量重绘（把 N 与判定操作数打进日志） |
- 每行带单调时钟 ms（`SystemClock.elapsedRealtime()`），⛔ 不用墙钟。
- 一次打开一个 `open_id`（随机短 id）贯穿 1–8 行，多次打开不串。
- **级别可改**：Debug 为默认；提供开关（设置页隐藏项或 `adb shell setprop debug.agentmirror.perftrace 1` 一类），关=完全静默（静默经济红线：默认路径零成本）。
- 服务端侧（可选但强烈建议，同一任务内做）：subscribe 帧 `recv/start/done/queue_ms` 三时间戳日志——作废代码里 open-latency-plan.md P0-a 有完整设计，可参考思路但**代码必须从基线重写**。

### 验收
- 机械：单测断言一次模拟打开产生 1–8 全事件且 open_id 一致、时间单调；关掉开关后 0 行。
- 真机：用户手机装包，导出诊断日志能看到完整链（这是 092 §11 金标准的量具化）。
- 这是**基线后的第一条产品改动**，本身必须过「真机不倒退」门（它只加日志，若打开变慢了就是仪表写错了）。

## 任务二：在模拟器上测定性能基线（此后一切工作的地板）

**前提**：任务一的仪表已合入（仪表版即新基线代码，记录其 commit sha 于基线文件）。
**被测物**：仪表版服务端（9900 同源另起隔离端口）+ 仪表版 APP，模拟器 `agentmirror_test_b`。

### 流程（作废轮已趟平的环境做法，照抄坐标）
1. 隔离环境：照 `e2e/layer2.sh` + 契约 `092 §4`——隔离 TMUX_TMPDIR（短路径自检）、
   假 CLI 用 `ln -s /bin/bash <dir>/claude`（⛔ cp 的 bash 跑不起来）、pm clear 后手填配对。
2. 三个夹具会话：① 真 `claude` CLI 空闲（alt=1）② 会重绘 TUI（trap WINCH 清屏+重绘）
   ③ 大滚回（seq 40000）。⛔ 不用「清屏后永不重绘」夹具（不可能世界，092 §9 定案）。
   ⛔ 绝不点真实舰队会话。
3. 每夹具冷点开 ≥10 次（每次 force-stop 重启 app），**只从 PerfTrace 日志取数**
   （adb logcat -s PerfTrace，解析 1→7 与 1→8 两个总时长及分段）。
4. 统计：均值、p50、p95、最大值。**极端值不剔除**——单独列出并附当次完整日志段与怀疑原因
   （录进基线文件的 outliers 节）。
5. 落盘 `.team/perf/baseline-<日期>.json`：双端 sha、apk md5、模拟器型号、每夹具分段统计、
   outliers。提交 git。

### 基线的效力（用户令，写死）
- **此后任何改动不允许低于此基线；优化必须高于此基线。**
- 用法：每个改动包在同环境同流程复测，逐段对比；任何段回退 = 不出门。
- 模拟器基线是回归地板；用户真机体验（秒进秒排）仍是最终金标准，两者都要过。

## 任务三：corral-core 仓库重构——可被 APP 与桌面端引用（基线得到之后才动）

**目标**：`corral-app`（https://github.com/Florious95/corral-app，独立仓）与未来桌面端能**引用**
corral-core 构建客户端；**APP 的全部东西从 corral-core 剥离出去**；用引用方式构建出的 APP
性能**不低于（力争高于）任务二基线**。

### 建议切分（供下一任裁定，非定案）
- corral-core 保留（可复用核）：`internal/protocol` 对应的**客户端协议层**（帧编解码）、
  终端模型（TerminalEmulator/快照与增量应用/滚回）、连接状态机（auth/订阅/重连）、
  主题模型。以 Kotlin 纯 JVM/KMP 模块形态输出，⛔ 不依赖 Android API（Compose/View 层不进核）。
- 剥离到 corral-app：全部 Android 壳（Activity/Compose UI/TermSurfaceView 绘制层/资源）。
- 桌面端未来引用同一核（Compose Desktop 或其它，由后续裁定）。
- 引用机制候选（按简单优先）：① Gradle composite build（includeBuild git 子模块）
  ② 发本地 maven（mavenLocal / GitHub Packages）。先 ①，够用不升级。
- server/ 与 corral-serve 镜像关系维持现状（mirror-push.sh 已处理），不在本次范围。

### 步骤骨架
1. 在 corral-core 内先做**模块内切分**（同仓拆 Gradle module：`:core-protocol` `:core-terminal`
   `:core-conn`，app module 只剩壳），每一步跑任务二流程复测基线——切分本身不许掉性能。
2. 切干净后把 app 壳整体迁往 corral-app 仓，corral-app 以 composite build 引 core 三模块。
3. 终验收：corral-app 构建出的 APK，任务二同流程测得 ≥ 基线；用户真机秒进秒排不倒退。
4. 镜像脚本（tools/mirror-push.sh / mirror-pr*.sh）按新仓界重划排除项。

### 红线
- 基线未测得（任务二未收口）⛔ 不许动重构。
- 重构期间一次只挪一个模块，每步复测；出现回退立即回退该步（回炉纪律：回退作分析）。
- 图标等 UI 资产迁移时带上 093 §2 裁定（只用 Provider 原生厂家图标）。
