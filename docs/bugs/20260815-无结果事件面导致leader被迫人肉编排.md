# 无结果事件面 ⇒ leader 被迫人肉编排

- 日期：2026-08-15
- 报告方：远程Agent安卓 leader
- 归属：**team-agent 框架**（结果事件面在框架队手里）
- 严重度：**高**——它把 leader 的上下文变成了编排的瓶颈资源，用户额度直接被它吃掉

## 现象

用户 2026-08-15 原话：

> 「假如说这些消息还在往你这里发，就说明你没有做好全自动编排。……**我的额度不多了。**」
> 「**千万不要再走人肉编排的流程。**」

实测：本工程跑一张 5 任务的账本，**每完成一个任务就打断 leader 一次**，且 leader 必须
亲自重跑机械判据（因为 `report_result` 不是完成凭据）。两条任务的实际中断记录：

| 任务 | leader 被打断 | leader 亲自做的事 |
|---|---|---|
| `t.keybar` | 1 次 | 重跑 gradle、发现缓存绿、做定点变异、改判据、改账本、提交 |
| `t.archive` | 1 次 | 重跑 3 条判据 + 补跑 `go test`、读失败测试源码、判定它是化石、重新派单 |

**5 个任务 ⇒ 至少 5 次 leader 中断，每次都是 Opus 级上下文。**

```
Team Agent message from dev-keybar for msg_eaed9e5d70b8:

Result id: res_bcf5e05f9318
```

## 原因分析

1. `report_result` 的 `result_route` 实际落点是 **leader**，且**注入 leader 屏幕**。
2. `presentation.sink = casefile|silent` 能抑制屏幕注入，但**只是不显示**——
   它仍然是「durable，可拉取」，**没有任何外部进程可以被结果唤醒**。
3. ⇒ **被唤醒的实体只有 leader 一个。** 任何第三方 runner（编排席、脚本、常驻进程）
   只能**轮询** `status` / `collect`，而轮询与「事件驱动、不轮询、不等待」的账本模型直接冲突。
4. ⇒ 结论：**在没有可订阅结果事件面之前，「全自动编排」在结构上不可能不经过 leader。**

## 诉求（按代价从低到高，任一条都能解开）

1. **可 tail 的结果事件文件**：每条 `report_result` 追加一行 JSON 到
   `.team/runtime/<team>/results.jsonl`，第三方 `tail -f` 即可。**这条最便宜。**
2. **阻塞到有结果就退出的命令**：`team-agent await-result --timeout N`，
   有结果 exit 0 并打印，超时 exit 非 0。编排席用它就是事件驱动而非轮询。
3. unix socket / webhook 订阅面（最完整，也最贵）。

## 本工程的临时绕行（已实施，供参考，不是解法）

建了 `orchestrator` 编排席接管循环，并要求所有席位回报带
`presentation={"sink":"casefile","class":"stage_result"}` 以免打到 leader 屏幕。
**但编排席仍然只能轮询**——它拿不到事件。这只是把轮询从 Opus 挪到便宜通道上，
**没有消除轮询本身**。

## 补充：`results.jsonl` 落地时请务必带上关联键（2026-08-15 追加）

team-agent 框架 leader 已确认归属并倾向实现 `results.jsonl`。**一条来自实际使用的约束**：

**每行必须能把结果映射回「当初那次派活」，否则 runner 用不了。**

现状是：编排器用 `team-agent send` 派活，拿到的是 `message_id`（如 `msg_31832416de80`）；
席位完成后产生的是 `Result id`（如 `res_bd82571235d8`）。**这两个之间目前没有可见的关联键。**
runner 拿到一行结果，无法判断它对应账本里的哪个任务——只能靠"哪个席位 + 时间最近"去猜，
这正是框架 leader 自己描述的那种"靠产物 mtime 判交付"的脆弱做法。

⇒ 请在每行至少带：`agent_id`、`result_id`、**触发该任务的 `message_id`（或等价的 dispatch 关联键）**、
`status`、`observed_at`。有了 message_id，编排器就能做确定性映射，不必猜。

## 补充：`presentation.sink` 与 `result_route` 是两个机制，别混

框架 leader 指出 `send` 无法声明 `result_route`。需要澄清的是本工程正在用的另一条路：
`report_result(presentation={"sink":"casefile","class":"stage_result"})`
——它抑制的是**向 leader 屏幕的实时注入**，不是路由。

**两个待确认的点**（我方尚未取得数据，取得后单独报）：
1. `presentation.sink=casefile` 能否抑制"Task … reported completed from X"这条**由 harness 自动产生**的通知？
   （它可能与 worker 自填的 presentation 不是同一条产生路径。）
2. 若不能，则在 `results.jsonl` 落地前，**本工程无任何手段阻止 leader 被逐条打断**——
   编排席只能减少 leader 的*工作量*，减不掉*中断次数*。
