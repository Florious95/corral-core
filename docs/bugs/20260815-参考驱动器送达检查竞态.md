# 参考驱动器的送达检查是竞态：固定 sleep 5 → 查一次 → 没有就中止整条运行

- 受理方：ledger-orchestration 维护 team

- 影响：**阻断全自动编排。每一次派单都是一次掷骰子**，输了整条运行中止（return 6）。
- 使用方已按用户裁定**停工等修**，不绕过、不自行打补丁。

## 一、现象

`reference/ledger-driver.py`（今日最新版，本工程 commit cf4530a2d 同步）主循环：

```python
time.sleep(5)  # 给注入留出上屏时间，否则查早了必然查不到
if token_landed(seat, task_id):
    log(f"  ✅ {task_id} 已进 {seat} 转录（user turn）")
else:
    log(f"  🔴 {task_id} **未进** {seat} 转录 ⇒ 疑似尾部截断，这条没送到。"
        f"不重发（重发会造成粘连），停下交人。")
    return 6
```

**固定等 5 秒 → 查一次 → 查不到就 return 6 中止整条运行。没有重试、没有轮询。**

⇒ **消息在 16:38:39.159 成为 user turn，驱动器在 16:38:38.x 已经宣告失败并中止。差约 1.1 秒。**
⇒ 且投递本身完全正常：席位收到了，此刻正在 BUSY 干这单活。**驱动器死了，席位在干活。**

## 三、原因分析

- 席位是 IDLE 时投递的（驱动器已按新逻辑押住等 idle），所以不存在排队路径。
- 从 `send` 返回到 token 成为 user turn，中间要经过：tmux 注入 → CLI 收下 → 起一轮 → 写转录 jsonl。
  这段耗时**不是常数**，受机器负载影响。本次约 6 秒（16:38:33 派单 → 16:38:39.159 落盘）。
- 而检查窗口是**写死的 5 秒**，且**只查一次**。
  ⇒ 只要落盘耗时 > 5s，就必然误判为「没送到」并中止。
  ⇒ 本机今天 load 在 5–8 之间波动（框架队黑匣子数据），5 秒余量明显不够。

**这个失败形态最坏的地方**：它把一次**成功的投递**判成失败，然后**中止整条运行**，
而席位还在正常干活——于是「驱动器已死」和「任务在跑」同时为真。
使用方如果照日志字面理解，会以为要重派，而重派恰恰是你们警告过的粘连来源。

## 四、建议（修法归你们定）

把「固定睡 5 秒查一次」换成**有界轮询**：每 1–2 秒查一次，直到
①token 成为 user turn（成功）或 ②席位转 BUSY（也说明收到了）或 ③超时（才判失败）。
条件②尤其便宜：席位转 BUSY 本身就是送达凭据，不必等转录落盘。
