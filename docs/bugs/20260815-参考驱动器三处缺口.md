## 一、`revision` 变了以后，「BUSY 就跳过派单」会让整条链静默停住

参考实现（L266-270）：

```python
if seat_state(seat) == "BUSY":
    log(f"跳过派单：{seat} 仍 BUSY，认定 {tid} 已在手上，直接等")
```

这条的前提是「**忙席位手上拿的是当前版本的任务**」。**账本一改，前提就不成立。**

实发（本工程 2026-08-15，任务 `t.done-fossil`，席位 `dev-state`）：

1. 席位撞上写路径不足，发 blocking 上报，请 leader 裁定 —— 此时它 **BUSY**（正在写那封上报）。
2. leader 裁定「扩权」，改账本 `revision 1 → 2`，重启驱动器。
3. 驱动器见席位 BUSY ⇒ **跳过派单** ⇒ **扩权裁定根本没送到席位**。
4. 席位等不到裁定，空转到 idle；驱动器墙钟到点后落判据，`A-df-no-done` exit=1。
5. 驱动器停。**日志上看起来像「席位没干活」，实际是「席位没收到新版本任务」。**

这个失败形态的坏处是**它伪装成席位的问题**。

建议：按「`ledger_id` + `task_id` + `revision`」记派单水位，本版本派过才允许跳过。
我分叉里的实现（已随分叉删除，供参考）：

```python
mark = f"{REPO}/.team/ledgers/.dispatched/{l['ledger_id']}.{tid}.r{l.get('revision',0)}"
if seat_state(seat) == "BUSY" and os.path.exists(mark):
    ...跳过...
else:
    ...派单，成功后 open(mark,"w").close()...
```

## 二、席位 BUSY 且**本版本未派过**时，参考实现没有出路

接上条：水位机制会得出「必须派」，但你们刚闭合的根因说**朝 BUSY 席位投递恰恰是消息被删的唯一触发条件**
（Enter#1 入队 ⇒ 输入框空 ⇒ 消费判据看屏幕判「未消费」⇒ 再按 2 次 Enter ⇒ 队列项被删）。

⇒ 「跳过」和「硬投」都不对。第三条路是**押住不投，轮询到席位 idle 再投**。
我分叉里是这么做的（`while seat_state(seat)=="BUSY": sleep 60`，超 `MAX_WAIT` 则停下交人，绝不硬投）。
现已随分叉删除。**要不要收进参考实现由你们定**，但参考实现目前没有这条路径。

## 三、`ledger-eval` 在全 succeeded 的账本上报 `TerminalProofIncomplete`，且**退出码是 0**

```
$ ledger-eval .team/ledgers/done-fossil-v1.json
error: 引擎状态推导失败：state_error TerminalProofIncomplete
$ echo $?
0
```

- 两张账本命中：`done-fossil-v1`（1 个任务，succeeded）、`refresh-and-contract-v2`（4 个任务，全 succeeded）。
- **两张都没有任何 judgment 判据**，`acceptance.judgment` 全为 `[]`。
  （此前我方报过一次同名状态，那次的触发条件是 required 里含 judgment 判据、
  而 schema 无处记录裁定。这次触发条件不同：零 judgment 也会命中。）
- **危险点在退出码**：驱动器按你们的规范「只认退出码，不 grep 输出文本」，
  于是 exit 0 ⇒ 继续；而输出里没有「现在可以动的任务」区块 ⇒ 前沿为空 ⇒
  驱动器判「没人该动」正常收工。**一张永远无法终结的账本，在驱动器眼里等同于「干完了」。**

期望：要么让终结失败反映在退出码上（4？），要么给出可写的终结证明字段。
现状下使用方无法把一张账本干净地关闭。

## 四、参考实现硬编码裸 `team-agent`

L114/L136/L159 直接 `subprocess.run(["team-agent", ...])`。
本工程强制所有调用走 `.team/ta` 净化包装器（存在理由：codex 席位会给子进程注入
不可达的托管代理；现在它还承载 tmux 追踪 shim 的 PATH）。
建议顶部加一个 `TA = "team-agent"` 常量并统一引用，使用方改一处即可。
本工程已这样本地化，除此之外未改你们任何逻辑。
