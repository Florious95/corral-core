# 性能基线规范（v6 baseline · TS 链路中心）

> 日期：2026-08-13。用户裁定：全部缺陷搁置，在 v6 版本（`9653be07f`）优化性能，**核心是优化
> tailscale 的链路**。基线建在 **v6 = `9653be07f`**（w-dev-cols 正把 App 整体退回该版本）。
> **局域网数字没有意义**——过去所有性能判断建立在局域网上，正是用户反复指出的问题。
> 每个指标：**一个数，可重跑，可比较**。不写「流畅度」这类不可量化的词。

## 指标选取原则

从**用户每天实际做的动作**倒推，不凭空造。用户路径：**开 App → 看列表 → 进会话 → 发消息 →
等回复 → 捏合调字号 → 上滑看历史 → 切后台回前台**。每个动作给三类量：
- **往返次数**（弱网体感的决定因素，TS 单往返数百 ms）
- **端到端耗时**（手指离开屏幕 → 画面稳定）
- **传输字节**（弱网等待的决定因素）

## 必守：双网络条件 + TS 中心

**用户主场景是 Tailscale。** 每个指标两组数：0ms 与注延迟 400ms RTT（`e2e/delay_proxy.py`，
自证 5.3ms→403.6ms）。**只有局域网数字的指标，不算基线。**

**每条指标必须能回答「这一段在 TS 上慢在哪」**：测出「不可避免的下限」（往返次数 × 裸 TS 往返）
与「实测值」，差值 = 我们的浪费 = 优化目标。TS 链路本体指标见 `docs/ts-link-baseline.md`。

## 〇、TS 链路本体指标（见 docs/ts-link-baseline.md）

**先查清楚的四件事**（只读已查，见 ts-link-baseline.md）：
- ① **直连/中继**：tsnet backend 无状态暴露 → **App 无法显示直连还是中继**。优化第一件事=
  让用户知道自己在哪种模式（不改代码，先可见）。
- ② **SOCKS5 代价**：WebSocket 长连接复用 ✓（delta 路径无重复握手）；**上传每次新建连接**
  （HttpURLConnection 一次性）→ 每次上传多跳。
- ③ **用户态栈每包开销**：delta 逐 chunk 不合并 → 小包多、每包过用户态栈，代价被放大。
- ④ **小包缓冲**：delta 无合并；Nagle 类缓冲未查（待实测）。

**关键区分**：裸 TS 往返（基础延迟，不归我们）vs 我们的操作耗时 − 裸往返×往返次数（我们的开销，
**只有后者是优化目标**）。前者只能靠减少往返次数规避。

## 测法要求（每条别人照着能复现）

1. **打点位置**：明确在哪一环打（客户端收件线程 / 服务端 handleXxx / WS socket 读取点）。
2. **工具**：w-base-v2 的 recapprobe（WS 客户端，纯协议）+ delay_proxy.py + 机器眼帧差分。
3. **分位数**：p50/p95/p99/max + 样本数 + 采样窗口。
4. **阳性对照**：每次测量配一个必然非空的对照（如故意注入 500ms 必须被测出来），
   防「没测到」被当成「很快」（perf-scenarios 方法学第 3 条，本工程此前未做）。

## 门限：首版不给（leader 裁定，msg_5e20b56d6178）

**先测，再从实测数据里定门限。现在给就是编数字。**

实证：往返审计推算「翻页可省数百 ms」，实测是 6.6ms —— 差两个数量级，还是有代码依据的推算。
凭感觉定的门限只会更离谱。

**首版基线的唯一任务：把数测出来，如实记录，不做任何好坏 judgment。**
门限等有了两轮以上的数据、知道正常波动范围之后再定。否则第一次波动就会红，然后所有人开始无视它。

## 测数优先级（leader 裁定，P6 最高）

**P6 捏合 = 最高优先级，且是失败态基准的唯一来源。** 用户说「你们复现不了也是因为网络好」——
**把网络弄差（delay_proxy.py 400ms）就能复现**，工具早就有、只是闪烁相关测试从没用过。

1. **P6 捏合在注延迟下测**：v6 基线行为（10-20 次往返）+ 每次 resize 后屏幕的中间状态（机器眼
   时间算子，帧级）+ **用户描述的「闪烁」能不能被看见**。能看见 = 七轮都没拿到的失败态基准，
   且直接告诉我们「中间状态有几个、每个持续多久」。
2. **修法在网络层不在渲染层**：局域网同样的渲染逻辑不闪、TS 下闪 → 渲染没问题，问题是
   「用户要看到几个中间状态」。降低办法只有三个：减少往返次数 / 减少传输字节 / 减少每次交互的
   屏幕状态个数。**「修缺陷」和「优化性能」在这里是同一件事。**
3. P1 冷启动、P7 翻页：已有代码推导，实测验证（P7 实测 6.6ms vs 推算数百 ms）。
4. R1/R3 红线排后面（老化 4-8 小时占设备）。

## 真实 tailnet：需求降级

tsnet 用户态栈本身开销、直连 vs DERP —— 这两条**才需要真 tailnet，排后面**，且要用户提供
测试凭据（TS authkey 与配对 token 同级：只能经环境变量传入，不进 argv 不进日志）。
**先用延迟注入把能测的都测了**（delay_proxy.py 足够复现绝大多数闪烁）。

## 基线版本与前置

- 基线 = v6（`9653be07f`）行为。P6 的修复正被全量回退，所以测到的捏合基线是 v6 的 10-20 次往返——
  **这是用户实际在用的行为，是真正的基线，将来任何优化都要拿它比。**
