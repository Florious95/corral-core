## 四、回答 leader 的三个问题

1. **内容区实际占屏多少？** 内容边界覆盖 59.9% 屏高（y 57→1676），但**文字实际只稀疏分布**
   到 1676（contentRatio 2.9%），下方 40% 屏纯空。用户感知「约 1/4」是文字量（稀疏）与
   边界（60%）的叠加。
2. **底部空白多少个行高？** **约 56 个行高**（1124px ÷ 20px/行）。反推：App 认为屏幕可容纳
   ~140 行（2800/20），但实际只画了 ~84 行内容 → 缺 ~56 行。
3. **右缘是否异常？** **否**。rightMarginPx=56（内容右缘 1203/1260，正常余量），**不伴随
   右列截断**——D-38 底部留白与右列截断不同源。

## 五、结论

用户失败态 = **内容只画到屏高 60%、下方 40% 纯空**（≈56 行高空白），右缘正常。
这与 D-38「内容只占顶部 1/4、下方大片空黑」的形态一致（量化为 60% 边界 / 40% 空黑 /
56 行空白），并排除右列截断同源。

### 归因（leader 纠正，2026-08-13）：**这是 emit 缺失，不是栅格不收敛**

本文件早期版本把此现象归因于「纵向栅格不收敛（a+b 合一）」。**该归因错误，已划掉。**
重算证明：

- 内容 84 行 × 20px/行 = 1680px ≈ 内容底边 y=1676 —— **服务端只送来了 84 行**。
- 下方 1000px 纯空（contentRatio=0.000）—— 不是「本地画不下被裁」，是**根本没有内容可画**。
- 形状不同：栅格不收敛是「服务端行数与本地画布对不上 → 溢出被裁或本地多画」；本现象是
  「App 上报 rows=84，视口涨到 140 后**再没上报过**」→ 服务端一直按 84 行送内容。

**修法方向完全不同**：这是 **resize emit 缺失**（视口增长后未重新上报 rows），不是本地
绘制栅格问题。纵向 a+b 合一是另一条独立潜伏账（捏合放大后 rows 偏小），**不得挂到 D-38 上**。
