## 1. 鼠标事件归属：给里面的 Agent，外层 tmux 不许截获

### 决定是什么

- **鼠标事件归属 = 被投影的 Agent TUI**，不是外层 tmux。
- 点击必须落到 Agent 的可折叠区域、工具调用展开、diff 展开上。
- **外层 tmux 必须不截获鼠标**：`mouse` 在全局 / 会话 / 窗口三级都关掉（或等效地让 tmux 把鼠标字节原样交给 pane）。否则点击被 tmux 吃掉去切窗格、拖分隔线、进 copy-mode，**永远到不了里面的 Agent**。
- APP 壳只采集触点；编码由终端核按对面 app 当时开的模式来做（见第 2、3 节）。壳不决定「这是切窗格还是点 Agent」。

### 为什么

用户已裁定（不是待议项）。原话：「鼠标事件是要给 Agent 的。就比如说你调用了一个工具，你点这个是可以看到它具体调用什么；你改了代码，我能看到它完整改的代码。」

直接推论：tmux `mouse on` 与「点 Agent」互斥，两者只能选一个。本契约选定后者。

### 违反了会看到什么现象

- 点 Agent 的折叠行，窗格被选中 / 分隔线被拖动 / 进入 copy-mode，折叠行不展开。
- `PaneModeChanged.in_copy_mode=true` 被推上来，但用户并没有想进 copy-mode。
- 验证 tmux 没在截获（后继施工时用隔离 socket，⛔ 不碰用户真实 tmux）：
  1. `tmux -S <sock> show-options -g mouse` 以及 `-s` / `-w` 同源项，期望 `off` 或空。
  2. 点一个已知可折叠的 Agent 区域：画面应由 Agent 重绘（镜像 delta 出现折叠内容），而不是 tmux 切 pane。
  3. 对照：若 `mouse on`，同一点击会切窗格且 Agent 无反应。

## 2. 鼠标坐标编码：只用 SGR 1006，排除 X10 / 1005 / 1015

### 决定是什么

- **只用 SGR 1006**：`CSI < Cb ; Cx ; Cy M`（按下）/ `m`（抬起），参数为十进制 ASCII，无字节上限。
- **⛔ 不用** X10（`CSI M Cb+32 Cx+32 Cy+32`）、1005（UTF-8 扩展）、1015（urxvt）。
- 后继改现有 `scroll_wheel` 注入路径时，也必须收敛到 1006，不得再发 X10。现状代码注释仍写「SGR or X10」：

```
server/internal/protocol/frames.go:309
The server atomically judges the pane's mouse-tracking state via
tmux if-shell -F '#{mouse_any_flag}' and either injects raw mouse bytes
(SGR or X10 format, no Enter appended) or enters tmux copy-mode
```

这是滚轮手势的**现状实现**，不是本契约对点击编码的许可。点击与后继滚轮统一走 1006。

### 为什么

X10 把坐标塞进单字节 `32+coord`，超过 223 列/行就废；在 UTF-8 模式下实测还会被卡在 127（xterm.js #1962，https://github.com/xtermjs/xterm.js/issues/1962）。手机上看宽 diff / 长日志会直接点到错误单元格，且**不报错**。SGR 1006 是纯 ASCII 十进制，列行无此上限。xterm.js 支持的序列见 https://xtermjs.org/docs/api/vtfeatures/ 。

### 违反了会看到什么现象

- 点屏幕右半 / 下半，Agent 响应落在完全不同的单元格（坐标被截断或 UTF-8 吃掉）。
- `cat -v` / `script` 看到的注入不是 `^[[<...M` / `m`，而是 `^[[M` 后跟高位字节（X10）或非 ASCII（1005）。
- 宽屏（>223 列，或 UTF-8 下 >127 列）点击「偶尔准、大半不准」。

## 3. 跟踪模式：安卓上用 1002（cell-motion），⛔ 不开 1003（any-motion）

### 决定是什么

- **开启 cell-motion（1002）**，再配合 1006 编码。按下后在**单元格之间**移动才上报；抬起结束。
- **⛔ 不开 any-motion（1003）**。手指滑动不靠 1003 的像素级移动流，而是映射成滚轮事件（已有 `scroll_wheel` 帧语义：`Frames.kt` 的 `ScrollWheelFrame`）。
- 1000（仅按下/抬起、无拖动）不够用：拖选 / 按住滑动需要 1002。
- APP 若收到对面 app 请求 1003，核层**降级为 1002**，并留痕两边操作数（请求码 / 实际开启码）。

### 为什么

1003 会把每一次鼠标移动都变成上报，实测压垮 PTY 转发（Termux/PRoot，https://github.com/Gitlawb/zero/issues/505）。蜂窝 + 中转打洞路径比 USB 更窄，1003 会把输入热路径打满。1002 已足够：单元格级拖动 + 滑动→滚轮。

### 违反了会看到什么现象

- 开了 1003：手指微动就卡、镜像帧堆积、输入延迟从「可打字」变成「跟不上」。logcat 里 PTY 转发队列持续上涨。
- 只开了 1000：点击有反应，按住拖动没有（拖折叠 / 拖选失败）。
- 降级没留痕：线上只看到「鼠标怪」，分不清是对面要了 1003 被我们降了，还是我们根本没开 1002。

## 4. 重连时必须按原顺序重放模式设置

### 决定是什么

- 终端核必须记录对面 app 发出的**每一个** DEC 模式码、它的开/关、以及**到达顺序**。至少覆盖：1000 / 1002 / 1003（协议组）与 1006 / 1015 / 1005（编码组）。
- 重连（含 subscribe 重放快照、进程重启、PTY 新建）后，按**原顺序**把这串模式设置重新发给对面——不是「最后一组胜出的集合」乱序补发。
- 编码方式（1006/1015/1005）与协议（1000/1002/1003）在实现里**互为互斥组，谁后设谁生效**。顺序是信息，集合不是信息。

### 为什么

mosh #576（https://github.com/mobile-shell/mosh/pull/576）：漏重放或乱序重放，会**静默**退回有字节上限的旧编码。不报错，只是坐标错。xterm.js 同样把编码与协议做成互斥，谁后设谁生效。本工程重连语义本就要求 subscribe 重放快照（`frames.go` 的 Subscribe 注释：idempotent replay），输入模式必须走同一条「重连 = 按序重建」纪律。

### 违反了会看到什么现象

- 重连前点击准，重连后点击落点整体偏移或只在左上角一块准（退回 X10/127 上限）。
- 重连后拖动消失（1002 丢了，只剩 1000 或全关）。
- 仪表若只记「当前模式集合」不记顺序，排障时无法证明是「没重放」还是「重放顺序反了」。

## 5. ack 策略与预测性本地回显（同一决定，不许拆开）

### 决定是什么

现有协议：**每个 `input` 必回一个 `input_ack`**。`ok=true` 表示字节已进 pane；`ok=false` 必带闭集 reason（`session_not_found` / `not_subscribed` / `inject_failed` / `too_large` / `internal`）。见 `server/internal/protocol/frames.go:247` 与 `app/core-protocol/src/main/java/dev/agentmirror/app/conn/FrameEnums.kt:88`。

逐键透传之后，若仍「一键一帧一 ack」，每一个按键都是一次网络往返。本节省略「先改 ack、以后再做回显」这条路——**ack 形态与预测回显一起定**：

1. **ack 语义不取消**。「发出去没效果」仍然不许发生。禁止用「周期性心跳代替 ack」——心跳只能证明连接活着，不能证明那一串字节进了 pane。
2. **允许合批，不允许无回执**。可打印连续键可在约一帧（≤16ms）窗口合成一个 `input`，**一帧一个 ack**。控制字节、鼠标 CSI、`C-c` / `esc` **不合批**，单独成帧立即发。合批是降低往返密度，不是丢掉回执。
3. **ack 未回时的本地回显**：预测字形立刻上屏，视觉上可区分「已预测、未确认」（淡/弱对比）。不得把按键藏到 ack 回来才画。依据：mosh 在 3G 上把中位 ~503ms 的往返做成近乎瞬时（https://mosh.org/）。
4. **ack 与预测不一致时的收敛**：
   - `ok=true`：该 `req_id` 的预测改为「已确认」。随后**镜像 delta/snapshot 是画面权威**，预测层让位，不做双向合并。
   - `ok=false`：撤回该 `req_id` 对应的全部预测字形，按 reason 给可见失败（pane 没了 / 未订阅 / 注入失败 / 过大）。
   - **超时**（≥ `max(1s, 2×` 近期 RTT`)` 仍无 ack）：视为未达，撤回预测，允许用户重发。不得把超时当成成功。
   - 预测了字符 A、镜像却画出 B：**镜像胜出**，硬替换预测区。
5. **重连**：未 ack 的批次不得当已注入。重连后先按第 4 节重放模式，再按原顺序重发未确认批次。
6. **IME 组合期**（用户 2026-08-15 **未裁定**，本契约取施工默认）：组合串留在输入法，不进预测层；commit/上屏那一刻才进合批队列。若实现时发现必须改，上报，不在本格改码。

### 为什么

requirement 003 的「send-must-arrive」仍然成立：没有 ack，「发出去没效果」会再次变成不可诊断。但蜂窝 + 广州中转打洞的 RTT 会让「等 ack 再画」把逐键体验做死。mosh 已经证明：预测回显解决的是**体感 RTT**，ack 解决的是**到达判定**，两者职责不同、必须同时在。拆成两次决定，第一次会把每键往返写进协议，第二次再加回显就要面对「已上线的 ack 节奏改不改」——改则破坏兼容，不改则回显盖不住协议成本。

### 违反了会看到什么现象

- 只做逐键 ack、不做预测：按键要等一截才出现，蜂窝下像卡输入法。
- 只做预测、ack 改成周期性无回执：输入「看起来成功」，pane 其实没收到；用户以为 Agent 忽略了键。
- ack 失败不撤回预测：本地有字、远端没有，镜像一刷新字突然消失（或反了：远端有、本地又画一次变成双字）。
- 合批把 `C-c` 跟在字母后面同一帧：中断键被推迟到合批窗口结束，Agent 停不下来。

## 6. `tmux send-keys` 的用法：可打印走 `-l`，只有控制字节走 `-H`，且批量成一次调用

### 决定是什么

服务端第 1 步会把「名字键闭集」改成裸字节注入。无论最终走 `send-keys` 还是写 pane 的 stdin，**字节怎么交给 tmux** 必须遵守：

- **可打印文本（含 UTF-8 中文）走 `send-keys -l`**（literal，不再二次解析）。
- **只有控制字节走 `send-keys -H`**（hex）。
- **同一次注入批量成一次 tmux 调用**，禁止「一字节一进程」。
- 现有名字键闭集（`esc` / `ctrl_c` / `tab` / `up` / `down` / `left` / `right` / `backspace`）在第 1 步被裸字节取代之前仍然有效；闭集外的名字不得静默当 no-op——`ErrInvalidKey` 必须在调用 tmux **之前**失败（`server/internal/bridge/tmux.go:39`）。

### 为什么

`-H` 每个字节会被展开成约 5 个字符（`0x2f 0x62 ...`）。iTerm2 因此被报过输入速度 bug（https://gitlab.com/gnachman/iterm2/-/work_items/10179）。逐字节 `exec` 还会把延迟乘上进程启动成本。`-l` 保持字面量，中文与空格不会被 tmux 再解释成绑定。

### 违反了会看到什么现象

- 整段可打印文本走 `-H`：打字明显变慢，CPU 在 tmux/服务端一侧升高，一串字母要「蹦」出来。
- 一字节一次 `send-keys`：延迟随字数线性变差，短词还行、长句卡顿。
- 可打印不走 `-l`：空格 / `-` / `"` 被 tmux 当成语法，注入内容与用户按的不一致。

## 7. 许可证边界：本仓 Apache-2.0；GPLv3 只许读，MIT 可参考可移植

### 决定是什么

本工程是 **Apache-2.0**（仓根 `LICENSE` 原文：`Apache License Version 2.0`）。

| 来源 | 许可 | 本工程允许做什么 |
| --- | --- | --- |
| xterm.js | **MIT** | **可参考，可移植**。移植必须保留其版权声明与 MIT 许可文本。序列表：https://xtermjs.org/docs/api/vtfeatures/ |
| Termux `terminal-emulator` / termux-app | **GPLv3** | **只能当参照实现阅读**。⛔ 不能 vendor、不能复制代码、不能把文件贴进本树。https://github.com/termux/termux-app |
| mosh | **GPLv3** | 同上：只读。预测回显的**思路**（本地预测 + 权威流收敛）可按本仓 Apache-2.0 重写；⛔ 不能搬它的源文件。https://github.com/mobile-shell/mosh |

**结论性的一句话**：可以抄 xterm.js（MIT，保留声明）；Termux 与 mosh 只许读不许抄（GPLv3 会污染 Apache-2.0）。

### 为什么

GPLv3 是 copyleft：把它们的代码搬进本树，本工程将无法维持 Apache-2.0 分发。用户目标是开源可被 corral-app / 桌面端引用，许可证污染会卡住引用方。xterm.js 的 MIT 与 Apache-2.0 兼容。

### 违反了会看到什么现象

- 源树里出现 Termux / mosh 的文件头或大段可对照原文：律师层面本仓不再是纯 Apache-2.0。
- 移植 xterm.js 却丢掉版权声明：MIT 条件没满足，同样侵权。
- 「对着 GPLv3 源文件改两行当自己的」：审查对原文即可证伪。

## 8. 改完仍不生效的已知坑

后继实测「点了没反应」时，先对这两条，再疑编码实现。

### 8.1 内层 app 自己没开鼠标上报 = 白改

- **判据现象：拖拽变成了选择复制。** 说明对面进程没进 tracking 模式，字节即使注入也对，终端只是在选文本。
- 验证：`script` 或 `cat -v` 看它有没有吐出 `\x1b[?1002h` 与 `\x1b[?1006h`。没有这两条，改我们这一侧无效。
- 出处：ttyd #218（https://github.com/tsl0922/ttyd/issues/218）。

### 8.2 tmux 层截获（见第 1 节）

- 现象：点击改变的是窗格/copy-mode，不是 Agent TUI。
- 先关 tmux `mouse`，再测 Agent。两条同时坏时，先修 tmux，否则永远看到「点不动」。

### 8.3 模式顺序在重连后静默退回旧编码（见第 4 节）

- 现象：第一次连上准，断网重连后坐标错、且无报错。不要先怀疑触控校准。
