# 081 · 后台久置回前台后，终端重排错乱

- 日期：2026-08-19
- 来源：用户实测 `.team/issues/shots/08-回前台重连后重排错乱.jpg`
- 基线包：`~/Desktop/agentmirror-ux3-07f5a1ca7.apk`

## 1. 现象

**用户原话**：「我在后台时间久了之后回到前台，由于它这个时候有重试重连的行为，
那么这个时候它必然重排是乱的。」

截图里的客观特征（不加推测）：
- 大量行**右端溢出一两个字符掉到下一行行首**，且断点在词中间：
  `…正好踩 0` / 换行 / `62`（应为 `062`）；
  `列表行的 S` / 换行 / `tatusChip`；
  `画到 c` / 换行 / `lip 边左侧被裁`；
  `必须是 p` / 换行 / `addingLeft`；
  `不得倒退 0` `76` `§` `1` 各占一行。
- 也有行右端出现孤立的 `→`、`t` / `.term`、`eme`。

⇒ **同一屏内存在两种换行宽度**：一部分内容按旧列宽已经折过行，
新内容按新列宽折行，两者叠在一起 ⇒ 视觉上就是"重排乱了"。

## 2. 归因方向（⛔ 未坐实，交给任务去量）

用户点明了触发条件：**后台久置 → 回前台 → 重试重连**。
可疑面在**列数（cols）协商**：`ConnectionManager.resize(ref, rows, cols)` 是唯一的协商入口。
候选成因（至少三种，判据必须能分开）：
1. **重连时按错误的宽度发了 resize**（例如用了后台期间被压缩/为 0 的 view 宽度）。
2. **重连后没有重发 resize**，服务端仍按旧 cols 折行，而 view 宽度已变。
3. **发了正确的 resize，但历史缓冲里的旧行不会被重折**——tmux 侧重折的是当前屏，
   已滚出的历史按当时的列宽定形 ⇒ 那部分**天然**是旧宽度。

🔴 第 3 种如果成立，那"必然乱"就是**真的必然**，修法不是"修 bug"而是
**重连后请求一次全屏重绘 / 丢弃并重取当前屏**，这是产品决策不是代码 bug。
⇒ **必须先分清是哪一种，再谈修法。**

## 3. 🔴 仪表不够，这是本条最先要补的

leader 核查：`termview/` 与 `session/` 下的 `DiagLog.record` 调用里，
**没有任何一条记录 cols 协商的操作数**。

按 2026-08-14 已立的诊断日志纪律——「凡是有守卫/阈值/比较的地方，
把参与比较的两边的原始数值都记下来」「光看导出的日志，就能判断出是
『该做而没做』还是『做了但做错了』」——现在这条做不到：
日志里既看不到重连时发了什么 cols，也看不到当时 view 宽度是多少。

**必须补的记录点（每条都要带两边操作数）**：
- `onResume` / 回前台：`view_width_px` `cell_width_px` `derived_cols` `last_sent_cols`
- 重连成功：`reconnect ok, resend_resize=<yes|no> cols=<n> rows=<n>`
- `resize()` 调用：`resize sent rows=<n> cols=<n> reason=<resume|rotate|ime|user>`
- 收到帧：`frame cols=<n>`（服务端认为的列宽）vs `render cols=<n>`（App 正在用的）

**判据 `A-rf-cols`**：导出的诊断日志里，
回前台后 30 秒内必须能读到 `derived_cols` 与 `frame cols` **两个数**，且两者相等。
🔴 不相等就是缺陷现场；**读不到这两个数就是仪表没做够，不算通过**。

## 4. 不得倒退
- 078 §1 终端左右内边距（`paddingLeft/Right` 影响 `colsFor` 的计算，改 cols 逻辑时别把它算漏）。
