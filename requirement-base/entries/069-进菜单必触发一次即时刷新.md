# 069 · 进入一级/二级菜单必须触发一次即时刷新

- 日期：2026-08-19
- 来源：用户「角色运行中还是空闲的状态更新太慢了。我老是点进去发现他在工作，出来才发现他在工作。
  进一级菜单、二级菜单的时候本来就应该更新一次，而不是等被动更新。被动更新是一方面，
  但你新进一次菜单，就得先更新一次。」
- 关联：061（2s 轮询 + 变更推送）、062（缓存优先，不得出现空列表帧）、068（白名单过滤）

## 1. 需求

**被动推送保留，但它不是唯一的刷新来源。** 每次**进入**一级或二级菜单，
必须立刻触发一次真实刷新，并在刷新结果到达时更新界面。

- 保留 062：进入瞬间先画缓存（**不得出现空列表帧**）。
- 新增：画完缓存的同时**强制发起一次新扫描**，结果到达即替换。
- 二者不是二选一：缓存负责「立刻有内容」，强制刷新负责「内容是对的」。

## 2. 根因（2026-08-19 读码定位，两级各一个，不是同一个毛病）

### 一级菜单
`wsConn.handleList` 调 `ensureInitialScan` —— 如其名，**只在第一次扫**。
此后每次 `list` 都直接返回 `currentSnapshot()` 的缓存。
⇒ **进一级菜单永远不重扫**，看到的是上一次扫描的世界。

### 二级菜单
`markLevel2` 只在订阅数 **0→1** 时向 `level2WakeCh` 发唤醒。
若 App 离开二级菜单时**不退订**、回来时**不重订阅**，服务端不会收到任何「用户又进来了」的信号，
于是不做任何额外动作。
⇒ 客户端侧看起来就是「状态是旧的，出去再进来才对」。

## 3. 判据（必须断言「世界变了」）

⛔ 不许写成「代码里有一次 scan 调用」——那是验东西在那儿。

- **A-rf-l1**：无人订阅时改变 tmux 世界（新建/销毁一个含白名单 CLI 的会话）
  ⇒ 客户端发一次 `list` ⇒ **返回的列表必须反映新世界**，不得是旧快照。
  🔴 此条须先在当前实现上**验红**（当前必红，因为 ensureInitialScan 不重扫）。
- **A-rf-l2**：无人订阅时把某节点从空闲切到工作
  ⇒ 客户端进入二级菜单 ⇒ **首个非缓存帧必须是新状态**，且**不得等满一个 2s cadence**。
- **A-rf-nocacheblank**：上面两条通过的同时，062 不得倒退——
  进入瞬间**不得出现空列表帧**（缓存优先仍然成立）。
- **A-rf-economy**：无人在菜单里时仍然零轮询（061 的零订阅零轮询不得倒退）。
  「进入时刷新」是**事件驱动的一次**，不是把轮询打开。

## 4. 边界

- 「进入」= 一级菜单打开 / 二级菜单打开。⛔ 不含列表内的滚动、旋转屏幕等，
  否则会退化成高频扫描，撞 061 的静默经济红线。
- 若强制刷新失败（tmux 不可达），**保留缓存内容**并按 061 的失败可见规则提示，
  ⛔ 不得因刷新失败而把列表清空。
