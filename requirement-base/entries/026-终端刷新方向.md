# 026 终端刷新方向：从下往上，新内容先到底部

- 状态：已裁定（必修，待定夺是否纳入本轮——见 [[037]] 的矛盾标注）
- 类型：缺陷 D-27
- 出处：用户 2026-08-12 真机测试原话「那个消息它是从整个 UI 整个会话界面的顶部开始往下进行刷新的。在慢的情况下，我要等很久才能够看到最新的回复」「我当前是在 TS 的局域网去和你沟通的，这个东西是不是刷的太慢了？」

## 缺陷现象

发消息后画面从整个 UI **顶部**开始往下刷新，慢网络下等很久才看到最新回复。

## 裁定行为

改为**从下往上刷新**——新内容先出现在底部。同时排查 TS 网络下刷新偏慢是**渲染瓶颈**还是**传输瓶颈**。

## 后续观察与回炉（2026-08-12 01:3x–01:5x）

- **R-006 定夺**：D-27 **纳入本轮修复**（用户验收中发现的缺陷，性质等同 D-20~D-25）。本轮修复范围 = D-20~D-27 共 8 条。登记于 REVISIONS.md R-006 定夺。
- **01:3x 观察**：只有发消息后才出现「从上往下逐行刷新、底部旧内容」现象。Claude Code 自己工作时（工具调用、打印输出）**没有**这个问题。推测：发送 input 后触发了某种全屏重放（可能是 resize 导致的 snapshot 重发），snapshot 从顶部开始写入 xterm 导致逐行刷新。
- **01:5x 复测**：该现象是**概率性非必现**，只在发消息后出现。进一步指向 **input_ack 或 input 触发的某条路径偶尔引发全屏 snapshot 重放**。
- **第二次回炉（用户质疑）**：如果分块太小是根因，为什么只在发消息后出现、CLI 自己吐字时不出现？两者本质都是 CLI 底部追加内容。推论：**分块大小可能不是真正根因**，两个场景的数据路径可能有差异。方向：找到「发消息追加」和「CLI 自己吐字追加」的差异点，**统一实现**。出处：用户原话「这种一个场景两个实现，其中一个场景无问题，另一个有问题的解决办法是不是改为一致更好」。
