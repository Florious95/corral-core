# 098 会话打开速度（tap→完全排布）优化方案

来源：2026-08-21 Opus 专项审计（完整方案 .team/artifacts/open-latency-plan.md，
原始 findings/verdicts .team/artifacts/audit-20260821-open-latency.json）。用户目标：打开点击到完全排布好提速。

## 核心归因（算术可证伪）
首帧 1794ms 中约 1670ms = Subscribe 帧在 ws readLoop 里**排在全量扫描帧之后**
（enterSessionLive 的 Level2Subscribe/List → 全量 Discover：23 socket 串行 exec、死 socket 5s 超时、
proctree 全表 ps 持锁）。裸客户端无扫描帧 ⇒ 108ms。handleSubscribe 本体仅 ~110ms（11 次 tmux exec）。

## 工作项（P0 为 2s 门主项）
- P0-a 服务端逐帧时间戳量具（先红判据 queue_ms>700→修后<50）
- P0-b 扫描帧移出 readLoop（List 已在 storm 分支、**补 Level2Subscribe**）+ Discover 并发化(上限8)
  + 死 socket 超时 5s→500ms + proctree 缓存合入 + readProcTable 出临界区
- P1 视口几何 seed 一次到位（persistViewportGeom 落 emulator.rows/cols；cache 按窗口宽分键；INITIAL_COLS 120→手机量级）
- P2 收帧口前移（vm.start() 显式化；⚠️ 必须排 P0-b 之后验收）
- P3 前半 bridge exec 压缩（11→3~4 次）；P3-linger 与「缓存旧帧秒显」两项【交用户裁】
- P4 渲染热路径卫生（presenter setter 守卫、onDraw 里 DiagLog 每帧调用摘除——量具卫生非卡顿修复，诚实标注）
