## 1. D1 · `userBlockBg` 写死成 APP 常量，永不跟主题（已实证）

`TermPalette.assembleSlot()`：

```kotlin
userBlockBg = app.userBlockBackground.toArgb()   // ← 只认外壳深浅，不跟主题
```

`TerminalSpec.kt` 里深色外壳的该常量是 `0xFF10241F`。

**像素实测（leader 亲量，非推测）**：

| 位置 | 实测色 |
|---|---|
| Grok 整块面板底 | `#0f241f` |
| Claude Code「已发送的用户消息」块底 | `#0f241f` |
| 同屏普通终端底 | `#1f1f27` |

`#0f241f` 就是 `0xFF10241F`（JPEG 压缩差 1）。主题底 `#1f1f27` 说明
`defaultBg/defaultFg/ansi16` 这条链是通的，**唯独 `userBlockBg` 不换**。

而 `userBlockBg` 是一个大汇水口，`colorFor` 有四条路排进它：
索引 254；索引 231/253/255 作底；`guardRgbBg` 中 `luma ≥ 220` 的两条分支。

⇒ **违反 085 §1.5**：重着色的语义是「任何颜色都必须投影到当前主题色板」，
存在一条逃出主题的路径，语义就不闭合。

### 方案（已定）

`userBlockBg` 从**当前主题现算**：

1. **优先用该主题自带的 `selection` 色**（上游 iTerm2 scheme 自带，语义最贴＝「被强调的一段文本的底」）；
2. **缺失、或与 `defaultFg` 对比度不达标时，回退**「从 `defaultBg` 朝 `defaultFg` 抬一档」。

两条都有 ⇒ 任何主题都不开天窗。

### 判据

- `A-089-d1-theme`：至少三个差异明显的主题，断言 `colorFor(Indexed(254), background=true)`
  的输出**互不相同**，且每个输出都可由该主题的 scheme 派生（`selection` 或 `defaultBg→defaultFg` 抬档）。
  🔴 先验红：当前实现该值恒为 `0xFF10241F`。
- `A-089-d1-esc`：断言**不存在任何输入**使 `colorFor` 返回一个不属于当前主题派生集合的颜色
  （穷举 256 索引 + 抽样真彩）。这条断言的是「逃逸路径已封死」，⛔ 不是「这一条改好了」。

## 2. D2 · Grok 整屏被染成用户块底（根因未定，⛔ 先补仪表）

用户明确：**Grok 是黑底白字**。黑底应走 `guardRgbBg` 的 `luma ≤ 32 → defaultBg`，
本应变成主题底 `#1f1f27`，**却变成了 `userBlockBg`** ⇒ 有别的分支抢先命中了
（近白索引 231/253/255、索引 254、或 `luma ≥ 220` 的真彩底）。

🔴 **从外部分不出是哪一条**，因为 `guardRgbBg` 与 `indexed` 的**四条分支一条日志都没有**。
按诊断日志纪律（记判据的操作数，不只记判决），现在做不到
「光看导出的日志就判断出是该做而没做、还是做了但做错了」。

⇒ **D2 的修复判据现在写不出来，⛔ 不入账本。**先做的是 **D2-meter**：

### D2-meter 判据

- `A-089-meter`：`guardRgbBg` 与 `indexed` 的**每一条分支**各记一条 `DiagLog`，
  内容必须含**参与比较的两边的原始数值**：输入 rgb、`luma`、`chroma`、命中哪条分支、输出 argb。
  单测覆盖四条分支，断言各产出一条含上述全部操作数的记录。🔴 先验红。
- 仪表落地后，取用户真机导出的诊断日志定位，**再写 D2 的修复判据**。

⚠️ **光修 D1 不会让 Grok 变回黑底**——绿色会变成「主题派生的用户块色」，
颜色变了，但**整屏被染色这件事还在**。D1 与 D2 必须分开验，⛔ 不许合并成一格判绿。

## 2.5 D2 实测证据二（2026-08-21，**浅色主题上的同一条缺陷**）

用户真机截图：**浅色主题**（终端底实测 `#feffff`）下，终端视图上方约 40% 被一整块
**`#464646`** 糊住，下方内容正常。

**leader 像素实测 + 代码对照**：`#464646` 是 `TermSchemes.kt:327`
「Apple System Colors」主题的 **ANSI 索引 8（bright black）**。
⇒ **有一大片区域被用 ANSI 8 当背景刷了**，而不是主题的 `defaultBg`。

### 这条与 §2 是同一个缺陷，不是新缺陷
- Grok 那次：大片区域被染成 `userBlockBg`（`#0f241f`）。D1 已封死那条路径。
- 本次：大片区域被染成 **ANSI 8**。⇒ **逃逸口换了一个，问题没换。**
- 共同形状：**某个大面积背景色没有落到 `defaultBg`，而是被投影到了某个 ANSI 槽**。
  这与 085 §1.5「任何颜色都必须投影到当前主题色板」不冲突——
  它确实落在色板内，**但落错了角色**：背景应当优先落 `defaultBg`，而不是就近落某个 ANSI 槽。

### 🔴 判据方向（写死，⛔ 不许只改这一个色值）
- **`A-089-d2-role`**：断言「大面积背景」的投影**优先落 `defaultBg`**，
  ⛔ 不是就近落 ANSI 槽。要能区分两个世界：构造一个 OKLab 上离 ANSI 8 更近、离 `defaultBg` 稍远的
  背景色，断言它仍落 `defaultBg`。先验红（当前会落 ANSI 8）。
- **⛔ 不许把 `#464646` 特判掉**——那是修症状。下一个主题的 ANSI 8 是别的值，问题原样复现。
- **定位必须用仪表**：`t.meter` 已落地，`guardRgbBg`/`indexed` 四条分支各记
  输入 rgb / luma / chroma / 阈值 / 命中分支 / 输出 argb。
  ⇒ **先从用户导出的诊断日志里读出「哪条分支、输入是什么」，再写修复判据。**
  ⛔ 在拿到那行读数之前不入账本（同 §2 的规矩）。

### 待办：需要用户导出一次诊断日志
搜 `term-remap` / `guard` 相关记录，看命中的是哪条分支、输入 rgb 是多少。

## 3. E6 · 「已附加图片」成功态仍组节点（已实证）

上一轮（083 §12）修了「已发送」蓝色堆叠，但**同一个函数里紧挨着的兄弟成功态没动**：

```kotlin
SessionScreen.kt:485    is InputStatus.Sent      -> null          // ← 上一轮修的
SessionScreen.kt:491    is UploadStatus.Success  -> "已附加图片"   // ← 原样留着
```

⇒ 上传图片/附件后仍会出现同形状的悬浮堆叠文本。

🔴 **本条必须在成功态的共同出口上修，⛔ 不许再补第二个 case。**
这正是「修一次，修在所有调用方都经过的地方」——上一轮修的是症状点。

### 判据

- `A-089-e6`：断言 `InputStatus.Sent` 与 `UploadStatus.Success` **都不组节点**。
- `A-089-e6-struct`：**结构性判据**——新增任意一个「成功态」，默认不组节点。
  🔴 这条断言的是「共同出口已存在」，⛔ 不是「这两个 case 都改了」。
- `A-089-e6-ui`：user gate——真机上传一张图片，截图确认无悬浮堆叠文本。
