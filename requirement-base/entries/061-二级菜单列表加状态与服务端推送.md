## 一、交付物形态（一次做完，不分阶段）

二级菜单 = **一个列表**，形态与当前一致。每行：

- 会话标识（会话名 / 所在 socket / 所在文件夹）
- **右侧一个状态标：进行中 / 空闲 / 未知**
- 点一行进入该会话（三级终端）

## 二、数据来源

| 字段 | 来源 | 规则 |
|---|---|---|
| 会话名 / 窗口 / socket / 文件夹 | tmux 格式串直接取**结构字段** | 不解析渲染出来的 `Ctrl-B w` 画面（对齐、截断、树线、CJK 宽度都会咬人） |
| 状态 | `pane_title` 前面的符号 | 服务端持符号表判定 |

符号会随 Agent CLI 变化 —— **那就改代码把新符号加进表里**。这条是可维护的，前提是下一条成立。

## 三、🔴 认不出的符号：记日志 + 显示未知，绝不猜

- UI 显示 **未知**，不得回落成「空闲」。前四轮的死法就是猜一个 idle 顶上，结果是**自信的错误**。
- 日志**必须记下没认出来的那个符号本身的 Unicode 码点 + 完整原始标题**。
  只写「符号未知」等于什么都没说——你知道有未知，但不知道该往表里加什么。
  （本工程诊断日志纪律：**记判据的操作数，不只记判决。**）

## 四、时效与推送

- **端到端状态延迟上限 5 秒**（用户定）。
- 服务端轮询 + **变更时推送**给 App；App 只收不轮，减少手机侧损耗。
- 轮询周期 **2 秒**，给传输与渲染留余量。
- 🔴 **零订阅者 ⇒ 零轮询**：没有客户端在看二级菜单时，服务端一次 tmux 都不调
  （工程常识红线①：空闲 CPU 趋近 0）。手机绝大多数时间不在看，这是常态不是边角。
- 🔴 **只推变更必须配低频心跳**：否则 App 分不清「没变化」和「连接死了」，
  故障形态是界面停在旧状态且看起来完全正常——又一个静默失败。
