# 060 二级菜单改为实时流，并以此取代整个状态判定

- 日期：2026-08-15
- 裁定人：用户（原话见下）
- **取代**：`docs/rulings/20260815-用户裁定原文-直通输入与刷新模型.md` §四 中**关于二级菜单**的三条不变量
  （进入即刷 / 下拉手动刷 / 零周期性自动刷新）。**该三条收窄为只管一级菜单。**
- **取代**：`058-状态检测先归档回退再重建.md` 的「重建」部分——**不再重建，整个删掉。**

## 一、裁定原文

> 「这肯定是裁定，这个二级菜单，也就是会话列表那个菜单，**是要实时展示的**，
> 而不是之前的周期性、非周期性以及手动刷新。」

> 「二级菜单就应该是实时流了。……**实际上二级菜单整个模块都应该拿出来回退。**
> 你要找到精确找到对应的代码，并且**把受影响的代码给它连根拔起**，
> 否则它的存在就会影响我们后面的迭代。」

## 二、新形态：二级菜单 = `Ctrl-B w` 的重绘

用户看到的数据结构（用户截图实证）：

```
(0) - team-agent-leader-claude_code-Agent-824c7e38-eb74-18c
(1)  └─> + 0: claude_code*: "◐保留V5代码保证审查参考"
(2) - team-remote-agent-android: 5 windows
(3)  └─> + 0: librarian-: "✳ librarian"
(4)  └─> + 1: dev-state: "✳ dev-state"
```

**`◐` / `✳` 本来就在 pane 标题字符串里。**

### 🔴 核心不变量：标题原样显示，一个字符都不解析

- **显示**：`pane_title` 原样画出来，含前缀符号。不识别、不匹配、不映射、不美化。
- **身份**（点某一行跳进哪个会话）：只用 tmux 的**结构字段**
  `session_name` / `window_index` / `window_name`。**不得从标题字符串里抠。**
- 划清这条的理由：混在一起之后，下一个人会以「反正都要解析」为由把标题也解析了。

## 三、为什么这条能终结前四轮的失败

前四轮每一轮都在造「符号识别层」，而**那个符号是 Agent CLI 自己定的，随时可改**：
第四轮的白名单里装的是盲文点阵 `⠋⠙⠹`，而 Claude Code 已换成 `◐`——判据当场变瞎，
**且是静默变瞎**（不报错，只是永远判 idle）。

用户给出的判据（本条是整套方案的地基）：

> 「它再怎么变，它也要让我作为用户能够识别到它在工作还是没工作。」

⇒ **「人能看懂」是 CLI 厂商自己的利益，永远成立；「机器能解析」从来不在它的考虑里。**
⇒ 把判断放在有保证的那一环（人眼），判断就不会瞎。

## 四、刷新模型收窄后的完整口径

| 层级 | 是什么 | 规则 |
|---|---|---|
| 一级（tmux socket / 工作目录） | 列表 | 进入即刷一次 + 下拉手动刷 + **零周期性自动刷新**（不变） |
| 二级（会话列表） | **实时流**（本条新裁定） | 流，不适用刷新规则 |
| 三级（终端画面） | 实时流 | 不变 |

## 五、连根拔起的范围

**整体归档回退，不在坏基线上改**：

- `server/internal/agentstate/`（状态判定，不再重建）
- protocol 的 `state` 字段（大概率一并废，实现时确认）
- App 侧状态徽章 / `AgentState` 枚举 / `StateBadge*` / `StateWatcher` 的状态分支
- 二级菜单原有的列表模型：下拉刷新、进入即刷、以及围绕「列表项 = 会话」的点击进入行为

**保留**（与三级共用，不属于本次回退）：WebSocket 传输、帧编解码、一级菜单的刷新模型。

## 六、工程红线约束

- 实时流**只在二级菜单打开时**拉数据，关掉即停——否则违反工程常识红线①
  「空闲 CPU 趋近 0、无固定频率子进程派生」。此条必须写成机械判据，不靠自觉。
- 不 attach tmux 客户端（用 `list-panes -a` 取数或 control mode 推送），
  避免多客户端参与尺寸谈判、压小用户真实窗口。
