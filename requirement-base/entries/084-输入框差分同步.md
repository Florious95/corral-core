# 084 · 输入框改差分同步（本地完整编辑 + 实时最小按键）

- 日期：2026-08-19
- 来源：用户提问「前面有个字要修改……它是**永远的增量模式**……有没有好的解决办法？」→ leader 给三方案 → **用户选 C，并要求实时**

## 1. 问题

现状是**逐键直通**（契约「直通输入：每键直达 CLI 输入框，含删除键」）：
手机输入框是"发射器"，CLI 那边才是真正的输入行。
⇒ 手机上的「移动光标、改中间的字、删中间一个字」**没有对应的东西可发**。

## 2. 方案（已定：C 差分同步）

leader 给过三条，用户选 C：

| | 做法 | 为什么不选 |
|---|---|---|
| A 逐键翻译 | 把编辑翻译成 `←`×N + 退格 + 插入 | ❌ 要知道 CLI 当前光标在哪，我们不知道；中文组合期会乱发 |
| B 发送时整行提交 | 本地完整编辑，按发送才送 | ❌ `/` 命令菜单、`@` 文件补全、Tab 补全、↑↓ 历史全废——它们依赖逐键 |
| **C 差分同步** | 本地完整编辑，**每次变化实时**算差分发最小按键 | ✅ 选它 |

**算法**：
```
prefix = 公共前缀长度(已同步文本, 当前文本)
发送:  BackSpace × (len(已同步) - prefix)  +  当前文本[prefix:]
已同步 = 当前文本
```

**为什么划算**：
- **常见路径零代价**：正常往后打字时 `prefix == len(已同步)` ⇒ 退格数 0 ⇒ 退化成今天的纯追加，行为与今天完全一致。
- **只有真的往前改时才发退格**，而那正是今天完全做不到的场景。
- 🔴 **补全菜单保住了**：CLI 收到的仍是逐键输入，`/` `@` `Tab` 照常工作。这是 B 丢掉、C 留住的东西。
- 不需要知道 CLI 光标位置——**约定同步后光标永远在行尾**，差分只需"退到公共前缀 + 补后缀"。

## 3. 🔴 用户要求：必须实时，⛔ 不是发送那一刻才同步

**用户原话**：「你提出来的差分同步我认可，但我希望它是**比较实时的**，而不是我发送那一刻，它在同步。」

⇒ **每次文本变化立刻算差分、立刻发。**
唯一允许延迟的是**中文输入法组合期**（`TextFieldValue.composition != null`）：
候选未确定时输入法会反复改文本，那段文本还不是用户要的，发过去 CLI 会收到一串垃圾再撤销。
⇒ **组合期攒着，上屏那一刻立即发**。英文/数字没有组合期，**一个字符都不许延迟**。

## 4. 前置

`t.chrome` 的「`BasicTextField` 改 `TextFieldValue` 重载」是本条前置——
没有 `TextFieldValue` 就拿不到 `selection` 和 `composition`。

## 5. 判据

- `A-df-append`：纯追加场景，发出的**退格数 == 0**，发出的字符序列与今天逐键直通**完全一致**（🔴 这条防的是"为了做差分把常见路径搞复杂/搞慢"）。
- `A-df-edit`：把光标移到中间删一个字再插一个字 ⇒ CLI 侧最终文本 == 手机侧文本。
  🔴 断言**两边最终文本相等**，⛔ 不许只断言"发了退格"。
- `A-df-ime`：中文组合期（拼音串在候选中）**不得发出任何按键**；上屏那一刻**立即**发出（延迟 ≤ 1 帧）。
- `A-df-latency`：英文逐字输入，从 `onValueChange` 到按键发出**不得引入额外延迟**。

## 6. ⚠️ 必须先量、再决定要不要加合并（⛔ 不许拍脑袋）

改中间一个字可能要连发十几个键。**CLI 对快速连发退格的吞吐未知**。
⇒ 先量两个数：**单次编辑发出的按键数** 与 **CLI 侧重绘/回显耗时**，写进说明。
量完再决定要不要加合并或极短延迟；🔴 若要加，**延迟上限 50ms**，且必须写明它与 §3「实时」的取舍。
