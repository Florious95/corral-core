- 截图：`.team/issues/shots/11-浅色下框线断点与logo黑底.jpg` / `12-已发送提示与卡片间距过大.jpg` / `13-输入框不能往前编辑.jpg`

## 🔴 0. 先记一条比六条本身更重要的：**模拟器验收在渲染层没有分辨力**

**用户原话**：「上面的那个展示的问题，在**模拟器上是完全正常的**，但是我在我**手机上就完全不正常**。」

⇒ 用户此前裁定的「模拟器 1:1 还原我手机」**在渲染层不成立**：
密度、字体 fallback 链、亚像素取整策略都不同。
**模拟器绿 ≠ 真机绿。** 此前 `t.clip` / `t.term` 那几格的绿，对真机的保证比 leader 以为的弱。

**修法（本轮必须做）**：判据不能只跑一台。
建 2–3 个**不同 density** 的 AVD（**3.0 整数 / 2.75 或 3.5 非整数**），同一条 `ui-check.sh` 跑多遍。
🔴 **非整数密度那台才是真正的守门员**——整数密度会把取整误差掩盖掉。

## §1 框线断点 + logo「黑底」= **同一个根因**

用户先报「线段中间有断点」，再报「Claude Code 那个图标存在黑底、长得很别扭」。
放大图（`11-…jpg`）显示：logo 不是有黑底，是**块与块之间接不上、缝里露出了背景色**。

**机理**：框线（U+2500–257F）与块元素（U+2580–259F）在 `GlyphSlot.kt` 里走**同一条 `SYSTEM_FALLBACK` 路径**，
而该路径是 `TermSurfaceView.drawCentered`——**逐格把字形在格内居中**：

```kotlin
val actual = paint.measureText(text, i, j)     // 字形自然宽度 < 格宽
centeredGlyphX(x, cellPx, actual)              // 居中 ⇒ 两侧各留 (cellPx-actual)/2
```

⇒ 每格左右各留一条空 ⇒ 框线接不上（断点）、色块接不上（露背景）。

🔴 **为什么模拟器看不出来**：模拟器 density = **整数 3.0**，`cellW` 是整数、`advance` 恰好贴合；
真机是**非整数密度**，`cellW` 带小数，逐格取整累积 0~1px 误差 ⇒ 缝显影。
⇒ 根因准确表述是：**绘制依赖「字形自然宽度 + 亚像素取整」，在非整数密度上必崩**。居中只是放大器。

**修法（选定）**：这两类字符**改用 Canvas 画几何，不用字形**。
- 块元素：`█` 整格 / `▀` 上半 / `▄` 下半 / `▌` 左半 / `▐` 右半 / `░▒▓` 按密度
- 框线：128 个字符映射成「本格画哪几条边 + 粗细」，格边界按**整数像素**对齐

✅ 附带收益：**免疫换字体**——将来换终端字体，框线和块不会跟着崩（呼应 078 讨论的字体可换性）。

## §2 显式背景色不受主题控制（两个表现）

**用户原话**：「Claude Code 它黑底白底唯一的问题，那就是**我发的消息，它依然是白底，不是灰底**。
然后 **grok 的黑底，在白色的手机主题上，它不会展示为白色**。」

**机理**：我们翻转的是**默认背景**；CLI 用**显式背景色**画的块（Claude Code 的用户消息高亮、grok 的整屏底色）不受影响。
它们假设自己跑在深色终端上，于是浅色主题下留下白块/黑块。

**修法**：做**背景色重映射**——CLI 说「用 X 号色当背景」，按当前主题把 X 映射成合适的值。
设计包已备好 `TerminalPalette.userBlockBackground`（浅 `E6F5F2` / 深 `10241F`），只是没接到重映射上。

🔴 **必须先查清是哪种颜色再动**（⛔ 不猜）：
| 类型 | 能不能翻 |
|---|---|
| ANSI 索引色（16/256） | ✅ 能重映射 |
| 反显 `\033[7m` | ✅ 能特判 |
| **24 位真彩色 `\033[48;2;r;g;b`** | ❌ 翻不了（`TerminalColor.Rgb` 原样画），只能做**亮度守卫**（浅底下压暗、保色相） |
⇒ 抓一次原始字节定案，把结论写进说明。

## §3 卡片与终端的**两层间距**过大

**用户原话**：「Agent CLI 它就已经预留成一个带弧边的卡片了，这个卡片本身它边上就有很大的间距，
首先这个间距要减少。第二点，它真实展示的内容，也就是这个卡片内部的左右，它又留了比较大的间距，
**这两个间距都要缩小**。」

```kotlin
Surface(                                      // 卡片
  .padding(Dims.terminalCardMargin)           // 第一层：外 8dp
  color = currentTerminalPalette().background // 卡片底色 = 主题终端底色
) { terminalContent() }                       // 自绘 SurfaceView
      TerminalMetrics.paddingLeft/Right = 14dp // 第二层：内 14dp
```

⇒ 屏幕边到首字符 = **8 + 14 = 22dp**（density 3 时 66px），横向吃掉 3–4 个字符位。

⚠️ **卡片与终端本该同色、看不出分界**；用户看到「白卡片 + 黑内容」是 §2 那条把它显影了。
⇒ **§2 修好，观感好一大半；但间距本身也确实过大，一并改。**

**取值（leader 定，附依据）**：
| | 现在 | 改为 | 依据 |
|---|---|---|---|
| 卡片外边距 | 8dp | **4dp** | 保留圆角呼吸，不贴死屏幕边 |
| 终端内 padding | 14dp | **6dp** | `t.clip` 实测首列左溢 11–13px，6dp×3 = 18px 仍盖得住 |

🔴 **联动必须一起做**：padding 减少 ⇒ 可用宽度增加 ⇒ **cols 变多** ⇒ CLI 可能切回宽布局
（就是用户真机上出现过的 Tips 双栏）。⇒ **必须同时加 cols 上限**，否则修一个坏一个。

## §4 「已发送」提示突兀

**用户原话**：「点击发送之后，它上面有一个**已发送**的三个字，很突兀，这个要删除。」

位置：`SessionScreen.kt:486` `is InputStatus.Sent -> "已发送"`，叠在终端内容上方。

🔴 **只删成功态，保留失败态**：那个状态机是「必达」语义的一部分
（`SessionViewModel.kt:104` 注释：「ok 显示已发送 / fail+超时明确报错」）。
⇒ 默认无提示、**出错才出声**，符合 061「失败可见」红线。
⛔ 不许把整个状态机删掉。

## §5 输入框不能往前编辑

**用户原话**：「当前的输入框，它**不能往前面去编辑**。」

**机理**（已定位）：`SessionShellScreen.kt:398` 用的是
```kotlin
BasicTextField(value = draft: String, onValueChange = onDraftChange, ...)
```
**String 重载不持有 `TextFieldValue`，光标位置由 Compose 内部管理**；
外部 `draft` 每次回写都会把 selection 重置到末尾 ⇒ 光标移到中间后一重组就跳回去 ⇒ 「不能往前编辑」。

**修法**：改用 **`TextFieldValue` 重载**，由调用方持有 `TextFieldValue`（含 `selection`），
⛔ 不要只传 String。判据要断言：把光标移到中间 → 触发一次外部状态更新 → **selection 不变**。

## §11 真机证据补齐：框线断点 / logo 黑缝（用户 2026-08-20 实测确认）

**用户原话**：「这个解决了，很不错」
**证据**：用户真机截图，Claude Code 启动欢迎框（`v2.1.219`）。

| 观察点 | 真机结果 |
|---|---|
| 框线 U+2500–257F（`┌ ─ │ ┬` 等） | **连续无断点**，横线跨格接得上，竖线与横线交点闭合 |
| logo 块字符 U+2580–259F | **无黑缝**，方块之间不再露底 |
| 浅色主题下整屏 | 纸色近白，logo 与文字未被套上暗格 |

### 为什么这条要单独记

独立验收席 `vz-v1-ver` **两轮都拒绝给这两条判「通过」**，原文：

> **证据不足。** 本场会话是 Claude 圆角卡片，屏上没有 U+2500–257F 夹具，无法量相邻格 `right/nextLeft`。
> 截图未见线段断点，**不能当成真机非整数密度已修**（083 §0）。
> …`userBlock` 像素在 `shot-d480-session.png` 上 **hits=0**。不能用「看起来没有黑底」收工。

⇒ **它的拒绝是对的**：模拟器那一场屏上根本没有被测字符，单测几何绿证明不了真机渲染绿。
⇒ 缺的这一环**只能由真机补**，而 083 §0 早就写明「**用户真机才是权威被测对象**」。

**这一条同时是对「模拟器在渲染层没有分辨力」的又一次确证**：
同一份代码，模拟器给不出结论，真机一眼可判。
⇒ 纪律不变：**渲染类缺陷，模拟器绿只是必要条件，真机截图才是终局。**

### 仍未由真机确认的（⛔ 不许因为这次绿了就一并当过）

## §12 🔴 回归：「已发送」又出现了，而且是**蓝色悬浮、多个堆叠**（用户 2026-08-20 实测）

**用户原话**：「有回归，那就是我发送消息，**键盘上面有已发送几个蓝色悬浮堆叠字**」

### 为什么这条是回归而不是新缺陷

083 原本就有这一条，且**已经判过绿**：

> ### 发送成功后无「已发送」；失败仍有错误提示
> **通过（成功态 UI + 失败态单测）。** 两密度 `uiassert absent 已发送`。
> `SessionScreen` `is InputStatus.Sent -> null`，仍有 `InputStatus.Failed`。
> 单测 `VzVerifySentHidesSuccessKeepsFailure`：Sent 无「已发送」，Failed「发送失败：超时」显示。
> —— `vz-v1` `t.ver` 独立验收报告 r19

⇒ **判据绿过，真机又出现了。** 而且用户描述比原缺陷更严重：
原来是「一个突兀的『已发送』」，现在是「**几个蓝色悬浮堆叠**」——数量与层叠是新的。

### 已知的可疑改动窗口

r19 判绿之后、本次真机之前，动过会话页/输入区的有：
- `vzfix-v1` `t.live`（会话页在屏订阅 + 顶栏灯）
- `vzfix-v1` `t.align`（顶栏墨迹对齐）
- `theme-v1` `t.wire` / `t.settings`（主题接入绘制层、设置页新增卡）
- `perf-v1` `t.perf`（**正在施工中**，热路径缓存）

⛔ **不许凭「最可能是谁」直接改**，先复现再定位。

### 判据要求（下一轮排单照抄）

1. **先复现**：模拟器上真发一条消息，`uiassert has 已发送` 必须**先红**（能看见），
   截图 + UI 树留证。⛔ 复现不出来不许开工。
2. **数量也要断言**：不只断言 `absent 已发送`，还要断言**同一时刻屏上「已发送」节点数 == 0**——
   「堆叠」说明旧实现可能是**每次发送新建一个节点且从不移除**，
   只测「有没有」会漏掉「有几个」。
3. **失败态不得被一并干掉**：`InputStatus.Failed` 的「发送失败：…」必须仍然显示
   （原判据就有这一条，⛔ 不许为了让成功态消失而把失败提示一起删）。
4. 双 density；截图前关输入法（`keyevent 111`）——⚠️ 但本条被测对象**就在键盘上方**，
   关输入法可能让它不可见 ⇒ **本条允许在开着输入法的状态下取 UI 树**，
   但截图要注意不要把输入法候选栏里的敏感内容拍进去（凭据红线）。

### 🔴 这条暴露的方法论问题（记下来，比这个 bug 本身重要）

`t.ver` 那轮对这条的证据是「两密度 `uiassert absent 已发送`」+ 单测。
**但那一场里席位并没有真的发一条消息**——验收报告自己写着
「本场未在模拟器上注入一次真实发送失败」，成功态也是看的**静态屏**。
⇒ **`absent` 在「根本没发生过发送」的屏上恒真。**
这正是「判据要能区分两个同形世界」那条铁律被违反的实例：
**「发过了但没显示」和「压根没发过」在 `absent` 断言下完全同形。**

⇒ 纪律：**凡是断言「某物不应出现」的判据，必须先制造出让它有机会出现的条件**，
并在同一脚本里证明那个条件真的发生了（例如先断言消息真的进了终端正文）。
⛔ 只断言 `absent` 而不制造触发条件的判据，是一个恒真判据。
