## §0 许可裁定（**先定这条，它决定了后面全部做法**）

### 已核事实（不是推测，逐条有来源）

| 事实 | 来源（可复核） |
|---|---|
| Heeler 是 **AGPL-3.0** | `gh repo view ZingerLittleBee/Heeler --json licenseInfo` → `agpl-3.0` |
| Heeler 是 iOS 上的 agent 控制台（SSH + libghostty 终端 + 配对 + 推送） | 同上 `description`。**和我们是同一个产品形态，只是 iOS + Swift** |
| Heeler 的主题**不是它自己的**，来自 Ghostty，而 Ghostty 的来自 iTerm2-Color-Schemes | `Sources/Heeler/Resources/Notices/GhosttyTheme-MIT.txt` |
| 该 notice 原文写明色值来源与许可 | 「Color scheme data sourced from iTerm2-Color-Schemes … Copyright (c) 2011-present Mark Badolato」，**MIT** |

### 裁定

1. ⛔ **一行 Heeler 的代码都不许抄。** 我们是 Apache-2.0，AGPL-3.0 是强传染 copyleft，
   把它的源码/资源并进来会把**整个 APP** 拖进 AGPL（还额外附加「网络交互也要放源码」那条）。
   这不是风格问题，是许可不兼容。
2. ✅ **色值直接从上游 `mbadolato/iTerm2-Color-Schemes`（MIT）取**，⛔ 不从 Heeler 转手。
   MIT 与 Apache-2.0 兼容，随包附 MIT 声明与版权行即可。
   **Heeler 自己就是这么做的**——它给这批色值单独放了一份 MIT notice，
   说明这批数据在它那儿也不是 AGPL 的一部分。
3. ✅ **Heeler 只能当「参考」，参考的是想法不是表达**：做哪些主题、设置页怎么组织、
   深浅怎么配对。**想法/事实/清单不受版权保护，具体代码表达受。**
   ⇒ 允许：照着它的主题清单选型、照着「族 + 深浅 + 跟随系统」的信息架构设计。
   ⇒ 禁止：照抄它的 Swift 文件结构/命名/注释/测试。
4. 🔴 **产物里必须有 `NOTICE` 或等价文件**，写明这批色值来自 iTerm2-Color-Schemes、MIT、
   版权行照抄。缺这个 = 我们违反 MIT。

### 为什么这条要单独立契约

用户点名「因为它的开源仓库是 AGPL」——他要的是**我先把边界说清楚再动手**。
一个把 AGPL 代码抄进 Apache-2.0 产品的改动，事后回退不掉（已发布的版本已经违约）。
⇒ 这条是**前置门**，思路席的第一产出就是它的落实方案，不是事后补声明。

## §1 要做什么

把一批成熟终端配色**录进设置页**，用户可选，会话页终端按选中的主题渲染。

### 主题清单（照 Heeler 的选型，共约 30 族，每族深/浅两套）

Afterglow / Alabaster / Apple System Colors / Atom One Dark / Ayu / Catppuccin(Latte·Mocha) /
Dracula / Everforest / Flexoki / GitHub / Gruvbox / Horizon / Iceberg / Kanagawa(Lotus·Wave) /
Melange / Modus(Operandi·Vivendi) / Monokai Pro / Night Owl / Nord / Oceanic Next /
One Dark / One Half / Poimandres / Rose Pine(·Dawn) / Selenized / Snazzy / Solarized(iTerm2) /
Tokyo Night(Day·Night) / Tomorrow(·Night) / Vesper / Zenbones / Zenburn

⚠️ 这是**清单**不是最终定案。思路席要核对每一个在 iTerm2-Color-Schemes 里的**准确文件名**
（同名不同拼写很常见：`Rose Pine` vs `RosePine`），核不到的**明写核不到**，⛔ 不许拿相近的顶上。

### 设置项形态（照 Heeler 的信息架构）

从它的键名读出来的模型：`follow-system` / `terminal-theme` / `terminal-theme-dark` / `terminal-theme-light`
⇒ **一个「跟随系统」开关 + 深色下用哪个主题 + 浅色下用哪个主题**（不是单选一个）。

🔴 **必须与 083 §2 已落地的浅/深两套自适应对齐**，⛔ 不得倒退：
083 §2 的裁定是「APP 自带深浅两套、自动适配；浅色 = 白底 + **灰底**用户消息块」。
主题库是在那之上**换终端正文的 16 色板 + 前景/背景**，不是把 083 §2 推翻重来。

## §2 判据（写在这里，账本照抄）

⛔ 不许用「截图 md5 互不相同」当判据（077 §2 已裁）。

1. **数据完整性（单测）**：每个主题必须有 16 个 ANSI 色 + `background` + `foreground` + `cursor`，
   缺一项该主题不得进清单。断言**具体色值常量**，不是「非空」。
2. **来源可核（单测或脚本）**：每个主题带 `source` 字段指向 iTerm2-Color-Schemes 的原文件名；
   判据脚本能从随包数据里把它读出来。
3. **NOTICE 存在且非空**，且含 `iTerm2-Color-Schemes` 与 `Mark Badolato` 两个串。
4. **设置页可选中（UI 树断言）**：`tools/uiassert.py` 断言主题列表项存在、选中态变化。
5. **切换真的改变了终端渲染**：🔴 **判据要断言「世界变了」**——
   切主题前后对同一屏取色采样，断言背景色值**从 A 变成 B 且 A≠B**，
   ⛔ 不许只断言「设置项被点了」。
6. **不倒退**：`./gradlew testDebugUnitTest` 全量绿；073/075/076/077/078/081/082 + land-v1 五格不倒退。
7. 🔴 **渲染类判据必须在两个不同 density 的 AVD 上各跑一遍，其中一个非整数密度**（083 §0）。

## §3 编排（用户明令：两个角色）

用户原话：「你必须有两个角色去做。第一个角色，给出思路。第二个角色，根据这个思路去做。」

| 格 | 角色 | 写范围 | 产出 |
|---|---|---|---|
| `t.plan` | 思路席 | **只写 `.team/nodes/theme-plan/`，⛔ 不碰 `app/`** | 方案文档：许可落实方案、主题清单核对结果、数据格式与生成方式、设置页信息架构、与 083 §2 的合流点、判据细化 |
| `t.impl` | 实现席 | `app/` + `.team/nodes/theme-impl/` | 照方案落地 + 判据全绿 |

**依赖**：`t.plan --requires_success--> t.impl`。

🔴 **`t.impl` 必须等 `vz-v1` 整张账本终态后才允许派单**——
铁律「同一 Gradle 模块同一时刻只放一席施工」，而 `vz-v1` 的 `t.bg`/`t.chrome`/`t.diff` 都在写 `app/`。
⇒ 本账本**先只放 `t.plan`**（它不碰 `app/`，与 `vz-v1` 无写冲突，可立即开跑）；
`vz-v1` 全绿后再「打针」提 revision 把 `t.impl` 加进来。
