# 057 发图预贴：对「一次性注入」的显式例外

- 状态：已裁定
- 类型：契约例外（对 [[003]] 第 1 条）
- 出处：用户 2026-08-14 原话「如果不发图，直接打字的话，就是直接上屏的。**我希望携带图片的时候也有这样的体验。**」
  与「点加号选择图片之后，就应该可以上传到对方的主机了。然后点发送就直接上屏了，这样体验更好。」

## 冲突是什么（由 w-img-probe 撞库发现并主动上报，不是事后补记）

[[003]] 第 1 条原文：「按发送那一刻整条消息经 send-keys **一次性注入**并回车」——
把「整条消息」与「发送那一刻」绑成一个原子动作。

而用户要的手感需要把注入**拆成两次**，中间隔着用户打字的时间：
上传成功即贴路径（让 CLI 后台开始解码），点发送只送文字 + 回车。
**结构上不再是「一次性」**，即便结果对用户更好。

查证结论：`042` 只管 App 自己的 `textFieldValue`（原话「导致你输入不方便」），
不管 CLI pane 那边的输入框，**不挡本设计**；
但也**没有任何现存条目批准过「发送前就往 CLI 输入框塞东西」**——这是真空地带。

## 裁定行为

**准予例外，但边界写死：**

1. **只对「带图片」这个子场景生效。** 纯文字消息完全不受影响，仍是原来的单次注入 + 回车。
2. **预贴的内容只能是图片路径本身**，不得包含用户文字——
   掺文字会落回 Claude Code 那条 fork `osascript` 的慢分支，Enter 被吞
   （见 `.team/evidence/fix-image-upload-input-box.json` 的回炉记录）。
3. **不清理 CLI 输入框。** 用户选了图却不发时，`[Image #N]` 允许滞留。
   理由：**App 是 pane 的镜像，那个占位符在用户屏幕上看得见，不是静默残留**；
   而「读懂 CLI 渲染出来的 UI 文本再决定要不要清」会引入一类新的脆弱性
   （Claude Code 改了占位符格式，判据静默失效），代价大于收益。
4. **附件语义由「单附件覆盖」改为「已贴进会话的图，可累加」。**
   连选两张就是两张，App 显示「已附加 N 张图」，与 CLI 输入框的实际状态一致。
   这比「清掉再贴」简单，且顺带支持了多图。
5. **手感判据（验收线）**：同一 pane 连续发一条纯文字、一条文字带图，
   两次「点发送 → 消息离开输入框」的耗时必须在**同一量级**。
   正常路径（用户打过字）必须是**零等待**；只有「选完图立刻发」才允许补差额。

## 为什么记这一条而不是悄悄绕过

[[038]] 定了「所有用户讨论记录入需求维基」。
更重要的是：**003 第 1 条不是随便写的**——「一次性注入」保证了「发送必达」可判定
（一个动作、一个 ack）。本例外把它拆成两步，等于把这个保证削弱到「带图场景下靠时间戳对齐」。
**后来的人必须能看见这个削弱是被明知且限定地批准的，而不是被人忘了。**
