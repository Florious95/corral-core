# 064 会话内悬浮窗：单独的实时流，展示 `Ctrl-B w` 那一页

- 日期：2026-08-18
- 裁定人：用户

## 一、用户原话

> 把 Ctrl+B+W 这一页单独做一个串流，我可以在会话当中，在右上角点击查看这个窗口。
> 它是一个悬浮窗口，然后点击窗口的其他地方，它就会消失。

## 二、形态

- **入口**：在**会话内**（三级终端画面）右上角一个按钮。
- **展开**：点击后浮出一个**悬浮窗**，盖在终端之上。
- **关闭**：**点击悬浮窗以外的任何地方即消失。**
- **内容**：全部节点总览，等价于 `Ctrl-B w` 那一页（会话 → 窗口树 + 每行的标题与状态）。
- **独立串流**：与二级菜单的列表流**分开**，各订各的，不共用一条流。

## 三、🔴 硬约束

### 1. 🔴 悬浮窗绝不影响用户真实窗口的尺寸

这是本条最硬的约束，优先于形态。（注：初稿写的是"不 attach"，
在改为抓屏保真后，**不 attach 可能做不到**——见下面第 3 条。
所以约束从"手段"（不 attach）收紧为"结果"（尺寸一个都不变），手段由实现席论证。）

理由（早先实测）：多客户端 attach 会参与 tmux 的尺寸协商，
**把用户真实窗口压小**。悬浮窗只是「看」，不该有任何副作用。

⇒ 打开/关闭悬浮窗，**用户所有真实会话的窗口行列数必须一个都不变**。这条要写成机械判据：
打开前采一次全部窗口的 `#{window_width}x#{window_height}`，打开悬浮窗、持续若干秒、关闭，再采一次，
**两次必须逐窗口完全相等**。任何一个变了就判红。

### 2. 打开才订阅，关掉即退订

零订阅者时服务端不得为这条流拉任何数据（工程常识红线①：空闲 CPU 趋近 0）。
悬浮窗绝大多数时间是关着的。

### 3. 🔴 内容要**抓屏保真**，不是自绘（2026-08-18 用户裁定，推翻本条初稿）

用户原话：
> 我还是建议跟我现在看到和你对话的这个对话窗口一样去抓屏，原生一致的，
> 有动态的，有动态转圈动态效果的。

⇒ 悬浮窗里要看到的是**那一页本身**：tmux 自己画的树线、对齐、以及**转圈符号的动画**。
不是我们按结构字段重画一个"长得差不多"的树。

**初稿写的是「用结构化字段渲染成树，不抓屏」，已被推翻，留档说明为何改：**
自绘拿不到动画，也拿不到 tmux 原生的排版；用户要的是「和我现在看到的一样」。

#### 这条的技术难点（必须正视，不许绕过）

`Ctrl-B w`（`choose-tree`）**不是某个 pane 的内容**，它是 tmux **客户端**画的覆盖层。
所以 `capture-pane` 抓不到它——要抓，就得有一个客户端处于那个模式。
而**多一个客户端就可能参与尺寸协商，把用户真实窗口压小**，
那正是本工程早先定下「二级菜单绝不 attach」的原因。

#### 一条候选路径（**推测，未验证，实现前必须先证伪或证实**）

为这件事单开一个**专用 tmux 会话**（scratch session），在它的 pane 里跑 `choose-tree`，
然后抓那个 pane。理由：它与用户的真实会话**不共用任何窗口**，
理论上不参与用户那边的尺寸协商；而 `choose-tree` 列的是整个 server 的所有会话，内容不缺。

⚠️ 未验证的点，逐条列出，实现席必须逐条给出结论：
1. `choose-tree` 跑在 pane 里时，`capture-pane` 能不能抓到它画的内容；
2. 它会不会随 pane 标题变化**自动重绘**（转圈动画要靠这个），还是只在按键时重绘；
3. 专用会话的客户端是否真的**零影响**于用户会话的尺寸
   （注意 tmux 3.x 的 `window-size` 选项默认值会影响这个结论，不要想当然）；
4. 抓屏频率与动画流畅度、CPU 之间怎么取舍。

#### 🔴 兜底纪律

**如果做不到「零尺寸影响」，不许悄悄降级、也不许悄悄接受副作用**——
发一条 `class="blocking"` 给 leader 说明，由 leader 裁定是改方案还是放弃该形态。
**用户的真实窗口被压小是不可接受的副作用，宁可不做这个功能。**

### 4. 状态沿用契约 062 的三态

进行中 / 空闲 / 未知，未知必须带证据、绝不回落空闲。

## 四、不做的事

- 不在悬浮窗里做操作（不发按键、不切换会话）。它只负责「看」。
  点击某一行是否跳转，**本条不定义**，等用户明确。
