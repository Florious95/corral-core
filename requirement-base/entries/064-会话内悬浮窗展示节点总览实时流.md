# 064 会话内悬浮窗：单独的实时流，展示 `Ctrl-B w` 那一页

- 日期：2026-08-18
- 裁定人：用户

## 一、用户原话

> 把 Ctrl+B+W 这一页单独做一个串流，我可以在会话当中，在右上角点击查看这个窗口。
> 它是一个悬浮窗口，然后点击窗口的其他地方，它就会消失。

## 二、形态

- **入口**：在**会话内**（三级终端画面）右上角一个按钮。
- **展开**：点击后浮出一个**悬浮窗**，盖在终端之上。
- **关闭**：**点击悬浮窗以外的任何地方即消失。**
- **内容**：全部节点总览，等价于 `Ctrl-B w` 那一页（会话 → 窗口树 + 每行的标题与状态）。
- **独立串流**：与二级菜单的列表流**分开**，各订各的，不共用一条流。

## 三、🔴 硬约束

### 1. 悬浮窗绝不参与终端尺寸谈判

它是 **App 内的覆盖层**，不是新开一个 tmux 客户端、不 attach。

理由（早先实测）：多客户端 attach 会参与 tmux 的尺寸协商，
**把用户真实窗口压小**。悬浮窗只是「看」，不该有任何副作用。

⇒ 打开/关闭悬浮窗，**当前会话的终端行列数必须一个都不变**。这条要写成机械判据。

### 2. 打开才订阅，关掉即退订

零订阅者时服务端不得为这条流拉任何数据（工程常识红线①：空闲 CPU 趋近 0）。
悬浮窗绝大多数时间是关着的。

### 3. 内容用结构化字段渲染，不抓屏

服务端给结构化数据（session / window_index / window_name / pane_title 原样 / state），
App 按 `Ctrl-B w` 的层级把它画成树。

**不去解析 tmux 渲染出来的那一页文本**——那要对付对齐、截断、树线字符、CJK 宽度、
终端宽度变化，而这些信息本来就是从结构字段拼出来的。

⚠️ **这是我的取舍，不是用户明确指定的。** 用户说的是「把那一页做成串流」。
如果你要的是**逐像素保真**（连树线字符都要一样），那要改成抓屏方案，代价见上。
说一声就改。

### 4. 状态沿用契约 062 的三态

进行中 / 空闲 / 未知，未知必须带证据、绝不回落空闲。

## 四、不做的事

- 不在悬浮窗里做操作（不发按键、不切换会话）。它只负责「看」。
  点击某一行是否跳转，**本条不定义**，等用户明确。
