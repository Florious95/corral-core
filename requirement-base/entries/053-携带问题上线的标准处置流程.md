# 053 携带问题上线的标准处置流程（回炉）

- 状态：已裁定（流程类，通用方法论）
- 类型：工作流 W-04
- 出处：用户 2026-08-12 原话「凡事出现携带问题上线的情况都要这么做」

## 触发条件

**凡修复后实测未生效（携带问题上线）**——不是 D-26 特例，是所有「改了没用」的标准流程。

## 流程（6 步）

1. **回退**该 commit。
2. **架构师审查**：分析为什么没生效，给出 MVP 方案。
3. **MVP 自身测试**：实机验证 MVP 方案可行。
4. MVP 测试通过。
5. 改工程代码。
6. 工程代码覆盖测试。

> 修正轨迹：初版为 5 步（无第 3 步 MVP 自身测试），用户补裁定后在 2 与 4 之间插入「MVP 自身测试」环节成 6 步。

## 回炉的工程原理（用户 2026-08-12 阐述）

回炉不只是流程，背后有工程原理：

1. 问题没解决却上了线 = **对应代码本身有问题**。
2. agent 上下文有限，项目越大理解代码越耗上下文，视角受限 → **加代码比删改代码更安全**（agent 倾向加而不是改）。
3. 腐败代码越堆越多形成**正反馈循环**——坏代码吸引更多坏代码。
4. 回炉首先**删除问题代码**，打断腐败堆叠的正反馈循环。

**核心洞察：回炉的价值不只是「重做」，而是「先删再做」——删除本身就是治疗。**
