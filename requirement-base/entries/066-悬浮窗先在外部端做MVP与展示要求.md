# 066 悬浮窗：先在外部端做 MVP，再进 App；以及展示要求

- 日期：2026-08-19
- 裁定人：用户（原话见下）
- **补充** `064` / `065`。形态、尺寸零影响、三缺陷修复要求全部不变。

## 一、裁定原文

> 你们在开发的时候可以先做 MVP，可以先构建一个外部端，然后把同样的实现，基于这个外部端
> 去完成这样一个小模块的实现，然后调试它，确定它展示的是简洁的样式，包含简洁的样式，
> 能够直接的以中文方式、中英文方式去看它的那个目录树，并且全部展开，
> 并且能看动态的看到它是工作还是停止。

## 二、方法：先外部端 MVP，再进 App

**先在外部端（web 端）把这个小模块做出来、调通、看对，再搬进安卓 App。**

理由（与本工程既有的测试三层流水线一致）：
- 第 1 层 Web 端能拦掉大部分问题，且**改一次看一次的循环快得多**；
- 安卓侧每次验证都要出 APK、装机、人工看图，一轮几十分钟；
- 2026-08-18 实测代价：悬浮窗第一版在安卓上才发现「ANSI 当文本画、画面无限追加、socket 取错」
  三个问题，而这三个**在 web 端一眼就能看见**。

⇒ 顺序：**web 端 MVP 调好样式 → 用户看过认可 → 再实现安卓侧**。

## 三、展示要求（可验收的口径）

| 要求 | 口径 |
|---|---|
| **简洁的样式** | 不出现任何裸控制序列；不出现观测装置自身（scratch 会话）；没有重复堆叠 |
| **中文 / 中英文正常** | 会话名与标题里的中文、以及中英混排，**不得乱码、不得错位**（CJK 宽度按双宽算） |
| **目录树全部展开** | 所有会话、窗口默认**全展开**，不需要用户再操作去展开 |
| **动态看到工作还是停止** | 每个节点的工作/停止状态**实时变化可见**（转圈动画或状态标，二者至少其一动起来） |

🔴 「简洁」这条容易变成主观判断。可机械化的部分必须机械化（前两列已在 065 写成判据）；
**剩下真正主观的部分（好不好看、密度合不合适）由用户在 web 端 MVP 上看过点头**，
不要在安卓侧才第一次给用户看。

## 四、边界

- 外部端 MVP 的目的是**调样式与验证机制**，不是交付物；它可以简陋，但**必须走真实的服务端流**，
  不许用假数据糊一个界面——假数据能让样式看起来对，却验不出 socket 取数、渲染、刷新这三件事。

## 附：MVP 落地后，安卓端怎么验（2026-08-19 leader 裁定）

web MVP 已做成（`web/js/overlay.js` 的 `OverlayEmulator`：解释备用屏/清屏/SGR，**整屏替换**；
实测中文树、全展开、8 帧转圈 `✳◐◑◒✳◐◑◒`、行数恒为 7 有界）。安卓端要的是同一层能力。

**但探针不能直接改用 web 那份 JS 模拟器去渲染** —— 那会立刻变绿而安卓仍然是坏的（假绿）。
现行探针 `probe-ov2.sh` 的渲染口径写死为「与当前 App 一致：把 `overlay_frame.text` 当普通字符串画」，
这个口径在 App 改用模拟器之后就过期了。

⇒ **正确形状（三段，缺一段就会假绿或永远假红）**：

1. **抓夹具**：探针连真实服务端流，把连续 ≥8 帧的 `overlay_frame`（含 `text`/`rows`/`cols`）
   原样落盘成夹具 `.team/nodes/ov2-probe/frames.jsonl`。
2. **喂安卓自己的渲染器**：一个 Kotlin 单测（名须含 `OverlayEmulatorFixture`）读该夹具，
   逐帧喂进 **App 真实的 OverlayEmulator**，取最终屏幕文本。
3. **在渲染结果上断言三条**（与 065 一致）：①无裸控制序列；②目标会话在、scratch 不在；
   ③行数有界（≤ `rows`）且同一棵树不重复。

探针的退出码 = 该 Kotlin 单测的退出码。**⛔ 不得用 JS 模拟器代跑**——被测对象是安卓的渲染器。
