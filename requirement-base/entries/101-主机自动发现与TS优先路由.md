## 用户原话（按先后顺序）

### 1. 主机自动发现，用户不再面对链接

> 我们来讨论，不要动手，很简单的，那就是希望服务端能够被客户端自主发现。并且是从多个途径发现，就比如说我先输入了TS的token，先入了网，那么它也能发现TS相关的IP并且构造链接。你就说现在要把链接这概念从我们的客户端上完全被移除。以后就不关注链接，只有token。链接是被自动发现的。同时的话，这个地方不要做选择，就是你连接TS就TS，你连接局域网就局域网。为什么？因为TS在局域网的情况下，它本身也是直连的，它跟局域网没什么区别。但是你切换有成本。你就说用户打开这个APP，无论是扫码还是什么，它都是扫的是哪一台主机，并且它的token是什么，然后链接是自主发现的，用户可以连接填写TS的token入网。那么在用户的眼中，在绑定界面就只有主机以及对应的token，没有链接的概念。主机是自主发现的。并且在任何情况下都优先使用TS。

### 2. TS 优先、允许局域网兜底、当前可用则保持

> 优先使用TS，那当然TS呢没有入网成功那就提示。同时的话，允许自动通过局域网连接。下次重连再优先TS。不要立即切过去。比如说这个时候就有一个路由的策略。它分为TS可用、局域网可用。当前是TS、当前是局域网。来形成状态空间。实际上这个东西按照我上面的理解是直接能给出来的，不需要额外解释。它的支撑点就在于TS可用的话，TS连接它本身也等于局域网。同时的话不要主动切换，当前能用就用，下次重连的时候，就按照新的策略。

### 3. 最终更正：不提示失败，两者不可用时工作区为空

> 我上面说错了，TS入网不需要提示。因为右上角直接显示的是局域网还是TS网页。我说两个都不可用的时候，工作区就是空的，这个时候都不需要提示。

原话中的“TS网页”按本轮随后确认的语境理解为右上角的 TS／局域网网络类型显示；不据此新增网页功能。

## 最终有效需求（整理，不是新增原话）

1. 用户绑定的是主机及其 token，不是一个固定地址。绑定界面去掉链接概念，不要求用户填写或选择 IP、端口、URL、网络路径。
2. 客户端通过多个途径自动发现主机及其可用地址，至少包括 TS 和局域网。输入 TS token 入网后，也要能发现 TS 相关地址并在内部构造连接。
3. 扫码识别的是目标主机及其绑定 token，地址由客户端自主发现；具体发现协议、扫码载荷字段与身份实现尚未设计。
4. TS token 用于 TS 入网，主机 token 用于主机绑定鉴权；二者用途不同，不把它们合并成同一个凭据，也不在文档中记录真实 token。
5. 首次连接和每次重连时优先 TS；TS 不可用且局域网可用时自动使用局域网，不让用户选择。
6. 当前连接能用就保持，不因为另一条路径变得可用而主动切换。特别是当前使用局域网时，TS 恢复不抢占，下次重连再优先 TS。
7. 右上角显示当前实际使用的网络类型：TS 或局域网。它是状态显示，不是路径选择器。
8. TS 入网失败不提示，不阻止局域网自动连接；TS 与局域网都不可用时，工作区为空，不显示额外弹窗、错误条或提示文案。

## 路由状态空间

“可用”描述对应路径当前的可用状态；表格不规定探测算法或判定阈值。当前连接仍可用时，不因策略偏好强制重建连接。

| TS 可用 | 局域网可用 | 当前为 TS | 当前为局域网 | 首次连接／重连 |
|---|---|---|---|---|
| 是 | 是 | 保持 TS | 保持局域网 | TS |
| 是 | 否 | 保持 TS | 当前连接失效后重连 TS | TS |
| 否 | 是 | 当前连接失效后重连局域网 | 保持局域网 | 局域网 |
| 否 | 否 | 工作区为空，不额外提示 | 工作区为空，不额外提示 | 工作区为空，不额外提示 |
