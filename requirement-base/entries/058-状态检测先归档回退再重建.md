# 058 状态检测：先归档回退，再重建

- 状态：已裁定
- 类型：处置裁定（[[025]] 施工的**强制前置**）
- 出处：用户 2026-08-15 原话「你现在记下来，也就是你在解决这个状态问题的时候，**一定要把对应的代码归档**，因为现在这个状态检查基本上是**完全不可用、完全不准确**的状态。也就是**回退与归档**。」

## 现状（用户判定，不是我们自评）

当前 Agent 工作状态检测**完全不可用、完全不准确**。这不是「准确率低」的量级问题，
是**判据本身不成立**——见 [[025]] 记录的三次修复三次失败，以及 2026-08-15 的复盘结论：

> 信息不在字形里，在导数里。三次都在调一张不含答案的白名单。

实证：调研文档记的 working 白名单是 braille `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`，
而用户 2026-08-15 截图显示 Claude Code 当前吐的是 `◐`（工作中）/ `✳`（空闲）——
**字形改版，白名单静默失明**。

- **归档对象**：`server/internal/agentstate/`（2026-08-15 时为 1699 行，
  含 `adapters.go` / `rules.go` / `identify.go` / `sample.go` / `track.go` 及其测试），
  以及 `server/internal/protocol/state.go` 的 `StateDone`
  （后者另有 2026-08-13 用户裁定「取消完成态，只留 working/idle」，至今未实现）。
- **归档不是删除**：落 `docs/archive/agentstate-round4/`，
  与 `docs/archive/image-attach-round1/`、`docs/archive/pane-reflow-wip/` 同规格。
- **归档物是根因探针的输入**，不是垃圾桶。按 [[053]]/[[054]] 回炉流程第 2 步，
  审查席读被回退的 diff 反推根因，产出根因探针；**回退后跑探针必须命中**，
  不命中说明诊断错了，不许往下走。

## 为什么必须先删再做

CLAUDE.md 已写死的回炉工程原理：

> agent 上下文有限倾向加代码，腐败代码正反馈堆叠，**回炉先删再做打断循环**。

本条是这条原理在状态检测上的具体应用，而且证据比一般情况更硬：
**三轮修复全部是「往白名单里加/减字形」**——每一轮都在同一个错误结构上加代码。
第四轮如果还在 `rules.go` 上打补丁，**它一定是第四次失败**，
因为那个文件的存在本身就在把人往「维护一张字形表」上引。

**判据换了（差分/存在，而非字形匹配），承载它的结构就不该是原来那个。**

## 边界

1. 归档**只针对状态检测**，不动同目录之外的采集链路（`RecentOutput`/`PaneTitle` 的**取数**保留，
   被否定的是**决策函数**）。
2. 归档动作本身要有独立提交（[[提交纪律]]「一次归档回退 = 一个关键点」）。
3. 归档后到新判据落地之间，状态字段应当**明确报 unknown**，
   **不许留一个会骗人的旧值**——[[012]] 的「unknown 不计入」兜得住判不出，兜不住判错。
